# ARCHITECTURE — {{PROJECT_NAME}} (Gradle 멀티모듈)

이 문서는 `{{PROJECT_NAME}}`의 **기술 아키텍처 정본**이다. 진입 가이드는 `./AGENTS.md`·`./CLAUDE.md`, 빌드·실행 상세는 `./README.md`와 `.agents/rules/tech.md`를 본다.

본 프로젝트는 **Gradle 멀티모듈**이다. 이 변형이 강제하는 것은 **모듈 의존 방향 하나**이고,
**모듈을 무엇으로 자를지는 프로젝트가 정한다** — 도메인 서비스, 외부 연동 어댑터, 기술 관심사, 공유 커널 무엇이든 될 수 있다.
의존 방향 위반은 리뷰가 아니라 **컴파일 실패**로 막힌다.

> **`hexagonal`과 무엇이 다른가**: 둘 다 Gradle 멀티모듈이다. 차이는 **규격의 강도**다.
> `hexagonal`은 *바운디드 컨텍스트당 `domain`·`application`·`primary`·`infra` 4모듈*이라는 **고정 규격**을 강제한다.
> `multimodule`은 **분할 축을 프로젝트가 고르고**(§3.1), 킷은 **등급 간 의존 방향과 공개 표면 규약만** 강제한다.
> 도메인 모델이 자산이고 규격을 통일하고 싶으면 `hexagonal`, 모듈 성격이 제각각이면 `multimodule`이다.

**이 문서의 `<module>`·`<shared>`·`<runtime>`은 자리표시자다.** 실제 이름은 §3.2에서 프로젝트가 정해 이 문서에 적는다.

스택 기준(버전 정본은 `gradle/libs.versions.toml` 단일 소스 — 구체 라이브러리·버전은 **프로젝트가 확정**):
**Kotlin/Java · Spring Boot(JVM)** · **Gradle 멀티모듈**(Java=Groovy DSL / Kotlin=Kotlin DSL, wrapper) · **버전 카탈로그** · **구조 테스트 도구**(ArchUnit 또는 Konsist).

## 0. 이 변형을 언제 쓰나 (선택 기준)

**쓴다:**
- **의존 격리를 컴파일러에게 맡기고 싶다.** 단일 모듈에서는 "이 패키지가 저 패키지를 참조하면 안 된다"를 테스트로만 막지만, 모듈이면 **빌드가 막는다**.
- **무거운/위험한 의존을 가둬야 한다.** 특정 SDK·드라이버·레거시 라이브러리가 전체 코드베이스로 새는 것을 막는다.
- 성격이 다른 것들이 한 배포 단위 안에 산다 — 예: 도메인 서비스 + 외부 연동 어댑터 + 배치 + 영속.
- **같은 역할의 구현이 여럿**이라 갈아 끼우거나 폴백해야 한다(§4.3).
- 모듈 단위 **재사용·병렬 빌드·빌드 캐시** 이득이 실제로 있다.

**쓰지 않는다:**
- 모듈이 사실상 하나다 → `layered`. 멀티모듈은 빌드 시간과 설정 비용만 늘린다.
- 규격을 통일한 **도메인 중심 설계**가 목표다 → `hexagonal`(컨텍스트당 4모듈 고정).
- 경계는 필요하지만 **빌드를 쪼갤 만큼은 아니다** → `modulith`(패키지가 모듈, Spring Modulith가 검증) 또는 `feature`(ArchUnit 슬라이스).
- 이미 독립 배포가 필요하고 조직도 그렇게 나뉘어 있다 → 별도 서비스로 분리(이 킷 범위 밖).

**승격/후퇴 신호:**
1. 모듈이 하나만 실질적으로 살아 있다 → `layered`로 후퇴(모듈 유지 비용 제거).
2. 구성 모듈들이 서로를 계속 참조하고 싶어한다 → **분할 축이 틀렸다**. §3.1로 돌아가 다시 자른다.
3. 한 모듈의 도메인 규칙이 지배적으로 두꺼워진다 → 그 모듈만 `hexagonal` 4모듈로 승격.
4. 특정 모듈이 독자적인 배포 주기·확장 요구를 갖는다 → 별도 서비스 분리 검토.
5. 전체 빌드가 느려 개발 흐름을 끊는다 → 병렬 빌드·빌드 캐시를 켜고, 그래도 느리면 모듈 수를 다시 본다. **모듈을 늘리는 것은 공짜가 아니다.**

전환 절차는 §12.

## 2. 시스템 경계

```
 ┌──────────┐        ┌──────────────────────────────────────────────┐
 │ Client   │───────▶│  {{PROJECT_NAME}}   (단일 배포 단위)          │
 │(Web/CLI) │        │  ┌────────────────────────────────────────┐  │
 └──────────┘        │  │ 실행 모듈 — 조립·부팅                  │  │
                     │  ├────────────────────────────────────────┤  │
                     │  │ 구성 모듈 A │ 구성 모듈 B │ 구성 모듈 C │  │
                     │  ├────────────────────────────────────────┤  │
                     │  │ 공유 모듈 — 계약·공용 모델·envelope     │  │
                     │  └────────────────────────────────────────┘  │
                     └───┬──────────────┬──────────────┬────────────┘
                         ▼              ▼              ▼
                   ┌───────────┐  ┌────────────┐  ┌────────────┐
                   │ 관계형 DB │  │ 외부 시스템│  │ 그 외(선택)│
                   │  (선택)   │  │   (선택)   │  │            │
                   └───────────┘  └────────────┘  └────────────┘
```

- **배포 단위는 하나**다. 모듈은 배포 경계가 아니라 **의존 격리 경계**다.
- 데이터 저장소·외부 시스템·캐시·큐는 **모두 선택**이며 프로젝트가 채택 여부를 정한다.
- 서비스 인스턴스는 **무상태**. 카운터·랭킹·세션 같은 공유 상태는 **DB나 외부 캐시**에 둔다 — 인스턴스 로컬 `static` 필드·JVM 락은 인스턴스가 2대가 되는 순간 무의미해진다(§11).

## 3. 모듈 구조

### 3.1 분할 축 고르기 (가장 먼저 답할 질문)

**모듈을 무엇으로 자를 것인가.** 하나만 고를 필요는 없지만, **왜 그렇게 잘랐는지 여기에 적는다.**

| 분할 축 | 언제 | 모듈 예시 |
|---|---|---|
| **도메인** | 서로 다른 업무 영역이 한 배포 단위에 산다 | `{{DOMAIN_EXAMPLE}}` · `user` · `notification` |
| **연동 대상** | 같은 역할의 외부 시스템이 여럿이거나 SDK가 무겁다 | `<vendor-a>` · `<vendor-b>` |
| **기술 관심사** | 영속·배치·메시징 등 기술 스택이 다른 덩어리가 있다 | `jpa` · `batch` · `messaging` |
| **공개 표면** | 웹 API와 관리자/내부 API의 노출 경계가 다르다 | `api` · `admin` |

- **분할 축은 섞어도 된다.** 실제 프로젝트는 보통 `도메인 몇 개 + 연동 어댑터 몇 개 + 영속 하나`처럼 섞인다.
- **모듈을 만들 이유가 "폴더가 커서"라면 만들지 않는다.** 패키지로 충분하다. 모듈은 **의존을 끊고 싶을 때** 만든다.
- 애매하면 **적게 자른다**. 합치는 것보다 나중에 쪼개는 것이 쉽다.

> **채택한 분할 축과 이유**: `(여기에 적는다)`

### 3.2 모듈 네이밍 (프로젝트가 정하고 여기에 기록)

킷은 이름을 강제하지 않는다. **한 가지 규약을 정해 일관되게 쓰는 것**만 지킨다.

```
# 예시 A — 접두사만 통일 (가장 흔함)
:{{PROJECT_SLUG}}-api       :{{PROJECT_SLUG}}-{{DOMAIN_EXAMPLE}}   :{{PROJECT_SLUG}}-jpa       :{{PROJECT_SLUG}}-common

# 예시 B — 역할을 접미사로 구분
:{{PROJECT_SLUG}}-bootstrap :{{PROJECT_SLUG}}-<vendor>-client      :{{PROJECT_SLUG}}-storage   :{{PROJECT_SLUG}}-contract

# 예시 C — 접두사 없이 짧게 (모듈 수가 적을 때)
:app                        :{{DOMAIN_EXAMPLE}}                     :persistence                :core
```

> **채택한 규약**: `(여기에 적는다 — 예: 접두사 {{PROJECT_SLUG}}- + 역할 단어 하나)`

- 이름에 `client`·`adapter` 같은 단어를 **의무적으로 붙이지 않는다.** 뜻이 분명해질 때만 붙인다.
- 모듈명은 **그것이 무엇인지**를 말해야 한다. `common2`·`util`·`core-new` 같은 이름은 분할 축이 없다는 신호다.
- 계층형 경로(`:a:domain`·`:b:domain`)를 쓰면 리프 모듈명이 겹쳐 capability 충돌이 난다. 이때는 `group`을 모듈별로 분리하고 `archivesName`을 경로 기반으로 유니크화한다.

### 3.3 모듈 등급과 의존 방향 (컴파일 강제)

이름이 무엇이든 모든 모듈은 **세 등급 중 하나**다. 의존은 **위에서 아래로만** 흐른다.

| 등급 | 역할 | 개수 | 의존 가능 |
|---|---|---|---|
| **실행(runtime)** | `@SpringBootApplication`·조립·설정·실행. `bootJar` 산출 | **1** | 구성 · 공유 (전부) |
| **구성(component)** | 도메인·어댑터·기술 관심사 — §3.1의 분할 결과 | N | **공유만** |
| **공유(shared)** | 계약 인터페이스·공용 모델·envelope·ErrorCode·예외 | 0~2 | **없음**(프레임워크 최소) |

> **이 프로젝트의 모듈 등급표** (모듈을 추가할 때마다 여기에 등록한다)
>
> | 모듈 | 등급 | 역할 | 의존 |
> |---|---|---|---|
> | `<runtime>` | 실행 | 부팅·조립·웹 경계 | 전부 |
> | `<module-a>` | 구성 | (역할) | `<shared>` |
> | `<shared>` | 공유 | 계약·공용 모델 | — |

- **의존 금지(컴파일 차단)**: `구성 → 실행`, `공유 → 구성/실행`, `구성 A ↔ 구성 B`(§3.4 예외 제외).
- **공유 모듈에는 Spring Web·JPA·벤더 SDK를 부착하지 않는다.** 여기에 무거운 의존을 넣으면 모든 모듈이 그것을 끌고 간다 — 격리의 목적이 사라진다. 검증(`jakarta.validation`)·직렬화 어노테이션 정도가 상한이고, 그것도 넣기 전에 왜 필요한지 답한다.
- **공유 모듈을 늘리지 않는다.** "둘 다 쓰니까 공유로"를 반복하면 공유 모듈이 사실상 전체가 된다. 둘만 쓰는 것은 **한쪽이 소유하고 계약으로 노출**한다.
- 실행 모듈에는 **조립과 설정만** 둔다. 비즈니스 로직이 실행 모듈에 쌓이면 모듈 분할이 무의미해진다.

### 3.4 구성 모듈 간 의존 (기본 금지 · 예외는 기록)

구성 모듈이 서로를 필요로 하면 **분할 축이 틀렸을 가능성을 먼저 의심한다.** 그래도 필요하면 셋 중 하나를 고른다.

| 방법 | 언제 | 대가 |
|---|---|---|
| (a) 계약을 **공유 등급으로 올린다** | 양쪽이 대등하게 쓰는 개념 | 공유 모듈이 커진다 |
| (b) **실행 모듈이 조립**한다(계약 주입) | 한쪽이 다른 쪽 결과를 쓰는 정도 | 실행 모듈이 배선을 안다 |
| (c) **직접 의존을 선언적으로 허용** | 명백한 상하 관계(예: `{{DOMAIN_EXAMPLE}} → user` 조회) | 순환 위험·분리 비용 |

**(c)를 고를 때 지킬 것:**
- 허용한 간선을 **아래 표에 반드시 기록**한다. 기록되지 않은 구성 모듈 간 의존은 리뷰에서 되돌린다.
- **순환은 절대 금지**다(Gradle이 막지만, 막히기 전에 설계를 다시 본다).
- 의존하는 쪽은 상대의 **공개 계약 타입만** 참조한다. 상대의 엔티티·DTO·내부 구현은 참조하지 않는다(§3.5).

> **허용된 구성 모듈 간 의존** (없으면 "없음"으로 유지)
>
> | from | to | 이유 | 승인일 |
> |---|---|---|---|
> | — | — | — | — |

### 3.5 모듈 공개 표면 (밖으로 나가는 것 / 갇히는 것)

각 구성 모듈은 **자기 안에 갇혀야 할 것**을 갖는다. 이것이 새면 모듈로 자른 의미가 없다.

| 모듈 안에 갇히는 것 | 모듈 밖으로 나가는 것 |
|---|---|
| JPA 엔티티 · 영속 매핑 | 공유 모듈의 공용 모델 / 값 객체 |
| 외부 SDK 타입 · 벤더 응답 DTO · 인증 자격증명 | 공개 계약 인터페이스의 구현 빈 |
| 내부 매퍼 · 내부 설정(`@ConfigurationProperties`) | 공유 모듈의 `ErrorCode`로 변환된 예외 |
| 모듈 전용 상수 · 내부 헬퍼 | (그 외 없음) |

- **변환은 소유 모듈 안에서 끝낸다.** 다른 모듈에 `<Vendor>ToDomainMapper`나 `<Entity>ToDto`가 생기면 경계가 잘못 그어진 것이다.
- **JPA 엔티티를 모듈 밖(컨트롤러·다른 모듈·응답)에 노출하지 않는다.** 영속 모델 변경이 곧 API 변경이 되어버린다.
- 외부 시스템의 HTTP 에러·타임아웃은 **소유 모듈에서 공유 모듈의 예외 타입으로 변환**해 던진다. 그래야 호출자가 벤더 중립으로 유지된다.

### 3.6 구조 테스트 (모듈 그래프가 못 잡는 것)

모듈 그래프는 **모듈 간 의존**을 막는다. 그러나 **모듈 안에서의 타입 누출**과 **네이밍·응답 규약**은 못 잡는다.
아래 골격을 **실행 모듈의 테스트 소스셋**(모든 모듈이 클래스패스에 올라오는 유일한 지점)에 두고 프로젝트에 맞게 늘린다.

```java
// 실행 모듈 test 의존에 ArchUnit 을 추가한다(카탈로그 경유 — tech.md 참조).
// Kotlin 프로젝트면 Konsist 로 같은 규칙을 표현해도 된다.
package {{PACKAGE_NS}}.architecture;

import com.tngtech.archunit.core.domain.JavaClasses;
import com.tngtech.archunit.core.importer.ClassFileImporter;
import org.junit.jupiter.api.Test;

import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.noClasses;
import static com.tngtech.archunit.library.dependencies.SlicesRuleDefinition.slices;

/** 모듈 그래프가 못 잡는 누출을 막는다. 이 테스트가 모듈 경계의 두 번째 강제 장치다. */
class ModuleBoundaryTest {

    private final JavaClasses all = new ClassFileImporter().importPackages("{{PACKAGE_NS}}");

    @Test
    void JPA_엔티티는_소유_모듈_밖으로_나가지_않는다() {
        noClasses().that().resideOutsideOfPackage("{{PACKAGE_NS}}.<persistence-module>..")
            .should().dependOnClassesThat().areAnnotatedWith("jakarta.persistence.Entity")
            .check(all);
    }

    @Test
    void 외부_SDK_타입은_소유_모듈_밖으로_나가지_않는다() {
        // 벤더 SDK 패키지를 프로젝트에 맞게 채운다. 외부 연동이 없으면 이 테스트는 지운다.
        noClasses().that().resideOutsideOfPackage("{{PACKAGE_NS}}.<vendor-module>..")
            .should().dependOnClassesThat().resideInAnyPackage("<vendor.sdk.package>..")
            .check(all);
    }

    @Test
    void 공유_모듈은_프레임워크를_모른다() {
        noClasses().that().resideInAPackage("{{PACKAGE_NS}}.<shared>..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("org.springframework.web..", "jakarta.persistence..")
            .check(all);
    }

    @Test
    void 모듈_간_순환이_없다() {
        slices().matching("{{PACKAGE_NS}}.(*)..").should().beFreeOfCycles().check(all);
    }
}
```

- **규칙은 프로젝트의 모듈 이름으로 채워야 작동한다.** `<persistence-module>`·`<vendor-module>`·`<shared>`를 그대로 두면 아무것도 검사하지 않는다.
- **규칙이 0개 클래스를 검사하면 실패로 취급한다.** ArchUnit 1.x는 `archRule.failOnEmptyShould` 기본값이 `true`다 — 자리표시자 미치환·패키지명 오타로 규칙이 조용히 죽는 것을 잡는 자동 감지이므로 `archunit.properties`에서 끄지 않는다.
- 해당 없는 규칙은 **주석 처리가 아니라 삭제**한다. 죽은 규칙은 "검사하고 있다"는 착각만 남긴다.
- 규칙을 `@Disabled`로 끄는 것 = 경계를 없애는 것이다. 규칙이 틀렸다면 `.agents/docs/decisions/`에 ADR을 남기고 경계를 다시 긋는다.

## 4. 모듈 통합 규약

### 4.1 계약은 공유 등급에, 구현은 구성 등급에

- 다른 모듈이 필요로 하는 것은 **인터페이스로 공유 등급에 올리고**, 구현은 소유 모듈에 둔다. 호출자는 인터페이스만 안다.
- 계약 시그니처에는 **공용 모델만** 쓴다. 엔티티·벤더 DTO가 시그니처에 등장하면 그것은 계약이 아니라 누출이다.
- **공개 표면을 작게 유지한다.** 공유 등급에 타입을 하나 더 올리는 것은 "이건 계약이다"라는 선언이고, 되돌리기 어렵다.

### 4.2 조립은 실행 모듈에서

- 구현 빈의 배선은 실행 모듈의 설정에서 한다. 구성 모듈이 다른 구성 모듈의 빈을 직접 찾지 않는다.
- 라이브러리 모듈의 `@Configuration`은 **실행 모듈의 컴포넌트 스캔 범위 밖**이다. `@AutoConfiguration` + `META-INF/spring/…AutoConfiguration.imports`로 자기 설정을 스스로 등록하거나, 실행 모듈이 명시적으로 `@Import` 한다.
  실행 모듈에서 `@ComponentScan(basePackages = "…다른 모듈 내부…")`로 남의 패키지를 긁는 방식은 쓰지 않는다 — 모듈이 자기 설정의 주인이 아니게 되고, 모듈을 추가할 때마다 실행 모듈을 고쳐야 한다.

### 4.3 (선택) 같은 역할의 구현이 여럿일 때

동일 계약의 구현이 둘 이상이고 **런타임에 골라야 하는 경우**(연동 벤더 다중화, 폴백, A/B, 비용 기반 라우팅)에만 적용한다.
구현이 하나뿐이면 **이 절은 건너뛴다** — 그때 인터페이스와 레지스트리는 오버엔지니어링이다.

```java
// 공유 등급: 계약 + 구현 식별자
public enum Provider { A, B }

public interface {{DOMAIN_EXAMPLE}}Port {
    Provider provider();                                        // 구현이 스스로 선언 → 레지스트리 키
    {{DOMAIN_EXAMPLE}}Result execute({{DOMAIN_EXAMPLE}}Command command);   // 인자·반환 모두 공용 모델
}
```

```java
// 실행 등급: 레지스트리 — Spring 이 모든 구현을 주입한다
@Component
public class ProviderRegistry {

    private final Map<Provider, {{DOMAIN_EXAMPLE}}Port> byProvider;

    public ProviderRegistry(List<{{DOMAIN_EXAMPLE}}Port> ports) {
        // 생성 시점에 확정되는 불변 맵. 등록 누락이 구조적으로 불가능하다.
        this.byProvider = ports.stream()
            .collect(Collectors.toUnmodifiableMap({{DOMAIN_EXAMPLE}}Port::provider, Function.identity()));
    }

    public {{DOMAIN_EXAMPLE}}Port get(Provider provider) {
        var port = byProvider.get(provider);
        if (port == null) throw new ProviderNotConfiguredException(provider);
        return port;
    }
}
```

**규칙:**
- **레지스트리 키는 구현이 스스로 선언한다.** 빈 이름 문자열 매칭이나 클래스명 규약으로 매핑하면 이름을 바꾸는 순간 컴파일러 경고 없이 라우팅이 깨진다(§11).
- 맵은 **생성자에서 확정된 불변 맵**이다. `static`/가변 맵을 `@PostConstruct`로 채우지 않는다(§11).
- 새 구현 추가 = 새 모듈 + 구현 1개 + 식별자 1개. **레지스트리와 호출자는 손대지 않는다**(OCP).

**폴백을 둔다면:**
- **잡는 예외를 좁힌다.** 회복 가능(타임아웃·5xx·rate limit)만 다음 구현으로 넘긴다. `catch (Exception)`으로 전부 삼키면 코드 버그(NPE·매핑 오류)가 "외부 장애"로 위장되어 원인이 영원히 안 드러난다.
- **회복 불가능(4xx 요청 오류·인증 실패)은 즉시 올린다.** 다음 구현도 똑같이 실패한다.
- **순서는 설정에서** 온다. 장애 대응이 배포가 되면 안 된다.
- **어느 구현이 응답했는지 결과에 남긴다.** 응답 품질이 구현마다 다르고, 폴백률은 지표다.
- 전부 실패하면 **마지막 실패를 `cause`로 달아** 올린다. 폴백은 유한하다(순환·재귀 금지).

## 5. 레이어 책임

| 위치 | 책임 | 하지 않는 것 |
|---|---|---|
| 실행 모듈 | 부팅·조립·설정·전역 예외 처리·(웹을 여기 두면) HTTP 경계 | 비즈니스 로직 축적 |
| 구성 모듈(도메인) | 업무 규칙·유스케이스·**트랜잭션 경계** | 다른 모듈 내부 참조, HTTP 상태코드 판단 |
| 구성 모듈(어댑터) | 외부 호출·인증·재시도·정규화·예외 변환 | 유스케이스 판단 |
| 구성 모듈(영속) | 엔티티·쿼리·영속 어댑터 | 트랜잭션 경계 선언, 비즈니스 규칙 |
| 공유 모듈 | 계약·공용 모델·envelope·ErrorCode | 구현, 프레임워크 의존 |

- **트랜잭션 경계는 유스케이스 서비스에만.** 영속 어댑터·리포지토리·**엔티티**에 `@Transactional`을 붙이지 않는다. 특히 **엔티티 메서드의 `@Transactional`은 프록시 대상이 아니라 아무 효과도 없다**(§11).
- **외부 호출을 트랜잭션 안에 넣지 않는다.** 외부 응답이 3초 걸리면 DB 커넥션을 3초 잡는다. 조회 → 트랜잭션 열기 → 저장 순으로 분리한다.
- **생성자 주입 only.** `@Autowired` 필드/세터 주입·`@Value` 필드 주입 금지 — 설정은 `@ConfigurationProperties`로 받아 생성자로 넘긴다(테스트에서 값을 바꿔 끼울 수 있어야 한다). 시간·난수·ID는 인터페이스로 주입한다.
- **파싱·검증은 경계에서.** 외부 입력(HTTP·큐·파일)은 인바운드 경계에서 DTO로 검증한 뒤 안쪽으로 넘긴다.
- **로깅은 경계에서 한 번만.** 외부 호출 실패는 어댑터에서 한 번, 정책 판단은 유스케이스에서 한 번. **자격증명·토큰·인증 헤더는 절대 로그에 남기지 않는다.**
- **횡단 관심사(AOP)의 실패가 주기능을 죽이지 않게 한다.** 수집·감사 같은 부가 기능은 예외를 삼켜 지표로 올리거나 비동기로 뺀다.

## 6. 코드 주석 규약 (요약)

- 코드는 라인 단위 What/How를, 주석은 Why를 설명한다. 단 **함수·메서드 Javadoc/KDoc은 ① 책임 한 줄 + ② 비자명한 Why + ③ `처리 흐름:`(의도를 곁들인 단계)** 로 로직 이해를 돕는다.
- **모듈 공개 계약에는 계약 주석을 반드시 단다**(누가 소비하는가·실패 시 무엇을 던지는가·멱등 여부).
- **외부 시스템 매퍼에는 정규화 근거를 남긴다**(왜 이 값이 저 값에 대응하는가, 상대가 안 주는 필드를 무엇으로 채웠는가). 이 정보는 벤더 문서에만 있고 코드에서 유추되지 않는다.
- 한국어로 작성한다. 비밀·토큰·키 원문은 주석/예시에도 넣지 않는다. 정본·Bad/Good 예시: `.agents/rules/code-comments.md`.

## 7. 상수·설정 외부화 (매직 리터럴 금지)

| 계층 | 무엇 | 위치/수단 |
|---|---|---|
| (a) 컴파일 타임 상수 | 코드 의미를 갖는 고정 라벨 | `enum`/`static final`(소유 **모듈** 안) |
| (b) 환경별 설정 | 배포 환경마다 달라지는 값 | `application.yml` + `@ConfigurationProperties`(**모듈 이름 prefix**) |
| (c) 운영자 변경 가능 값 | 배포 없이 조정 | 설정 서버·기능 플래그·DB 설정 테이블(캐시·무효화 동반) |

- 설정 프로퍼티는 **모듈 이름을 prefix로** 쓴다 — 소유가 드러나고 모듈을 떼어낼 때 그대로 옮겨진다.
- **자격증명·시크릿은 환경변수/시크릿 매니저에서만** 온다. `application.yml`에는 `${ENV_VAR}` 참조만 둔다.
- 에러코드·사용자 메시지는 문자열 리터럴 금지: 공유 모듈의 `ErrorCode` + i18n 키.

## 8. 성능·신뢰성 예산 (부하테스트로 확정)

- **무한/대량 결과 금지**: 목록은 페이지네이션 + 상한 강제.
- **N+1 회피**: fetch join·`@EntityGraph`·배치 조회. WHERE/JOIN/ORDER BY 컬럼에 인덱스 동반.
- **집계·카운터는 DB의 원자적 연산으로.** 조회 후 +1 해서 저장하는 read-modify-write는 동시 요청에서 갱신을 잃고, JVM 락(`synchronized`/`ReentrantLock`)은 인스턴스 하나에서만 유효하다.
- **외부 호출에는 timeout·재시도 상한·서킷브레이커.** connect/read 둘 다 건다. 무한 대기는 스레드 풀 고갈 → 전체 장애로 번진다.
- **재시도는 멱등 요청에만.** 결제·전송은 멱등키 없이 재시도하지 않는다.
- **폴백을 둔다면 총 지연을 예산에 넣는다**: `Σ(구현별 타임아웃)`이 곧 사용자 지연이다.
- **동기 응답 경로 보호**: 무거운 작업은 요청-응답 경로 밖으로.
- **빌드도 예산이다**: 모듈이 늘면 빌드가 느려진다. 병렬 빌드·빌드 캐시·구성 캐시를 켜고, 그래도 느리면 모듈 수를 다시 본다.

## 9. TDD 워크플로 (요약)

```
RED   유스케이스/어댑터 행위 1개에 대한 실패 테스트
GREEN 최소 구현으로 통과
REFACTOR 중복 제거·의도 드러내기
```

| 대상 | 도구 | 비고 |
|---|---|---|
| 도메인 규칙 | JUnit5/Kotest | 순수 로직. Spring 미기동 |
| 유스케이스 | JUnit5/Kotest + **손수 짠 fake 계약 구현** | 조립·정책·폴백 경로 검증. Mock은 꼭 필요할 때만 |
| 외부 연동 어댑터 | **HTTP 목 서버**(MockWebServer·WireMock 등 프로젝트 선택) | 타임아웃·5xx·429·깨진 응답을 주입해 예외 변환 검증 |
| 영속 | `@DataJpaTest` (+ Testcontainers 선택) | 쿼리·매핑·원자적 갱신 |
| 웹 | `@WebMvcTest` | envelope·상태코드·검증 실패 응답 |
| **구조** | **ArchUnit/Konsist**(§3.6) | 이 테스트가 모듈 경계다 |

- **실제 외부 시스템을 때리는 테스트를 `check` 기본 경로에 두지 않는다.** 남의 가용성에 우리 빌드를 묶고, CI에 실 자격증명이 있어야 하며, rate limit에 걸린다. 계약 확인이 필요하면 **태그로 분리해 수동/야간 실행**한다.
- 외부 응답 샘플은 픽스처로 저장하고 **스키마가 바뀌면 픽스처부터 갱신**한다.
- 검증 게이트: `./gradlew check` (CI·pre-commit·hook이 모두 `scripts/verify.sh`를 호출).

## 10. 새 모듈/기능 추가 워크플로

**새 모듈 추가:**
1. **정말 모듈이어야 하는지 답한다.** 끊고 싶은 의존이 무엇인가? 답이 없으면 기존 모듈의 패키지로 만든다.
2. **등급을 정한다**(§3.3) — 구성 등급이 기본이다. 공유 등급은 신중하게.
3. `settings.gradle`에 등록 → 모듈 빌드 스크립트 작성. **의존은 등급 규칙대로**(구성은 공유만).
4. 필요한 라이브러리를 `gradle/libs.versions.toml`에 추가하고 **카탈로그 별칭으로만** 참조한다.
5. 패키지를 `{{PACKAGE_NS}}.<module>`로 만들고, §3.3 등급표와 §3.6 구조 테스트에 이 모듈을 등록한다.
6. `./gradlew check` — 의존 방향과 누출이 잡히는지 확인.

**새 기능 추가:**
1. **모듈 결정**: 기존 모듈 안인지 새 모듈인지 먼저 답한다.
2. TDD 사이클: 도메인 → 유스케이스(fake 계약) → 어댑터/영속 → 웹 → 구조 검증.
3. **검증**: `./gradlew check` 통과 + OpenAPI/문서 동기화(`.agents/docs/openapi`).
4. **계획 추적**: 복잡 작업은 `.agents/docs/product-<slug>-specs/tasks/active/`에 기록.

## 11. Anti-pattern (코드리뷰 즉시 차단)

**모듈 경계**
- 구성 모듈이 실행 모듈에 의존(등급 역행).
- 기록되지 않은 구성 모듈 간 직접 의존(§3.4 표에 없는 간선).
- 공유 모듈에 Spring Web·JPA·벤더 SDK 의존 추가 — 모든 모듈이 그것을 끌고 간다.
- JPA 엔티티를 컨트롤러·다른 모듈·응답 시그니처에 노출.
- 외부 SDK 타입·벤더 DTO가 소유 모듈 밖에 등장.
- 다른 모듈의 변환 매퍼를 내가 갖고 있기.
- 실행 모듈에서 `@ComponentScan`으로 다른 모듈 내부 패키지 긁기.
- 라이브러리 모듈에 `bootJar` 활성 — 실행형 레이아웃으로 패키징되어 다른 모듈이 클래스를 못 찾는다.
- "일단 편하니까" 의존 한 줄 추가 — 이 아키텍처를 없애는 가장 흔한 방법이다.

**상태·라우팅**
- `static`/가변 맵을 `@PostConstruct`로 채우기 — 인스턴스 간 상태가 새고, 초기화 순서에 의존하며, 테스트가 서로를 오염시킨다. **생성자 주입 + 불변 맵**을 쓴다.
- 빈 이름 문자열 매칭·클래스명 규약으로 구현 찾기 — 이름을 바꾸면 **컴파일러가 아무 말 없이** 라우팅이 깨진다.
- 인스턴스 로컬 `synchronized`/`ReentrantLock`으로 카운터·랭킹 갱신 — 2대로 늘리면 갱신 손실.
- 조회 후 +1 해서 저장(read-modify-write) — 동시 요청에서 손실. 원자적 UPDATE 한 문장으로.

**예외·트랜잭션**
- `catch (Exception)`으로 전부 삼키고 폴백/기본값 반환 — 버그가 "외부 장애"로 위장된다.
- 폴백 실패 원인을 버리기 — 마지막 실패를 `cause`로 달아 올린다.
- 타임아웃 없는 외부 호출.
- **엔티티 메서드에 `@Transactional`/`@Modifying`** — 프록시 대상이 아니라 **아무 효과가 없다**.
- 영속 어댑터·리포지토리에 `@Transactional` 부착(경계 분산).
- 트랜잭션 안에서 외부 호출(커넥션 점유).

**의존성·응답·테스트**
- 루트에서 `allprojects { dependencies { … } }`로 모든 모듈에 라이브러리 뿌리기 — 모듈 분리가 무의미해진다.
- 버전·좌표를 모듈 빌드 스크립트에 직접 박기(카탈로그 우회).
- 컨트롤러에서 `ResponseEntity<DTO>` 직접 반환(envelope 우회).
- envelope의 `data`를 `Object`로 두기 — 제네릭으로 타입을 지킨다.
- 실제 외부 시스템을 때리는 테스트를 CI 기본 경로에 두기.
- 구조 테스트의 자리표시자(`<module>` 등)를 안 채워 아무것도 검사하지 않는 상태로 두기.
- 테스트 없이 모듈 코드 추가.

## 12. 다른 변형으로 전환하기

| 목표 | 디렉터리 이동 | 강제 규칙 교체 지점 |
|---|---|---|
| → `hexagonal` (도메인 규칙이 지배적이고 규격을 통일할 때) | 도메인 모듈을 `<ctx>/{domain,application,primary,infra}` 4모듈로 쪼갠다. **어댑터·영속 모듈은 그대로 `infra`가 된다**(계약이 이미 있어 전환 비용이 낮다). | 모듈 그래프 유지 + Konsist로 도메인 프레임워크 무의존 추가 |
| → `layered` (모듈이 사실상 하나일 때) | 모듈을 하나로 합치고 `{config,common,controller,service,repository,entity}`로 평탄화. | 모듈 그래프 → **ArchUnit `layeredArchitecture()`** |
| → `modulith` (빌드는 합치되 경계는 유지할 때) | 단일 모듈로 합친 뒤 각 모듈을 `<module>/{루트 타입, internal/…}` 패키지로. | 모듈 그래프 → **Spring Modulith `ApplicationModules.verify()`** |
| → 서비스 분리(이 킷 범위 밖) | 한 모듈을 새 리포로 옮긴다. 계약 호출은 HTTP/메시지로 교체. | 모듈 그래프 → **계약 테스트** |

- 전환은 **한 모듈씩** 옮기고 각 단계마다 `./gradlew check`를 통과시킨다.
- 전환 시작 전 `.agents/docs/decisions/`에 ADR을 남긴다(왜 옮기는지·되돌릴 조건).
- **공유 등급의 계약은 어느 전환에서도 살아남는다.** 여기에 한 투자는 버려지지 않는다.
