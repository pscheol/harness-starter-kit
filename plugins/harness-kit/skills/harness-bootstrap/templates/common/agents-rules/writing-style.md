# 문체 규칙 — 사람이 읽는 글

이 파일은 {{PROJECT_NAME}}이 만드는 **모든 글**(스펙 문서·주석·커밋 메시지·리포트·PR 설명)의 문체 원본이다.
주석의 *분량과 위치*는 `.agents/rules/code-comments.md`가, *문장 자체*는 이 파일이 정한다.

> 읽는 사람은 옆자리 동료다. 검사 결과를 낭독하는 기계가 아니라, 사람에게 설명하듯 쓴다.
> 문장을 하나 더 쓸지 고민되면 지운다. 짧은 글이 안 읽혀서 문제된 적은 없다.

## 1. 작업 일지를 쓰지 않는다

에이전트가 "내가 무엇을 했는지"는 문서에 남기지 않는다. 남기는 것은 **결과와 사실**이다.
과정은 대화로 보고하고, 파일에는 결론만 적는다.

```text
✗ requirements와 design을 대조한 결과, 두 문서의 필드명이 동일했다.
✓ 필드명은 requirements와 design이 같다.

✗ 테스트를 실행하였고 모두 성공적으로 통과되었음을 확인했습니다.
✓ 테스트 42개 전부 통과.

✗ 해당 부분을 검토해 본 결과 문제가 없다고 판단됩니다.
✓ 문제 없다. (근거를 댈 수 없으면 "확인 못 했다"고 쓴다)
```

금지: `~한 결과`, `~임을 확인했다`, `대조 결과`, `검토해 본 결과`, `~로 판단됩니다`, `살펴보면`.

## 2. 공허한 문장을 쓰지 않는다

정보가 0인 문장은 분량만 늘린다. 아래는 통째로 지워도 뜻이 안 바뀐다.

```text
✗ 이 인터페이스가 두 모듈 사이의 계약이 된다.     → '계약'이 아무것도 제약하지 않는다
✓ 이 인터페이스를 바꾸면 어댑터 3곳을 같이 고쳐야 한다.

✗ 안정적이고 효율적인 처리를 보장한다.
✓ 재시도 3회 후에도 실패하면 DLQ로 보낸다.

✗ 성공적으로 완료되었습니다 / 원활하게 동작합니다 / 적절히 처리합니다
✓ (숫자·조건으로 바꾸고, 쓸 말이 없으면 문장을 지운다)
```

정보 없는 수식어: `성공적으로` `원활하게` `적절히` `효과적으로` `안정적으로` `유연하게` `강력한` `최적화된`.
막연한 명사: `~에 대한 처리` `~의 관리` `~와 관련된 부분`.

## 3. 능동으로, 짧게

- 피동·명사화를 능동 동사로: `검증이 수행된다` → `검증한다`. `삭제 처리를 진행한다` → `삭제한다`.
- 한 문장에 주장 하나. 한 문단 3줄 이내.
- `~할 수 있도록 한다` → `~한다`. `~하는 것이 가능하다` → `~한다`.
- 제목에서 한 말을 첫 문장에서 되풀이하지 않는다.

## 4. 판단은 숫자와 조건으로

측정할 수 없는 형용사는 검증도 반박도 안 된다.

```text
✗ 응답이 빠르다 · 부하를 잘 견딘다 · 커버리지가 충분하다
✓ p95 120ms · 동시 1,000 요청에서 오류율 0.1% 미만 · 커버리지 82%
```

모르면 지어내지 않는다. `[NEEDS CLARIFICATION: 질문]`으로 남긴다(`.agents/rules/guardrails.md`).

## 5. 장식하지 않는다

- 문서 본문에 이모지를 넣지 않는다. 템플릿이 이미 쓰는 상태 기호(`✅` `⚠️` 등)만 그 자리에서 유지한다.
- 굵게(`**`)는 한 화면에 두세 번까지. 전부 굵으면 아무것도 강조되지 않는다.
- "다음과 같습니다:" 같은 예고 없이 바로 목록을 연다.
- 불릿이 여덟 개를 넘으면 묶거나 표로 바꾼다.

## 6. 문서 종류별

| 대상 | 쓰는 것 | 쓰지 않는 것 |
|---|---|---|
| requirements | 사용자가 얻는 결과, 측정 가능한 기준 | 클래스·프레임워크·구현 방식 |
| design | 선택한 방식과 **버린 대안의 이유** | 코드 전문 복붙, 자명한 설명 |
| tasks 의 `결과` | 검증 명령과 그 출력(통과/실패 수) | "성공적으로 완료했습니다" 류의 소감 |
| `/hx-analyze` 리포트 | 위치·발견·권고 세 가지 | 분석 과정 서술 |
| 커밋 메시지 | 무엇을 왜 바꿨는지 한 줄 | 파일 목록(git이 안다) |

## 7. 한국어 규약

- 기술 용어·식별자는 원문 그대로 둔다: `transaction` `idempotent` `OrderService`. 억지 번역하지 않는다.
- 영어 어순을 옮긴 번역투(`~에 의해 ~되어진다`)를 쓰지 않는다.
- 한 문서 안에서 종결어미를 섞지 않는다. 규칙·명세는 평서형(`~한다`)으로 통일한다.
- 비밀·토큰·키 원문은 어떤 문서·예시에도 넣지 않는다.

## 8. 리뷰 체크리스트

- 작업 과정을 서술한 문장이 있는가 → 결과만 남기고 삭제.
- 지워도 뜻이 안 바뀌는 문장이 있는가 → 삭제.
- 측정 불가한 형용사가 판단 근거로 쓰였는가 → 숫자·조건으로 교체.
- 한 문단이 3줄을 넘는가 → 쪼개거나 줄인다.
- 제목·앞 문단과 같은 말을 반복하는가 → 삭제.
