# 이슈 작업 락 — 두 작업자가 같은 티켓을 잡지 않게

설정 원본은 `.agents/issue-tracker.yml`의 `lock` 절이다. 작업 규약 전체는
[`issue-tracker-workflow.md`](./issue-tracker-workflow.md).

## 1. 무엇을 막는가

에이전트는 사람보다 빠르게 착수한다. 그래서 이런 일이 실제로 생긴다.

- 사람이 티켓을 잡고 로컬에서 작업 중인데 에이전트가 같은 티켓으로 브랜치를 판다.
- 에이전트 세션 둘이 같은 티켓을 동시에 진행해 서로의 커밋을 덮는다.

담당자(assignee) 필드만으로는 부족하다. 담당자는 **누가 책임지는가**이지
**지금 누가 손을 대고 있는가**가 아니다. 락은 후자를 표현한다.

## 2. 락의 형태

`.agents/issue-tracker.yml`의 `lock.mode`로 정한다. 셋 중 하나다.

| mode | 저장 위치 | 장점 | 단점 |
|---|---|---|---|
| `field` | 커스텀 필드 | 조회·필터가 쉽다 | 트래커 관리자 권한으로 필드를 만들어야 한다 |
| `label` | 라벨(접두사 + 소유자) | 설정이 필요 없다 | 라벨 목록이 지저분해진다 |
| `comment` | 특정 형식의 코멘트 | 어디서나 된다 | 파싱이 약하고 히스토리가 늘어난다 |

- 가능하면 `field`. 안 되면 `label`. `comment`는 최후다.
- 소유자 표기는 `lock.ownerFormat`을 따른다. **사람이 읽고 연락할 수 있는 형태**여야 한다
  (예: `agent:<session-id>@<host>`). 불투명한 해시만 남기면 락이 걸렸을 때 아무도 풀지 못한다.
- 획득 시각을 함께 기록한다. TTL 판정의 근거다.

## 3. 획득 · 갱신 · 해제

**획득** — 착수 직전, pull gate 통과 후.

1. 티켓을 다시 읽어 락 필드를 확인한다.
2. 락이 없으면 자기 소유자·시각을 쓴다.
3. **쓴 뒤 다시 읽어 자기 것인지 확인한다.** 트래커에는 원자적 CAS가 없어서
   동시에 두 세션이 쓰면 나중 것이 이긴다. 다시 읽어 확인하는 것이 유일한 방어다.
4. 자기 것이 아니면 착수하지 않는다.

**갱신** — 긴 작업 중 TTL이 지나기 전에 시각을 새로 쓴다. 갱신하지 않으면 남이 stale로 보고 가져간다.

**해제** — 다음 중 하나가 일어나면 **반드시** 푼다.

- 리뷰 요청으로 전이했다(작업이 손을 떠났다).
- 착수를 철회했다(To Do로 되돌린다).
- 세션이 끝난다.

**해제하지 않고 세션을 끝내지 않는다.** 남은 락은 다음 사람을 막는다.

## 4. stale 락

`lock.ttlMinutes`가 지난 락은 stale이다. 그래도 **자동으로 깨지 않는다.**

1. stale 락을 발견하면 **사용자에게 보고**한다 — 누가·언제 걸었는지, 얼마나 지났는지.
2. 사용자가 승인하면 깬다. 깰 때 **코멘트로 남긴다**(누가 왜 깼는지).
3. 승인 없이 깨지 않는다. 소유자가 아직 작업 중일 수 있다.

TTL은 "작업이 이 시간을 넘지 않는다"가 아니라 "이 시간이 지나면 확인이 필요하다"는 뜻이다.
권장값은 90~240분. 너무 짧으면 정상 작업이 stale로 보이고, 너무 길면 죽은 락이 오래 남는다.

## 5. 락이 있어도 되는 일

락은 **쓰기 작업**을 막는다. 아래는 락 없이 해도 된다.

- 티켓 읽기·요약
- 코드 읽기·분석·질문 답변
- 관련 코드 탐색

락이 있는 티켓을 사용자가 굳이 진행하라고 하면, **락 소유자가 누구인지 알린 뒤**
사용자의 명시 승인으로 진행한다. 그 사실을 코멘트로 남긴다.

## 6. 실패 처리

- 락 필드 쓰기가 실패하면 **착수하지 않는다.** 락 없이 진행하는 것이 가장 위험하다.
- 해제가 실패하면 사용자에게 알린다. 조용히 넘기면 다음 사람이 막힌다.
- 설정에 `TBD`가 남아 있으면 락 기능은 동작하지 않는다. 그때는 **에이전트가 쓰기 전이를 하지 않는다**
  (`issue-tracker-workflow.md` §4).

## 7. 안티-규칙

- ❌ 락을 확인하지 않고 착수하는 것.
- ❌ 쓴 뒤 다시 읽어 확인하지 않는 것(동시 획득을 못 잡는다).
- ❌ stale 락을 사용자 승인 없이 깨는 것.
- ❌ 락을 걸어 두고 세션을 끝내는 것.
- ❌ 담당자 필드를 락 대신 쓰는 것(다른 의미다).
- ❌ 락 소유자를 알아볼 수 없는 값으로 적는 것.
- ❌ 락 실패를 무시하고 "일단 진행"하는 것.
