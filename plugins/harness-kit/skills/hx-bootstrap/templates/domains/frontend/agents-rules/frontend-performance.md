# 프론트엔드 성능 — 예산을 먼저 정하고, 측정한 것만 고친다

성능은 "빠르게 만들자"가 아니라 **숫자를 넘겼는가**의 문제다. 예산이 없으면 최적화는 근거 없는
취향이 되고, 측정이 없으면 고친 자리가 느린 자리인지 알 수 없다.

## 1. 예산

## 2. 측정 없이 고치지 않는다

1. **재현** — 느린 화면·조작을 지목한다. "전반적으로 느리다"는 착수 지점이 아니다.
2. **측정** — 프로파일러·트레이스로 실제 비용 지점을 찾는다.
3. **수정** — 한 번에 하나.
4. **재측정** — 숫자가 움직였는지 본다. 안 움직였으면 되돌린다.

전/후 숫자가 없는 성능 변경은 리뷰에서 근거가 없다(`verification-ladder.md` L2 이상).

## 3. 로딩 전략

- 초기 번들에는 **첫 화면에 필요한 것만** 넣는다. 무거운 라이브러리(차트·에디터·PDF·지도)는 동적 import.
- 라우트 단위 코드 스플리팅이 기본이다. 스플리팅 지점이 사라지지 않도록 라우팅은 한 곳에서 선언한다.
- 폰트는 필요한 굵기만 서브셋으로. 표시 지연은 `font-display: swap`.
- 이미지는 **폭·높이를 명시한다.** 레이아웃 이동의 최대 원인이다. 히어로만 우선 로드, 나머지는 지연.
- 서드파티 스크립트는 기본이 지연 로드다. 무엇을 왜 넣었는지 목록을 유지한다(들어올 때보다 뺄 때가 어렵다).

## 4. 렌더·애니메이션

- 애니메이션은 컴포지터 친화 속성만: `transform` · `opacity` · `clip-path`.
  `width`·`top`·`margin`·`font-size` 를 애니메이션하면 매 프레임 레이아웃이 다시 계산된다.
- `will-change` 는 좁게 쓰고 끝나면 제거한다. 켜 둔 채로 두면 메모리만 먹는다.
- 스크롤·리사이즈 핸들러에 계산을 넣지 않는다. IntersectionObserver·ResizeObserver 를 쓴다.
- 긴 목록은 가상화한다. 단, 목록이 실제로 길어진 뒤에 넣는다.
- 모션은 `prefers-reduced-motion` 을 존중한다(`accessibility.md`).

## 5. 데스크톱(Electron) 고유

- **main 프로세스를 막지 않는다.** 동기 파일 I/O·큰 JSON 파싱·암호 연산을 main 에서 돌리면
  모든 창이 함께 멈춘다. 무거운 작업은 워커나 자식 프로세스로 보낸다.
- IPC 는 왕복 비용이 있다. 루프 안에서 채널을 호출하지 말고 배치로 주고받는다.
- 큰 데이터를 IPC 로 통째 넘기지 않는다(구조화 복제 비용). 페이지네이션하거나 경로를 넘긴다.
- 창을 늘리면 렌더러 프로세스가 늘어난다. 메모리 예산은 **창 수 기준**으로 잡는다.
- 앱 시작 경로에서 하는 일을 목록으로 관리한다. 콜드 스타트는 거기서만 나빠진다.

## 6. 자동화로 잡히는 영역

여기 적힌 것은 도구가 잡는다. **리뷰에서 다시 지적하지 않는다**(`pr-review-policy.md`).

- [ ] 번들 크기 회귀 — 번들 분석 + CI 예산 검사
- [ ] 이미지 크기 미지정 — 린터 규칙
- [ ] 무거운 라이브러리의 정적 import — 번들 분석 리포트

## 7. 안티-규칙

- ❌ 측정 없이 메모이제이션을 뿌리는 것. 비용은 확실하고 이득은 불확실하다.
- ❌ 마이크로 최적화(루프 방식·연산자 선택)로 시작하는 것. 병목은 거의 항상 네트워크·렌더 트리·번들이다.
- ❌ 예산 초과를 "나중에 최적화"로 미루는 것. 초과는 그 PR 의 문제다.
- ❌ 성능을 이유로 접근성·정확성을 깎는 것(`accessibility.md`).
