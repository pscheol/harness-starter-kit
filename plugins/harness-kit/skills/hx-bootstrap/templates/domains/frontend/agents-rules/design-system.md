# 디자인 시스템 — 값은 만들지 않고 가져온다

UI 를 만들 때 **색·간격·타이포·반경·모션 값을 새로 지어내지 않는다.** 기존 토큰에서 고르고,
없으면 디자인 소스를 확인하고, 거기에도 없으면 구현을 멈추고 묻는다.

## 1. 왜

에이전트는 "적당히 어울리는 값"을 아주 잘 만들어낸다. `12px`, `#3B7DDD`, `0.2s ease` 같은 값이
화면마다 조금씩 다르게 쌓이면 디자인 시스템은 조용히 사라진다. 사라진 뒤에는 되돌릴 방법이
전면 리팩터링밖에 없다.

값 하나를 지어내는 비용은 0 이고, 그 값이 만든 불일치를 걷어내는 비용은 화면 수에 비례한다.

## 2. 기준 문서

> 설치 후 채운다. **어느 것이 최신 기준인지** 명시한다. 비워 두면 이 규칙은 동작하지 않는다.

| 종류 | 위치 | 우선순위 | 비고 |
|---|---|---|---|
| 최근 변경 반영 | | 0 (최우선) | 바뀐 것부터 여기서 확인 |
| 디자인 가이드 | | 1 | |
| 레이아웃 기준 | | 2 | |
| 사용자 매뉴얼·카피 | | 3 | |

기준이 충돌하면 **숫자가 작은 쪽**을 따른다. 그래도 모호하면 구현하지 말고 확인한다
(`guardrails.md` 추측 금지).

## 3. 토큰 owner

> 설치 후 채운다. 토큰은 여기 적힌 곳에만 추가한다.

| 종류 | 정의 위치 |
|---|---|
| 색 | |
| 간격 | |
| 타이포 | |
| 반경·그림자 | |
| 모션(지속·이징) | |
| z-index 층 | |

- 화면 하나의 특수 값을 공통 토큰으로 올리지 않는다. 특수 값은 그 화면에 국소로 둔다.
- 토큰을 추가하면 **이름이 역할을 말해야 한다.** `blue-500` 이 아니라 `color-danger` 쪽이다.
- 하드코딩이 불가피하면 그 자리에 **왜 토큰이 아닌지**를 주석으로 남긴다(`code-comments.md`).

## 4. 컴포넌트

- 새 컴포넌트 전에 `reuse-before-new.md` 의 Inventory 를 수행한다. 같은 역할이 다른 이름으로
  이미 있으면 **기존 것을 개선**한다. 프론트엔드에서 가장 흔한 낭비가 버튼 다섯 개다.
- 상태를 빠뜨리지 않는다: `default` · `hover` · `focus-visible` · `active` · `disabled` ·
  `loading` · `empty` · `error`. 이 중 무엇을 안 만들었는지 스스로 말할 수 있어야 한다.
- 컴포넌트는 **자기 바깥 여백을 갖지 않는다.** 바깥 여백은 배치하는 쪽이 정한다
  (그러지 않으면 같은 컴포넌트가 화면마다 다른 간격을 강요한다).
- 공개 API 는 좁게. 스타일을 통째로 뚫는 prop(임의 클래스·인라인 스타일 주입)을 기본으로 열지 않는다.

## 5. 레이아웃·밀도

- 간격은 스케일에서만 고른다. 스케일 밖 값이 필요하면 그건 디자인 결정이므로 확인 대상이다.
- 브레이크포인트는 토큰이다. 컴포넌트마다 다른 숫자를 쓰지 않는다.
- 데스크톱(Electron)과 웹이 같은 컴포넌트를 공유한다면 **밀도만 다르고 토큰은 같다.**
  밀도 차이는 별도 토큰 축(`density-compact` 등)으로 표현한다.

## 6. 자동화로 잡히는 영역

여기 적힌 것은 도구가 잡는다. **리뷰에서 다시 지적하지 않는다**(`pr-review-policy.md`).

- [ ] 토큰 밖 하드코딩 값(색·간격) — 린터 규칙으로 승격 가능
- [ ] 미사용 토큰·미사용 컴포넌트 — dead code 도구
- [ ] 대비 비율 — 접근성 검사 도구(`accessibility.md`)

## 7. 안티-규칙

- ❌ 디자인 소스 확인 없이 "더 예쁜" 값을 제안하는 것.
- ❌ 픽셀 단위 미세 정합을 코드 리뷰에서 지적하는 것 — 사람 확인(L4) 영역이다
      (`verification-ladder.md`).
- ❌ 이 규칙을 근거로 기존 화면 전체의 디자인 통일을 시작하는 것. 별도 작업으로 등록한다.
- ❌ 토큰이 없다는 이유로 요구를 축소하는 것. 없으면 묻는다.
