# 설계 원칙 — 객체지향 · 클린 아키텍처 · SOLID

이 문서는 **어떤 구조를 고를지가 아니라 그 구조 안에서 코드를 어떻게 짤지**의 원본이다.
레이아웃·모듈 경계는 `ARCHITECTURE.md`와 `.agents/rules/structure.md`가 정하고, 이 문서는 그 안에서 반복되는 판단을 정한다.

원칙을 외우는 것이 목적이 아니다. **위반 신호를 알아보고 무엇으로 바꿀지 아는 것**이 목적이라, 각 항목은
`원칙 → 실제로 나타나는 위반 신호 → 어떻게 고치나` 순서로 쓴다.

> 원칙은 목적이 아니라 수단이다. 원칙을 지키느라 코드가 더 어려워지면 그건 잘못 적용한 것이다.
> 판단이 갈리면 **바꾸기 쉬운 쪽**을 고른다.

---

## 1. 클린 아키텍처 — 의존 규칙 하나

클린 아키텍처의 실체는 규칙 하나다. **소스 코드 의존은 항상 안쪽(정책)을 향한다.**

```
   바깥 ─────────────────────────────────────▶ 안쪽
   프레임워크 · DB · HTTP · 외부 SDK      비즈니스 규칙 · 도메인 모델
   (자주 바뀐다 · 교체된다)               (제품의 이유. 늦게 바뀐다)
```

- **안쪽은 바깥을 모른다.** 도메인 코드에 HTTP 상태코드·ORM 어노테이션·벤더 SDK 타입이 등장하면 방향이 뒤집힌 것이다.
- 안쪽이 바깥의 기능을 필요로 하면 **안쪽이 인터페이스를 소유**하고 바깥이 구현한다. 이것이 §2.5 DIP이고, 헥사고날의 포트가 정확히 이것이다.
- 경계를 넘을 때 **모델을 바꾼다**. 요청 DTO → 도메인 모델 → 영속 모델. 하나의 클래스가 세 역할을 겸하면 바깥의 변경이 안쪽까지 전파된다.
- 이 규칙을 **문서가 아니라 도구로** 강제한다. 스택마다 수단이 다르다(모듈 그래프·import-linter·depguard·ArchUnit/Konsist). 강제 수단은 `ARCHITECTURE.md`에 있다.

### 위반 신호

| 신호 | 무엇이 잘못됐나 |
|---|---|
| 도메인 클래스가 프레임워크 어노테이션·타입을 참조 | 안쪽이 바깥을 안다 |
| 안쪽 코드가 결과를 HTTP 상태코드로 판단 | 표현 관심사가 정책에 스몄다 |
| 한 클래스가 요청·도메인·테이블을 동시에 표현 | 경계에서 모델을 안 바꿨다 |
| 인터페이스를 **구현하는 쪽 패키지**에 뒀다 | 추상의 소유자가 바깥이다(DIP 미적용) |
| 테스트가 DB·HTTP 없이는 아무것도 못 돌린다 | 정책이 인프라에 묶였다 |

### 고치는 법

1. 안쪽에서 바깥 타입을 참조하는 지점을 찾는다(강제 도구가 이미 알려 준다).
2. 그 지점에 필요한 **동작만** 담은 인터페이스를 안쪽에 만든다. 이름은 도메인 언어로(`OrderRepository`·`PaymentGateway` — `JpaOrderDao` ✗).
3. 바깥에 구현을 두고 조립 지점(실행 단위)에서 주입한다.
4. 테스트에서 그 인터페이스의 fake를 쓴다. **fake로 테스트가 돌아가면 경계가 제대로 그어진 것이다.**

## 2. SOLID

### 2.1 SRP — 바뀌는 이유가 하나

"함수가 짧아야 한다"가 아니라 **"이 코드를 바꾸라고 요구하는 사람이 한 부류인가"**다.
결제 정책과 정산 리포트 양식이 한 클래스에 있으면, 서로 무관한 두 요구가 같은 파일을 흔든다.

**위반 신호**
- 클래스명에 `Manager`·`Util`·`Helper`·`Facade`·`Common`이 들어간다(무엇을 하는지 이름이 못 말한다).
- 메서드 목록이 서로 관련 없는 무리로 나뉜다(앞의 5개는 조회, 뒤의 5개는 알림 발송).
- 변경 이력에서 **같은 파일이 서로 다른 이유로 반복 수정**된다.
- 테스트 준비(fixture)가 검증하려는 것과 무관한 의존을 잔뜩 만든다.

**고치는 법** — 메서드를 "누가 이 변경을 요구하는가"로 묶고, 묶음마다 클래스를 나눈다.
나눈 뒤 호출부가 두 객체를 연달아 부르게 되면 그 조립이 유스케이스의 책임이다.

> 반대 방향도 위반이다. 클래스가 너무 잘게 쪼개져 **한 요구를 처리하려고 7개 파일을 열어야** 하면 응집이 깨진 것이다.

### 2.2 OCP — 확장에는 열리고 수정에는 닫힌다

새 종류(결제 수단·알림 채널·외부 벤더)를 추가할 때 **기존 코드를 고치지 않고 새 파일만 더하면** 되는 상태.

**위반 신호**
- 새 종류를 추가할 때마다 `when`/`switch`/`if-else` 사슬을 찾아 다니며 분기를 더한다.
- 그 분기가 **여러 파일에 흩어져** 있어 하나를 빠뜨리면 조용히 잘못 동작한다.
- 열거 타입에 값을 추가했더니 컴파일은 되는데 런타임에 기본 분기로 빠진다.

**고치는 법**
1. 분기의 각 갈래가 하는 일을 인터페이스 하나로 표현한다.
2. 갈래마다 구현을 만든다. **구현이 자기 식별자를 스스로 선언**한다(`provider()` 같은 메서드).
3. 조립 지점에서 구현 목록을 받아 **불변 맵**으로 확정한다. 클래스명 규약·빈 이름 문자열 매칭으로 찾지 않는다 — 이름을 바꾸면 컴파일러가 아무 말 없이 라우팅이 깨진다.
4. 등록되지 않은 종류는 **명시적으로 실패**시킨다(조용한 기본 분기 금지).

> 모든 분기를 다형성으로 바꾸라는 뜻이 아니다. **갈래가 앞으로 늘어날 것 같을 때만** 값을 한다.
> 두 갈래로 끝날 것이 확실하면 조건문이 더 읽기 쉽다(YAGNI).

### 2.3 LSP — 하위 타입은 상위 타입 자리에 그대로 들어간다

상위 타입을 기대하는 코드에 하위 타입을 넣었을 때 **놀랄 일이 없어야** 한다.

**위반 신호**
- 하위 구현이 일부 메서드에서 "지원하지 않음" 예외를 던진다.
- 하위 구현이 상위보다 **더 강한 입력 조건**을 요구하거나 **더 약한 결과**를 보장한다.
- 호출부에 "이 구현이면 이렇게" 같은 타입 검사 분기가 등장한다.
- 상속 계층이 "재사용하려고" 만들어졌다(공통 필드를 모으려고 부모 클래스를 만듦).

**고치는 법**
- 계약(사전조건·사후조건·예외)을 인터페이스 문서에 적고, **모든 구현에 같은 테스트 묶음**을 돌린다. 통과 못 하는 구현은 그 인터페이스의 하위 타입이 아니다.
- 상속이 "코드 재사용" 목적이면 **합성으로 바꾼다**. 상속은 "정말로 대체 가능한가"에 답할 수 있을 때만 쓴다.
- 계층이 셋 이상 깊어지면 멈추고 다시 본다. 깊은 상속 계층은 거의 항상 합성이 나은 신호다.

### 2.4 ISP — 쓰지 않는 것에 의존하지 않는다

인터페이스는 **호출자 관점**에서 좁게 만든다. 구현체 하나를 그대로 베낀 인터페이스는 인터페이스가 아니다.

**위반 신호**
- 인터페이스 메서드가 10개가 넘고, 어느 호출자도 절반 이상을 쓰지 않는다.
- fake를 만들 때 안 쓰는 메서드까지 전부 채워야 한다.
- 인터페이스에 메서드를 추가했더니 관련 없는 구현·테스트가 줄줄이 깨진다.
- 저장소 인터페이스에 `updateColumnA`·`upsertByKeys` 같은 **저장 메커니즘**이 드러난다.

**고치는 법**
- 인터페이스를 **호출자별로** 쪼갠다(읽기 전용 조회와 쓰기를 나눈다).
- 저장소 인터페이스는 **애그리거트 단위**로 정의한다(`save(order)`·`findById`). 멱등·충돌 처리는 구현 안에서 끝낸다.
- **인터페이스와 구현 한 쌍을 관성으로 만들지 않는다.** 구현이 하나뿐이고 테스트 대역도 필요 없다면 클래스만 둔다. 인터페이스는 (a) 레이어 경계를 넘거나 (b) 구현이 실제로 여럿이거나 (c) 테스트에서 대체해야 할 때 값을 한다.

### 2.5 DIP — 추상은 안쪽이 소유한다

"인터페이스를 쓴다"가 아니라 **"인터페이스를 누가 소유하는가"**다.
저수준 모듈이 정의한 인터페이스를 고수준이 가져다 쓰면 방향은 그대로다 — 이름만 추상일 뿐이다.

**위반 신호**
- 저장소 인터페이스가 영속 패키지에 있고 서비스가 그것을 import한다.
- 인터페이스 시그니처에 저수준 타입이 등장한다(ORM 전용 조건 객체·SDK 응답 타입).
- 인터페이스 이름이 기술을 드러낸다(`JpaOrderDao`·`RedisCacheClient`).

**고치는 법**
1. 인터페이스를 **쓰는 쪽(안쪽) 패키지로 옮긴다**. 이름을 도메인 언어로 바꾼다.
2. 시그니처에서 저수준 타입을 걷어내고 도메인 타입으로 바꾼다.
3. 구현은 바깥에 두고 조립 지점에서 주입한다.
4. 생성자 주입만 쓴다. 필드 주입·서비스 로케이터·전역 싱글턴은 의존을 숨겨서 **도구가 순환을 못 잡게** 만든다.

## 3. 객체지향 — 데이터와 규칙을 같이 둔다

### 3.1 캡슐화와 불변식

- 객체는 **잘못된 상태로 존재할 수 없어야** 한다. 생성 시점에 불변식을 검증하고, 통과 못 하면 인스턴스를 만들지 않는다.
- 상태를 바꾸는 통로는 **의미 있는 동작**이다(`order.cancel(reason)`). 무분별한 setter는 불변식을 검증할 자리를 없앤다.
- 컬렉션 필드는 **읽기 전용 뷰로** 노출한다. 내부 리스트를 그대로 반환하면 외부가 규칙을 우회해 수정한다.
- 값 객체(금액·기간·식별자)를 만든다. 원시 타입을 그대로 넘기면 인자 순서를 바꿔도 컴파일이 통과한다.

### 3.2 Tell, Don't Ask

객체에게 **물어서 내가 판단**하지 말고, **시켜라**.

```
// 물어보고 내가 판단 — 규칙이 호출부로 샌다
if (order.status == PAID && order.shippedAt == null) {
    order.status = CANCELLED
}

// 시킨다 — 규칙이 객체 안에 남는다
order.cancel(reason)
```

- 호출부에 접근자 여러 개와 조건문이 함께 나타나면 그 판단은 대개 객체의 것이다.
- 이 신호가 반복되면 **Anemic Domain Model**이다: 데이터만 든 객체 + 규칙을 전부 가진 서비스. 객체지향이 아니라 절차형에 클래스 옷을 입힌 것이다.
- 다만 **조회·표현 목적의 데이터 전달 객체(DTO)는 빈약해도 된다.** 규칙을 담지 않는 것이 그 객체의 역할이다.

### 3.3 상속보다 합성

- 상속은 부모의 **모든 변경**을 자식이 물려받는다. 결합이 가장 강한 재사용 수단이다.
- "공통 필드가 있어서" 부모를 만들지 않는다. 공통 **동작**이 있고 하위 타입이 정말 대체 가능할 때만 쓴다(§2.3).
- 기본은 합성 + 위임이다. 프레임워크가 요구하는 상속(테스트 기반 클래스 등)은 예외.

### 3.4 불변을 기본으로

- 필드는 기본이 불변이다. 상태 변경이 필요하면 **새 인스턴스를 반환**하는 편이 추적이 쉽다.
- 가변 상태를 여러 스레드가 공유하면 락으로 막으려 하기 전에 **공유를 없앨 수 있는지** 본다.
- 카운터·집계처럼 진짜 공유가 필요한 값은 프로세스 안 락이 아니라 **저장소의 원자적 연산**으로 처리한다(인스턴스가 둘이면 프로세스 락은 무력하다).

## 4. 적용 순서 (막혔을 때)

1. **경계부터** — 이 코드는 안쪽인가 바깥인가. 안쪽이면 프레임워크 타입이 들어와선 안 된다(§1).
2. **규칙의 자리** — 이 판단은 객체가 스스로 할 수 있는가(§3.2). 없으면 어느 레이어의 책임인가.
3. **추상의 소유자** — 인터페이스를 만든다면 누가 소유하는가(§2.5). 소유자가 헷갈리면 아직 필요 없는 인터페이스다.
4. **확장 지점** — 앞으로 종류가 늘어날 곳인가(§2.2). 아니면 분기로 둔다.
5. **테스트로 확인** — 인프라 없이 이 규칙을 테스트할 수 있는가. 못 하면 1번으로 돌아간다.

## 5. 과잉 설계 방지 (원칙보다 우선하는 것)

- **아직 없는 요구를 위한 추상을 만들지 않는다.** 구현이 하나뿐인 인터페이스, 확장 지점이 없는 전략 패턴, 쓰이지 않는 이벤트 발행은 원칙 준수가 아니라 부채다.
- 패턴 이름으로 설계를 정당화하지 않는다. **"이걸 넣으면 무엇이 쉬워지는가"**에 한 문장으로 답하지 못하면 넣지 않는다.
- 추상 계층을 더할 때마다 읽는 사람이 따라가야 할 파일이 하나 늘어난다. 그 비용을 지불할 이유를 코드가 아니라 **요구**에서 찾는다.
- 규칙이 틀렸다고 판단되면 조용히 어기지 말고 **ADR**(`.agents/docs/decisions/`)에 남기고 바꾼다.
