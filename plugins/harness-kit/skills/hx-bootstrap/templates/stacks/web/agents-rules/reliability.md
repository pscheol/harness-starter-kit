# 신뢰성 · 안정성 기준 — {{PROJECT_NAME}}

프론트엔드의 장애는 대부분 **네트워크가 느리거나 실패했을 때** 드러난다.
정상 경로만 만든 화면은 완성된 화면이 아니다.

## 전제 — 실패는 정상 상태다

- 요청은 실패한다. 느리다. 순서가 바뀐다. 사용자는 중간에 이탈한다.
- 개발 환경의 빠른 로컬 네트워크에서는 이 중 아무것도 재현되지 않는다. **느린 네트워크와 실패를
  일부러 재현해 보고** 화면을 만든다(개발자 도구의 스로틀링·오프라인 모드).

## 실패 격리 (에러 경계)

- 앱 전체에 에러 경계 하나만 두면 위젯 하나의 실패가 전체 화면을 날린다. **의미 있는 단위마다** 둔다.
- 에러 경계는 다음 행동을 제공한다: 이 영역만 재시도 · 새로고침 · 이전 화면.
- 에러 경계가 잡은 오류는 모니터링으로 보낸다. 화면만 바꾸고 삼키면 아무도 모른다.
- 비동기 오류는 렌더 오류와 경로가 다르다. 쿼리 계층의 에러 상태도 함께 다룬다.
- 라우트 전환 실패(청크 로드 실패)를 처리한다. 배포 직후 구버전 청크가 사라져 자주 발생한다 —
  이때는 재시도가 아니라 **새로고침**이 답이다.

## 타임아웃 · 재시도 · 취소

- 모든 요청에 타임아웃. 재시도는 멱등한 요청만, 지수 백오프 + 지터.
- 4xx는 재시도하지 않는다. 429는 안내 후 지정 시점에.
- 화면 이탈·입력 변경 시 이전 요청을 취소한다. 취소 실패(`AbortError`)는 에러 화면이 아니다.
- 상세는 [`api-standards.md`](./api-standards.md).

## 레이스 컨디션

프론트엔드에서 가장 자주 나고 가장 늦게 발견되는 결함이다.

- **늦게 온 이전 응답**이 최신 응답을 덮어쓴다 → 취소 또는 요청 식별자 비교로 최신 것만 반영한다.
- **연속 변경 요청**의 도착 순서는 보장되지 않는다 → 순서가 중요하면 직렬화하거나 서버 응답으로 확정한다.
- **낙관적 업데이트 + 실패 롤백** 중에 다른 변경이 끼면 롤백이 최신 값을 되돌린다 → 롤백 대상은
  스냅샷 시점 기준으로 좁힌다([`ui-state.md`](./ui-state.md)).
- 마운트 직후 언마운트되는 컴포넌트에서 상태를 갱신하지 않는다(정리 함수 필수).

## 오프라인 · 불안정한 연결

- 오프라인 감지와 복귀 시 재조회 정책을 정한다. 무한 재시도 루프를 만들지 않는다.
- 사용자가 입력 중이던 내용은 실패해도 사라지지 않게 한다. 폼 초안 보존이 없으면 실패가 곧 데이터 손실이다.
- 재시도 중임을 화면에 표시한다. 아무 반응 없는 대기가 가장 나쁘다.

## 세션 · 인증 만료

- 401을 받으면 **현재 위치를 기억한 채** 재인증 흐름으로 보내고, 완료 후 돌아온다.
- 토큰 갱신이 여러 요청에서 동시에 트리거되지 않게 한 번만 수행하고 나머지는 그 결과를 기다린다.
- 갱신 실패는 로그아웃으로 수렴한다. 무한 갱신 루프를 만들지 않는다.
- 다른 탭에서 로그아웃했을 때의 동작을 정한다(탭 간 동기화).

## 폼 · 중복 제출

- 제출 중에는 제출 버튼을 비활성화한다. 이것이 없으면 더블클릭이 곧 중복 생성이다.
- 그래도 중복은 발생한다 — 서버 멱등성이 최종 방어선이다. 프론트 처리로 대체하지 않는다.
- 제출 실패 시 입력값을 유지하고 어느 필드가 왜 틀렸는지 표시한다.
- 페이지 이탈 시 저장되지 않은 변경을 경고한다(단, 남용하면 사용자가 무시하게 된다).

## 관측성

- 처리되지 않은 오류·거부된 프로미스를 모니터링으로 보낸다.
- 에러 리포트에 **상관용 식별자**(백엔드의 `request_id`)와 화면 경로를 함께 담는다.
- 개인정보·토큰·요청 본문 전체를 리포트에 담지 않는다([`security.md`](./security.md)).
- 사용자 체감 지표(LCP·INP·CLS)를 실사용 환경에서 수집한다. 로컬 측정만으로는 회귀를 못 잡는다
  ([`frontend-performance.md`](./frontend-performance.md)).
- 소스맵을 모니터링 도구에 업로드하되 공개 배포에는 올리지 않는다.

## 배포 · 버전 불일치

- 배포 후에도 사용자는 **이전 버전 앱**을 열어 두고 있다. 클라이언트와 API 버전 불일치를 전제로 설계한다.
- API는 하위 호환을 지키고, 깨는 변경은 버전을 나눈다.
- 새 버전 배포를 감지하면 사용자에게 새로고침을 권한다(강제하지 않는다 — 작업 중일 수 있다).
- 기능 플래그로 배포와 노출을 분리한다. 플래그 제거는 별도 작업으로 등록한다.
