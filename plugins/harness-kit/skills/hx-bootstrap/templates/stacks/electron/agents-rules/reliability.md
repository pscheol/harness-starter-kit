# 신뢰성 · 안정성 기준 — {{PROJECT_NAME}}

데스크톱 앱은 **웹 페이지와 달리 새로고침이 없다.** 사용자는 앱을 몇 주씩 켜 두고,
네트워크는 통제되지 않으며, 데이터는 사용자 컴퓨터에 남는다. 그 전제 위에서 만든다.

## 1. main 프로세스는 앱 전체의 단일 장애점이다

- **main이 멈추면 모든 창이 멈춘다.** 동기 파일 I/O·큰 JSON 파싱·암호 연산·압축을 main에서 돌리지 않는다.
  워커 스레드나 자식 프로세스로 보낸다.
- **main에서 처리되지 않은 예외는 앱을 죽인다.** 최상위 예외·거부된 프로미스 핸들러를 두고,
  로깅한 뒤 사용자에게 복구 경로를 준다.
- 렌더러 프로세스가 죽는 것은 회복 가능하다. `render-process-gone`을 감지해 창을 다시 만들거나
  사용자에게 알린다. 조용히 흰 화면을 남기지 않는다.
- 크래시 리포터를 붙이되 개인정보·비밀이 담기지 않게 필드를 고른다([`security.md`](./security.md)).

## 2. 생명주기 · 창

- 창을 닫는 동작의 의미가 OS마다 다르다(macOS는 앱이 살아 있는 것이 관례). **플랫폼 분기를 한 곳에 모은다.**
- 창을 여러 개 열 수 있다면 **모든 기능이 두 번째 창에서도 동작해야 한다.** 전역 싱글턴 가정이 깨지는 지점이다.
- 창별 상태(스크롤·선택)와 앱 전역 상태(설정·세션)를 구분한다. 전역을 창 안에 두면 창을 닫을 때 사라진다.
- 창 위치·크기 복원은 화면 구성이 바뀐 경우를 처리한다(모니터가 사라져 창이 화면 밖으로 나가는 문제).
- 종료 시 정리 순서를 정한다: 진행 중 작업 취소 → 저장 → 워처·워커 종료 → 창 파괴.
  **저장되지 않은 변경이 있으면 종료를 막고 사용자에게 묻는다.**

## 3. IPC 안정성

- `webContents`가 파괴된 뒤 `send`하면 예외가 난다. 전송 전에 살아 있는지 확인한다.
- 창이 닫히면 그 창을 위한 작업을 **취소**한다. 결과를 받을 곳이 없는 작업을 계속 돌리지 않는다.
- 오래 걸리는 작업에는 작업 ID·진행률·취소 채널을 둔다([`api-standards.md`](./api-standards.md)).
- 진행률 통지에 빈도 상한을 둔다. 프레임마다 보내면 IPC 자체가 병목이 된다.
- `handle` 중복 등록을 막는다(핫 리로드에서 자주 발생). 등록은 한 곳에서 한 번만.
- 렌더러 구독은 언마운트에서 해제한다. 창 수명 동안 누적되면 같은 이벤트가 N번 처리된다.

## 4. 네트워크 — 통제되지 않은 환경을 가정한다

- 모든 외부 호출에 타임아웃. 재시도는 멱등한 요청만, 지수 백오프 + 지터. 4xx는 재시도하지 않는다.
- **오프라인이 기본 상태 중 하나다.** 오프라인 감지, 복귀 시 재조회, 무한 재시도 방지.
- 사내망 프록시·사설 인증서·SSL 가로채기 환경을 만난다. 실패를 **사용자가 이해할 수 있는 말**로 보여 준다
  ("네트워크 오류"가 아니라 "회사 네트워크의 프록시 설정 때문일 수 있습니다").
- 인증 만료 시 재인증 흐름을 앱 안에서 처리하고, 작업 중이던 내용을 잃지 않게 한다.
- 상세는 [`api-standards.md`](./api-standards.md).

## 5. 로컬 데이터 — 사용자 컴퓨터에 남는다

- **쓰기는 원자적으로**: 임시 파일에 쓰고 이름을 바꾼다. 중간에 앱이 죽어도 파일이 깨지지 않는다.
- 저장 파일에 **스키마 버전**을 함께 넣고 마이그레이션 경로를 만든다. 구버전 파일로 앱이 시작되지
  않는 상황을 막고, **다운그레이드**(사용자가 이전 버전을 다시 설치)도 고려한다.
- 파일이 손상됐을 때의 동작을 정한다: 백업본 복구 → 실패하면 초기화 + 사용자 통지.
  **조용히 초기화하지 않는다.** 사용자 데이터가 사라진 것을 알려야 한다.
- 동시 실행 인스턴스를 막거나(단일 인스턴스 락) 파일 접근을 조율한다. 두 인스턴스가 같은 파일을
  쓰면 데이터가 섞인다.
- 삭제·덮어쓰기 동작에는 되돌릴 수 없다는 표시와 확인 단계를 둔다.

## 6. 상태 · 레이스

- 늦게 온 이전 응답이 최신 결과를 덮어쓴다 → 요청 식별자 비교 또는 취소로 정리한다.
- 낙관적 업데이트는 스냅샷 → 반영 → 실패 시 복구 → 보이는 통지 순서를 지킨다([`ui-state.md`](./ui-state.md)).
- 파일 워처는 이벤트가 몰려 온다(에디터 저장 한 번에 여러 번). 디바운스하고 멱등하게 처리한다.
- 외부에서 파일이 바뀌었을 때의 정책을 정한다(자동 반영·충돌 표시·무시).

## 7. 업데이트 · 버전

- 자동 업데이트는 **서명 검증되는 채널**로만. 실패 시 앱이 못 쓰게 되지 않아야 한다.
- 업데이트 적용 시점을 사용자가 통제하게 한다(작업 중 강제 재시작 금지).
- **구버전 앱이 계속 돌고 있다는 전제**로 서버 API 호환을 유지한다. 사용자는 업데이트를 미룬다.
- 롤백 절차를 문서로 남긴다. 자동 업데이트가 나쁜 빌드를 배포한 상황이 가장 비싼 장애다.
- 마이그레이션은 되돌릴 수 없을 수 있다. 되돌릴 수 없는 마이그레이션 전에 백업을 만든다.

## 8. 관측성

- 로그는 **파일로도** 남긴다(사용자가 보내 줄 수 있어야 한다). 회전·상한을 둔다.
- 로그에 프로세스(main/renderer)·창 ID·작업 ID를 넣어 상관 가능하게 한다.
- 개인정보·비밀·파일 내용 전체를 로그에 남기지 않는다.
- 사용자가 로그를 첨부해 문의할 수 있는 경로를 앱 안에 둔다("로그 폴더 열기").
- 콜드 스타트·메모리·IPC 지연 지표를 수집한다([`frontend-performance.md`](./frontend-performance.md)).

## 9. 실패를 일부러 재현해 본다

개발 환경에서는 아무것도 실패하지 않는다. 아래를 의도적으로 만들어 보고 화면을 확인한다.

- 네트워크 끊기 · 느린 네트워크 · 프록시 뒤
- 디스크 가득 참 · 파일 권한 없음 · 파일 손상
- 앱 강제 종료 후 재시작(저장되지 않은 상태)
- 두 번째 창 · 창을 닫았다 다시 열기 · 모니터 분리
- 구버전 데이터 파일로 시작
