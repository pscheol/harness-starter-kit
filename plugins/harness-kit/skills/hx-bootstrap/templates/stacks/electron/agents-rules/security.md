# 보안 가드레일 — {{PROJECT_NAME}}

이 규칙 위반은 **코드리뷰 즉시 차단 대상**이다. 일정·성능보다 우선한다.
프로젝트 고유의 권한 모델은 여기가 아니라 `product.md`와 설계 문서에서 정한다.
이 파일은 **어느 Electron 앱에서나 지켜야 하는 최소 방어선**만 규정한다.

## 대전제 — 데스크톱 앱의 XSS는 웹의 XSS보다 비싸다

브라우저의 XSS는 그 사이트의 데이터를 가져간다. **Electron의 XSS는 사용자의 컴퓨터를 가져간다.**
경계가 무너지면 파일 읽기·쓰기, 명령 실행, 네트워크 접근이 전부 열린다.

그래서 이 스택의 보안은 "입력을 잘 검사하자"가 아니라 **"렌더러에 권한을 주지 않는다"** 로 시작한다.

## 프로세스 경계 (협상 대상 아님)

모든 `BrowserWindow`·`BrowserView`·`WebContentsView`는 아래 설정으로 연다.

```ts
webPreferences: {
  contextIsolation: true,      // preload 스코프와 페이지 스코프 분리
  nodeIntegration: false,      // 렌더러에 Node 권한 없음
  sandbox: true,               // 렌더러 프로세스 격리
  webSecurity: true,           // 동일 출처 정책 유지(기본값 — 끄지 않는다)
  preload: /* 절대 경로 */,
}
```

- 이 값들을 "개발 편의"로 잠깐 풀지 않는다. 잠깐이 영구가 된다.
- `scripts/verify.sh`의 **프로세스 경계 가드**가 이 설정들을 grep으로 검사한다(fast 레벨 포함).
  가드를 통과시키려고 패턴을 우회하는 코드를 쓰지 않는다.
- `<webview>`는 쓰지 않는다. 꼭 필요하면 설계 문서에 근거를 남기고 별도 검토를 받는다.
- `experimentalFeatures`·`allowRunningInsecureContent`를 켜지 않는다.

## IPC — 화이트리스트만 노출한다

```ts
// preload — ✗ 절대 금지: 임의 채널 호출을 허용하는 것과 같다
contextBridge.exposeInMainWorld('api', ipcRenderer);
contextBridge.exposeInMainWorld('api', { invoke: (ch, ...a) => ipcRenderer.invoke(ch, ...a) });

// preload — ✓ 동작 단위로 좁게 노출한다
contextBridge.exposeInMainWorld('{{PROJECT_SLUG}}', {
  {{DOMAIN_EXAMPLE}}: {
    list: (query: unknown) => ipcRenderer.invoke('{{DOMAIN_EXAMPLE}}:list', query),
  },
});
```

- **채널 이름을 인자로 받는 함수를 노출하지 않는다.** 그건 화이트리스트가 아니다.
- 노출하는 것은 **동작**이지 자원이 아니다. "파일 읽기"가 아니라 "이 문서 열기".
- 노출 표면을 최소로 유지한다. 렌더러가 쓰지 않는 API를 미리 열어 두지 않는다.
- preload에 비즈니스 로직·권한 판정을 넣지 않는다. 다리는 다리다.
- 이벤트 구독을 노출할 때 콜백에 **main이 보낸 이벤트 객체를 그대로 넘기지 않는다**(내부 참조가 샌다).
  필요한 데이터만 골라 넘긴다.

## main 핸들러 — 렌더러 입력은 신뢰 경계 밖이다

- 모든 `handle`은 인자를 **스키마로 파싱**한 뒤 쓴다. `as`로 단정하지 않는다.
- 파싱 실패는 에러로 반환한다. 조용히 기본값으로 진행하지 않는다.
- **경로**: 사용자·렌더러가 준 문자열로 경로를 조립하지 않는다. 허용된 루트(앱 데이터·사용자가 다이얼로그로
  고른 경로) 하위인지 정규화 후 검증한다. `..`가 포함될 수 있다고 가정한다.
- **셸·프로세스 실행**: 렌더러 입력을 명령줄에 넣지 않는다. 셸을 경유하지 않고 인자를 분리해 전달한다.
- **외부 열기**: `shell.openExternal`에 임의 URL을 넘기지 않는다. **스킴을 allowlist로 제한**한다
  (`https:`만 등). `file:`·`javascript:`·커스텀 스킴은 코드 실행 경로가 된다.
- 채널마다 **부작용의 크기**를 의식한다. 파일 삭제·설정 변경·업데이트 트리거 같은 채널은 별도로 표시하고
  필요하면 사용자 확인을 main에서 요구한다.

## 렌더러 — 웹의 규칙이 그대로 적용된다

- **사용자·외부 콘텐츠를 HTML로 주입하지 않는다.** `innerHTML`·`dangerouslySetInnerHTML` 기본 금지.
  불가피하면 검증된 정제 라이브러리를 거치고 이유를 주석으로 남긴다.
- `eval`·`new Function`·문자열 `setTimeout` 금지.
- **CSP를 설정한다.** 로컬 파일로 로드하더라도 마찬가지다. `script-src`에 `'unsafe-inline'`·`'unsafe-eval'`을 넣지 않는다.
- 외부 URL을 앱 창에서 열지 않는다. `setWindowOpenHandler`로 **새 창 생성을 기본 거부**하고,
  허용 목록에 든 https URL만 **외부 브라우저**로 보낸다.
- 앱 안에서 원격 콘텐츠를 렌더링해야 한다면 그 창은 별도 세션·별도 preload(없음)로 격리한다.

## 비밀 · 자격증명

- **비밀을 렌더러에 내리지 않는다.** 렌더러 코드는 사용자가 볼 수 있고, DevTools로 런타임 값도 볼 수 있다.
- 자격증명이 필요한 외부 호출은 **main에서** 한다. 렌더러에는 결과만 준다.
- 토큰·비밀번호는 OS 키체인(Credential Manager·Keychain·Secret Service)에 저장한다.
  평문 파일·`localStorage`에 두지 않는다.
- 설정 파일에 비밀을 쓰지 않는다. 서명 인증서·업데이트 토큰을 리포에 커밋하지 않는다.
- 로그에 비밀·개인정보·전체 요청 본문을 남기지 않는다. 크래시 리포트도 마찬가지다.

## 자동 업데이트 · 배포

- **코드 서명은 선택이 아니다.** 서명되지 않은 앱은 OS 경고를 넘어 사용자가 실행하도록 훈련시킨다.
- 자동 업데이트는 **서명 검증이 되는 채널**로만 한다. HTTPS + 서명 확인 없이 업데이트를 적용하지 않는다.
- 업데이트 서버 주소를 사용자 입력이나 설정 파일로 바꿀 수 있게 만들지 않는다(공급망 침해 경로).
- 릴리스 채널(stable/beta)을 분리하고, 롤백 절차를 문서로 남긴다.

## 의존성 · 네이티브 모듈

- 락파일을 커밋하고 재현 설치(`--frozen-lockfile`)를 쓴다.
- **Electron 버전을 최신 안정선으로 유지한다.** Chromium 보안 패치가 여기로 들어온다.
  버전이 오래되면 앱 코드가 완벽해도 취약하다.
- 알려진 취약점 스캔을 정기적으로 돌린다. `postinstall`을 실행하는 새 의존성은 검토 대상이다.
- 네이티브 모듈은 출처와 빌드 방식을 확인한다(임의 바이너리를 받아 실행하는 설치 스크립트 주의).

## 파일 · 저장소

- 앱 데이터는 OS 표준 경로 API로 얻는다. 경로를 하드코딩하지 않는다.
- 사용자 파일에 쓰기 전에 대상이 의도한 디렉터리 하위인지 확인한다.
- 임시 파일은 예측 가능한 이름으로 만들지 않는다.
- 다운로드·가져오기 파일은 확장자만 믿지 않는다. 열기 전에 내용·크기를 확인한다.
- 사용자 데이터를 삭제하는 동작에는 되돌릴 수 없다는 표시와 확인 단계를 둔다.

## 진단 · 배포 위생

- 운영 빌드에서 DevTools를 기본으로 열지 않는다(디버그 빌드에서만).
- 소스맵을 배포 아티팩트에 그대로 넣을지 의식적으로 정한다. 크래시 리포터에는 올리되 배포본에는 넣지 않는 쪽이 기본.
- 원격 디버깅 포트를 켠 채 배포하지 않는다.
