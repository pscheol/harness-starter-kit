jira-workflow · notion · multi-harness

선택 모듈은 다섯이다. 외부 도구를 붙이는 aidlc · entire 는 앞 두 장에서 다뤘고, 이 장은 모듈 공통 규칙과 나머지 셋 — 이슈 트래커(jira-workflow), Notion 접수(notion), 여러 리포(multi-harness) — 을 다룬다.

jira-workflow — 이슈 트래커

Jira(또는 비슷한 트래커)를 쓰는 팀을 위한 작업 규약이다. 켜면 규칙 issue-tracker-workflow.md · issue-agent-lock.md, 설정 .agents/issue-tracker.yml, 스킬 /kns-issue(조회 · 착수 · 리뷰 요청 · 착수 철회 · 락 해제 · 티켓 생성) · /kns-ticket(티켓 하나를 가져오기 → SDD 스펙 → 착수 → 구현 → 리뷰 요청까지)이 깔린다.

대응

AI-DLC 말Jira리포

Unit작업 항목(contract · integration → 작업, feature → 스토리, 버그 → 버그). 이 키가 이슈 키issues/<키>-<이름>/ · 브랜치 · MR
Bolt하위 작업(선택, Bolt 2개 이하 Unit 은 만들지 않는다)tasks.md 의 Phase

상태와 누가 옮기나

Jira 상태킷 단계옮기는 주체
백로그Unit 목록에 있음에이전트(사람 요청으로 이슈 생성)
요구사항 작성requirements draft에이전트
요구사항 승인 대기requirements in-review에이전트
설계design사람(PO) — requirements 승인 전이
구현 중tasks active사람(개발자) — design · tasks 승인 전이
검증MR 열림에이전트(MR + affected 통과)
완료tasks completed사람(QA · PO) — 완료 승인 전이
배포됨운영 기록사람(운영) — 배포 승인 전이

에이전트가 옮길 수 있는 상한은 "검증"이다(agentBoundary.maxStatus: verifying). approvalTransitions 에 적힌 전이(요구사항 승인 대기 → 설계, 설계 → 구현 중, 검증 → 완료, 완료 → 배포됨)는 에이전트가 하지 않는다.

설정하기

  1. 모듈을 켠다

    knots-sync add jira-workflow. .agents/issue-tracker.yml 이 TBD 가 든 채로 깔린다.

  2. ID 를 채운다 — /kns:jira-setup

    플러그인 스킬이 트래커 접근 수단(MCP · CLI · REST)을 정하고, 트래커에서 상태 ID · 전이 ID 를 조회해 statusMap · approvalTransitions · issueTypes · groupMap 의 TBD 를 채운 뒤 읽기 전용 스모크로 확인한다.

  3. 토큰은 환경 변수에만

    REST 는 JIRA_API_TOKEN · JIRA_USER_EMAIL 을 읽는다. 리포 · 세션에 쓰지 않는다.

  4. 이슈 키를 Jira 에서 받는다

    knots-sync.json 의 issueKey.source = "jira"(설치 때 --issue-source jira). Intent 키는 에픽 키가 된다.

맞추기

$ knots-sync sync jira --dry-run                     # 리포 → Jira: 에이전트 몫 전이 · 원격 링크(설명은 고치지 않는다)
$ knots-sync sync jira --issue <키> --to <상태>          # 한 이슈만(에이전트 몫 전이만)
$ knots-sync sync jira --approvals                   # Jira → 리포: 사람이 한 승인 전이를 approvals.md 로(REST, changelog)
$ knots-sync intake --from jira:PAY-40 --name payment-revamp   # 에픽을 요구사항으로 접수

가져온 승인은 경로: jira 와 근거: changelog <id> 줄로 남는다. 모듈이 꺼져 있으면 sync jira 는 exit 0 으로 아무것도 하지 않는다. 이미 가져온 출처를 다시 intake 하면 diff 만 보이고(exit 4), --yes 로 반영한다.

실제 Jira

Jira 연동은 흉내 응답(가짜 REST)으로만 시험했다. 실제 Jira 프로젝트에서 상태 · 전이 ID 조회, 승인 전이 가져오기, 에픽 접수를 사람이 확인해야 한다(로드맵의 사람 확인 목록).

notion — Notion 접수 출처

요구사항이 Notion 에 쌓이는 팀을 위한 모듈이다. Notion 페이지나 요구사항 데이터베이스 항목을 intake.md 로 가져온다.

$ knots-sync add notion
$ export NOTION_TOKEN=…          # 사람 셸에만. 리포에 쓰지 않는다
$ knots-sync intake --from notion:https://www.notion.so/… --name refund-policy [--depth 1] [--yes]
  • 가져오는 것은 사람이 터미널에서 한다. 에이전트 세션은 토큰을 읽거나 Notion 을 직접 부르지 않는다.
  • Notion 통합(integration)에 가져올 페이지를 공유해 둔다. 하위 페이지는 --depth 단계(기본 1)만 따라가고 파일 · 이미지는 첨부로 받는다.
  • 가져온 글은 trust: untrusted. intake.md 머리 source: {type, ref, url, importedAt, version} 가 출처다. 가져온 뒤의 원본은 리포다. 다시 가져오면 바뀐 부분을 diff 로 보이고 --yes 전에는 덮지 않는다.
  • 속성 대응은 knots-sync.json 의 notion 절(database · properties · kindMap · writeBack). writeBack 은 기본 꺼짐 — 킷은 Notion 에 쓰지 않는다.
실제 Notion

흉내 응답으로만 시험했다. 실제 워크스페이스 · 데이터베이스 연결은 사람 확인 항목이다.

multi-harness — 여러 리포

상위 리포 하나와 도메인 리포(submodule) 여럿을 하네스 하나로 다루는 팀을 위한 모듈이다. 공통 하네스 파일을 배포 단위(배포 대상 폴더, tools/harness/units.json)마다 복사하고, 리포 간 작업 순서와 안전 검사를 준다. 이 "배포 단위"는 Intent 의 Unit 과 다른 것이다 — Intent Unit 의 repo 값이 배포 단위 id 다.

$ knots-sync add multi-harness
$ knots-sync sync units --check            # 단위마다 공통 하네스가 맞는지(쓰지 않음). 줄 형식은 tools/harness/sync.py 와 같다
$ knots-sync sync units                    # 복사
$ knots-sync sync units --unit api --adopt # 한 단위만 · 있던 파일을 받아들이며
$ python3 scripts/harness/check_submodules.py [--record <이슈 키>]
기능 하나가 도메인 리포 둘 이상을 건드릴 때(규칙 cross-repo.md)
단계하는 일
1 계약 확정상위 리포에 계약 Unit(kind: contract) 이슈. design §6 승인이 계약 승인이다
2 병렬 구현도메인 리포마다 구현 세션 1개. 리포가 다르면 worktree 없이 각자 폴더에서
3 경계 검증상위 리포에서 계약 시험 + check_submodules.py + 도메인 간 경로 가드
4 순서 커밋제공 도메인 → 소비 도메인 → 상위 리포 포인터. 포인터를 먼저 커밋하지 않는다
5 기록check_submodules.py --record <이슈 키> 로 상위 specs-index.md 의 그 이슈 행에 도메인별 submodule SHA
  • check_submodules.py 가 보는 것: 초기화 안 됨 · 포인터가 원격에 없는 커밋을 가리킴 · 커밋 안 된 변경이 있는데 포인터를 커밋하려 함 · 상위와 submodule 의 이슈 키가 다름. affected 검증은 바뀐 도메인 submodule 에만 이것을 부른다.
  • 도메인 파일이 다른 도메인 경로를 참조하면 scripts/guards/no-cross-domain-paths.sh 가 알린다. 예외는 .agents/guards/cross-domain-allow.txt 에 경로 사유 로. 경고로 시작하고 위반이 0건이 되면 강제로 올린다.
  • 하위 단위는 .agents/harness.json 으로 자기 하네스 루트를 표시한다. 훅과 스크립트는 작업 폴더에서 위로 올라가며 가장 가까운 knots-sync.json 또는 harness.json 을 루트로 쓴다.
  • submodule 이 있는 상위 리포는 worktree 로 만들지 않는다(git 이 권하지 않는다). worktree 는 도메인 리포 단위로만.
