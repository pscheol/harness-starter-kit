01 · 개념

개념

knots-sync 를 쓰기 전에 알아야 할 말은 많지 않다. 원본은 한 곳, 일은 SDD 단계를 따라 흐르고, 단계 사이에는 사람이 승인하는 게이트가 있다. 이 장은 그 뼈대를 그림으로 보여 준다.

일곱 가지 원칙

설계서의 공통 계약에서 사용자에게 보이는 것만 추렸다. 이 원칙이 명령과 화면의 동작을 정한다.

  1. 원본은 .agents/ 한 곳이다. 하네스 폴더의 파일은 원본에서 만든 실제 파일이고, 복사본은 동기화 훅 · 보호 훅 · 배치 검사로 원본과 맞춘다. 하네스 폴더를 손으로 고치면 다음 repair 가 원본에서 다시 만든다.
  2. 완료 판정은 scripts/verify.sh 한 곳이다. 훅 · git 훅 · CI 는 이 스크립트를 부르기만 한다.
  3. 사람이 고친 파일과 다른 도구의 파일은 덮지 않는다. 킷 새 판이 사람이 고친 파일과 부딪히면 새 판을 <경로>.new 로 옆에 둔다.
  4. 외부 도구(AI-DLC · Entire)의 파일은 고치지 않는다. 킷은 그 파일을 external:<도구> 소유로 기록만 한다.
  5. 모듈 없이도 전 흐름이 돈다. AI-DLC · Entire 는 기본 꺼짐인 선택 모듈이다.
  6. 화면 없이도 모든 기능이 돈다. 관리 페이지는 CLI 와 같은 핵심 모듈을 부르는 화면일 뿐이다. 화면에만 있는 기능은 없다.
  7. 킷을 들여도 토큰이 늘지 않게 한다. 킷 자체는 모델을 부르지 않고, 세션에 덧붙이는 양에 상한을 둔다(세션 시작 훅 2,560바이트, 진입 파일 24KB). 사람이 연 세션의 모델 · effort 는 바꾸지 않는다. 모델 조절은 위임 작업(하위 에이전트)에만 한다.

흐름과 게이트

요구사항 하나가 운영까지 가는 길이다. 마름모가 게이트, 즉 사람이 승인해야 다음 단계로 넘어가는 자리다. 속이 찬 마름모 넷(requirements · design · mr · done)은 줄일 수 없는 하한이고, 속이 빈 마름모는 팀이 흐름 틀(flow.gates)에서 켜고 끈다.

게이트 아홉 — 무엇을 승인하나
게이트승인 대상기본 승인자 그룹줄일 수 있나통과 조건(요약)

requirementsrequirements.mdpo하한막는 질문 0, [NEEDS CLARIFICATION 0
designdesign.mddev하한requirements 통과, 의존 계약 이슈의 design 통과, §13 배포 · 롤백 칸
taskstasks.mddev팀 설정design 통과
mr문서 없음(MR 자체)dev하한같은 head 의 affected 검증 passed, 품질 게이트 passed, 열린 리뷰 CRITICAL · HIGH 0
done문서 없음(병합된 이슈)qa · po하한mr 통과, 이슈 브랜치가 base 에 병합됨
deploy배포 기록의 계획 구간ops팀 설정포함 이슈 done, 롤백 시험 또는 면제, 배포 커밋의 full 통과 등(→ deploy 게이트)

승인자 그룹(po · dev · qa · ops)은 .agents/knots-sync.json 의 approvers · groups 로 정한다. 둘 다 선택이다. 그 게이트의 승인자가 비어 있으면 이 리포의 git 사용자 누구나 승인할 수 있다. 신원은 그 체크아웃의 git user.email 이다. 회원 · 로그인은 없다.

흐름 틀 바꾸기는 터미널 명령이고 MR 로 올린다: knots-sync flow gates --add <게이트> --after <게이트> · --remove <게이트>. 하한 넷은 빼지 못한다.

일의 크기(프로필)와 위험

모든 일이 아홉 게이트를 다 지나지는 않는다. 접수할 때의 종류와 분해 판정으로 프로필이 정해지고, 프로필이 만드는 산출물의 게이트만 생긴다. 위험 등급은 승인 깊이를 정한다. 하한 넷은 이슈가 있는 모든 프로필에 있다.

프로필언제만드는 것
trivial바뀐 줄 20 이하, 새 · 지운 파일 0, 위험 경로 0이슈 없이 chore/<이름> 브랜치와 MR(넘으면 affected 검증이 "이슈가 필요하다"로 실패)
bug접수 종류 bug이슈 하나(재현 · 현재 · 기대 · 바뀌면 안 되는 동작)
unitfeature · change 이고 분해 기준 넷 모두 미만Intent(짧게) · current-state · 이슈 하나. 기획물 없음
featurefeature · change 이고 분해 기준 하나 이상(스토리 ≥ 5 · 도메인 ≥ 2 · 사용자 유형 ≥ 3 · 외부 통합 ≥ 3)전부
product접수 종류 product(처음부터 만드는 제품)전부 + 걷는 뼈대 Unit
refactor접수 종류 refactorIntent · current-state · 이슈, 특성 시험이 첫 Phase

위험은 low(게이트마다 1명) · medium(1명, design 의 "사람이 볼 곳" 줄 필수) · high(권한 · 인증 · 결제 · 개인정보 · 되돌릴 수 없는 마이그레이션 등 — design · mr · deploy 에 서로 다른 승인자 2명, 롤백 시험 면제 불가)다. diff 가 risk.highPaths 에 걸리면 문서 값과 상관없이 high 로 본다.

이슈의 SDLC 여덟 단계

이슈 하나는 .agents/docs/issues/<키>-<이름>/ 폴더 하나, 브랜치 <종류>/<키>-<이름> 하나, MR 하나다. 폴더 안 문서는 단계에 들어갈 때만 생긴다.

단계남는 것스킬게이트
S1 분석requirements — 스토리 · R#.# 수용 기준 · 성공 기준 SC-/kns-specify · /kns-clarifyrequirements approved
S2 기획requirements — 정책 표 P-# · 화면 표(없으면 "화면 없음")/kns-specify · /kns-checklist
S3 설계design — 순서도 · 시퀀스 · 상태 · DB · 인덱스 · 캐시 키 · 동시성 · API · §13 배포 · 롤백/kns-plan · /kns-analyzeConstitution Check · design approved
S4 계획tasks.md(state: active), Phase = Bolt/kns-taskstasks(팀 설정)
S5 구현코드 · 시험/kns-implement · /kns-maintainchanged 검증
S6 테스트tasks 의 [VERIFICATION] 기록/kns-checklist · verify.sh검증 레벨
S7 문서 반영기능 문서 원고 · 생성 HTML/kns-docs기능 문서 검사
S8 완료state: check → 사람 검수 → completed/kns-converge(남은 일)done 승인

문서 머리(frontmatter)의 status 는 draft → in-review → approved 로 간다. 에이전트는 in-review 까지만 올린다. approved 는 승인 경로만 바꾼다. 파일이 있다는 것이 승인은 아니다.

Intent · Unit · Bolt

요구사항이 크면 이슈 하나로 끝나지 않는다. knots-sync 는 AI-DLC 의 말을 빌려 세 층으로 나눈다.

Intent
요구사항 하나를 정리한 설계 단위. Jira 에픽에 대응한다. 키는 INT-<n>(jira-workflow 를 켜면 에픽 키). 폴더 .agents/docs/intents/<키>-<이름>/ 에 intake.md · intent.md · questions.md · units.json · approvals.md · plans/ 가 산다.
Unit
독립적으로 만들고 배포할 수 있는 작업 묶음. Unit 하나 = 이슈 하나 = SDD 폴더 하나 = 브랜치 · MR 하나. 도메인 사이 API · 이벤트는 kind: contract Unit 으로 먼저 만든다.
Bolt
Unit 안의 작업 묶음. tasks.md 의 Phase 하나다. Bolt 가 끝날 때마다 changed 검증을 돈다.
이슈 키
Unit 의 식별자. 형식 ^[A-Z][A-Z0-9]{1,9}-[1-9][0-9]{0,5}$. Jira 를 쓰면 Jira 키, 아니면 킷이 <접두>-<다음 번호> 로 만든다. 외부 이슈 번호를 지어내지 않는다.
질문
questions.md 의 Q-n. 선택지 2~4개 · 권장안 · 답할 직무(po · dev …) · 막는 게이트가 있다. 사람이 관리 페이지나 knots-sync answer 로 답한다.

승인 — 누가, 어디서, 어떻게

게이트 승인은 네 경로로만 생기고, 모두 approvals.md 에 덧붙이는 한 줄 기록으로 남는다. 에이전트는 이 파일을 쓰지 못한다(Claude Code 는 permissions.deny 에 Edit(//**/approvals.md), 다른 하네스는 PreToolUse 훅, git pre-commit 은 기존 줄 변경을 거부).

승인 경로 넷
경로방법기록의 경로 줄
관리 페이지사람 터미널에서 연 서버의 "승인하고 기록" + PINdashboard
사람 터미널knots-sync approve <키> --gate <게이트> --phrase "…"(Node 없는 리포는 python3 scripts/harness/approve.py <키> <게이트> --phrase "…"). TTY 가 아니면 exit 3, 마지막에 이슈 키를 다시 입력해 확인한다terminal
Jira(모듈을 켰을 때)사람이 Jira 에서 한 승인 전이를 knots-sync sync jira --approvals 로 가져온다jira
AI-DLC(모듈을 켰을 때)AI-DLC 의 사람 입력 확인 훅이 받은 승인을 knots-sync sync aidlc 가 옮긴다. 기록에 승인자가 있을 때만aidlc
형식approvals.md 한 기록(설계서 06 §3.7) 
## 2026-11-23T14:05:12+09:00 · design · approved
- 승인자: kim@example.com (Kim) · 그룹: dev
- 대상: design.md · sha256: 9f1c2ab0…(64자)
- 문구: "B안으로 반영해"
- 경로: dashboard
- 기록 ID: 01JDQ4ZK6B7Y0M9W2S3T4V5X6Y

승인은 문서의 sha256 에 묶인다. 승인 뒤 문서가 바뀌면 그 승인은 오래된(stale) 승인이 되고 다시 받아야 한다(머리의 status · state 줄만 바뀐 것은 셈하지 않는다). 승인 문구는 기록일 뿐이고 문구만으로 승인이 생기지는 않는다.

왜 이렇게까지 하나

에이전트가 스스로 승인하면 게이트가 없는 것과 같다. 그래서 PIN 은 사람 터미널에만 나오고, 에이전트 세션 안에서 연 서버는 읽기 전용으로 뜨며(판정: CLAUDECODE=1 같은 하네스 변수 · 부모 프로세스), 훅이 에이전트의 knots-sync approve|answer|review decide 실행과 토큰 파일 읽기를 막는다. 같은 OS 사용자의 임의 프로세스까지는 막지 못한다 — 더 강한 증거가 필요한 게이트는 Jira 사람 전이나 MR 플랫폼 승인을 같이 쓴다.

하네스와 역할

하네스는 Claude Code · Codex · Cursor · Kiro 같은 에이전트 실행 도구다. knots-sync 는 같은 원본을 각 하네스가 읽는 자리에 놓는다.

역할은 "누가 어떤 세션에서 무엇을 하나"다. 사람이 세션을 열고, 킷은 그 세션이 어떤 역할인지 알려 주고 경계를 지킨다. 기본 배치(결정 D7)는 아래와 같고 knots-sync.json 의 roles 로 바꾼다.

역할기본 하네스하는 일쓰는 곳
designClaude Code/kns-intent · /kns-plans · /kns-specify · /kns-planIntent 폴더 · 이슈 문서(승인 · 답 줄은 쓰지 않는다)
implementClaude Code/kns-tasks · /kns-implement · /kns-maintain코드 · 시험 · tasks
reviewCodex/kns-review · /kns-scan(읽는 세션)지적 파일만(findings.json). 체크아웃하지 않고 원격 diff 를 읽는다
docsKiro/kns-docs기능 문서 원고
진행 판정사람게이트 승인 · 질문 답 · 리뷰 판단 · 세션에 요청approvals.md · questions.md 의 답

같은 리포에서 파일을 쓰는 세션이 둘 이상이면 이슈마다 worktree 를 만든다: python3 scripts/harness/worktree.py new <키>. 자리는 리포 옆 ../<리포>.worktrees/<키>-<이름>/, 리포당 3개까지, 끝나면 done 으로 바로 지운다.

원본 · 복사본 · 소유자

.agents/knots-sync.lock 은 킷이 깐 파일마다 소유자와 sha256 을 적는다. 소유자가 update · remove · uninstall 의 동작을 정한다.

owner누구 것updateremove · uninstall
kit킷이 깐 파일고치지 않았으면 새 판으로 바꾼다. 사람이 고쳤으면 새 판을 .new 로 옆에 둔다(exit 4)고치지 않은 것만 지운다. 고친 것은 남기고 exit 4
user설치 전부터 있던 파일(init --adopt 로 받은 파일 포함)건드리지 않는다건드리지 않는다
pack:<이름>회사 팩이 준 파일update --packs 로만 바꾼다uninstall 은 함께 지운다(--keep-packs 면 남긴다)
external:<도구>AI-DLC · Entire 가 만든 파일 · 훅기록만(op: none). 파일 · 훅 sha 를 바꾸지 않는다지우지 않는다. 도구 쪽 명령은 사람이 실행한다

사람이 고친 킷 파일은 doctor 에 drifted 로 보인다. 계속 고친 채 쓰려면 놔두고, 킷 판으로 돌리려면 그 파일을 지운 뒤 knots-sync repair 로 되살린다.
