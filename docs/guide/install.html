설치

설치는 두 번 일어난다. 먼저 내 컴퓨터의 하네스에 킷 스킬(플러그인)을 깔고, 그 다음 리포마다 킷을 깐다. 리포에 까는 일은 플러그인 스킬 /kns:bootstrap 으로 해도 되고 CLI knots-sync init 으로 해도 된다. 둘은 같은 설치기를 부른다.

두 층의 스킬

이름이 모두 kns 로 시작하지만 사는 곳이 다르다. 먼저 구분해 둔다.

층스킬사는 곳언제
킷 스킬(10종)kns:bootstrap · kns:jvm-setup · kns:jvm-hexagonal · kns:jvm-layered · kns:jvm-layered-multimodule · kns:web-setup · kns:electron-setup · kns:jira-setup · kns:agent-add · kns:update내 컴퓨터의 하네스 플러그인(kns: 네임스페이스). Kiro 는 ~/.kiro/skills/kns-*리포에 골격을 깔거나 킷을 올릴 때
프로젝트 스킬(15종)kns-intent · kns-plans · kns-specify · kns-clarify · kns-checklist · kns-plan · kns-tasks · kns-analyze · kns-implement · kns-maintain · kns-review · kns-scan · kns-docs · kns-converge · kns-harness리포 안(.agents/skills/ 원본, 하네스 폴더에 복사본)매일 개발할 때

플러그인 스킬은 kns: 네임스페이스를 가져서 프로젝트 스킬과 부딪히지 않는다. 프로젝트 스킬에 kns- 를 붙인 것은 /plan · /analyze 같은 흔한 이름이 다른 플러그인과 부딪히지 않게 하려는 것이다.

준비물

  • Node 18.3 이상 — CLI 와 관리 페이지. 없으면 플러그인의 kit.sh 가 v1 설치 스크립트로 내려간다(아래 CLI). 런타임 의존성은 0개다.
  • git — 승인자 신원(user.email)과 변경 범위 계산에 쓴다.
  • python3 · bash — 리포 스크립트(scripts/verify.sh · scripts/harness/*.py)가 Node 없이 돈다. 팀원 중 Node 가 없는 사람도 검증 · 승인 · 보드를 쓸 수 있다.
  • 쓰는 하네스 하나 이상 — Claude Code · Codex · Cursor · Kiro.

Claude Code

  1. 마켓플레이스를 더하고 플러그인을 깐다

    # Claude Code 안에서. 로컬 경로로 등록
/plugin marketplace add /path/to/harness-starter-kit
/plugin install kns@knots-sync

# GitHub 에 올린 저장소라면
/plugin marketplace add <owner>/harness-starter-kit

  2. Claude Code 를 다시 켠다

    플러그인과 스킬 목록은 세션이 시작될 때 읽힌다. /plugin 으로 kns 가 보이는지 확인한다.

  3. 리포에 깐다

    /kns:bootstrap                          # 현재 폴더. 스택 · 변형은 판단 후 애매하면 묻는다
/kns:bootstrap ~/work/api --dry-run     # 미리보기
/kns:jvm-setup                          # JVM 전용 입구 — 아키텍처 8종 중 고르기
/kns:web-setup                          # 웹 프론트엔드 — 3종
/kns:electron-setup                     # Electron — 3종

    자연어로도 된다: "kns:bootstrap 스킬로 이 리포에 하네스 골격을 깔아줘".

Codex

$ codex plugin marketplace add /path/to/harness-starter-kit
$ codex plugin add kns@knots-sync

Codex 플러그인 매니페스트에는 커맨드 칸이 없어 스킬로 부른다: /skills 목록에서 고르거나 $kns:bootstrap. 리포에 깐 뒤의 프로젝트 스킬은 $kns-specify 처럼 $ 로 부른다. 확인은 codex plugin list.

Codex 스킬 경로

프로젝트 로컬 .codex/prompts/ 는 Codex 가 찾는 자리가 아니다(유저 홈 전용이고 custom prompts 자체가 사라질 예정이다). 그래서 Codex 공식 프로젝트 스킬 경로인 .agents/skills/ 를 쓴다 — 원본이 곧 Codex 스킬이다.

Kiro

Kiro 에는 플러그인 마켓플레이스가 없어서 킷 저장소의 install-kiro.sh 가 그 자리를 대신한다. 스킬 폴더를 통째로 복사하므로 설치 뒤에는 킷 저장소를 옮기거나 지워도 그대로 돈다.

$ bash install-kiro.sh                      # ~/.kiro/skills/ 에 킷 스킬 설치
$ bash install-kiro.sh --dry-run            # 계획만
$ bash install-kiro.sh --force              # 기존 것도 덮어쓴다(킷을 올렸을 때)
$ bash install-kiro.sh --uninstall          # 이 스크립트가 깐 것만 지운다
$ bash install-kiro.sh --home=/path/.kiro   # 대상 홈(환경 변수 KIRO_HOME 도 된다)
  • 스킬은 ~/.kiro/skills/kns-<명령>/SKILL.md 로 깔린다(예: kns-bootstrap 에는 setup.sh · lib/ · templates/ 까지 함께 간다). 옛 이름(hx-*) 설치 기록이 있으면 그 폴더만 치운다.
  • Kiro 스킬 규약은 <홈>/skills/<스킬명>/SKILL.md 다. 한 겹 더 감싸면(skills/kns/skills/…) 인식되지 않는다 — 저장소를 통째로 복사해 넣으면 이 함정에 빠진다.
  • 설치 기록은 ~/.kiro/.knots-sync-manifest.json 에 남고, --uninstall 은 그 기록에 적힌 폴더만 지운다.
  • 세션 시작 때 읽히므로 설치 뒤 kiro-cli 를 다시 켠다.

이 스크립트가 까는 것은 킷 스킬이다. 리포 쪽 Kiro 배선(.kiro/steering · .kiro/skills · .kiro/agents · .kiro/hooks)은 리포에 킷을 깔 때 --agents kiro 로 생긴다.

Cursor

Cursor 용 플러그인 경로는 따로 없다. 리포에 킷을 깔 때 하네스로 cursor 를 고르면 된다. CLI 는 킷 저장소나 다른 하네스의 플러그인 폴더에 있는 것을 쓴다(아래 CLI).

$ knots-sync init --agents claude,cursor     # 새로 깔 때
$ knots-sync add cursor                     # 이미 깐 리포에 더할 때

Cursor 는 .cursor/commands/kns-*.md(15개)와 .cursor/rules/(22개)를 받고, 채팅에서 /kns-specify 처럼 부른다.

Cursor 규칙의 globs

Cursor 규칙의 globs 쉼표 목록, Kiro fileMatchPattern 배열이 실제 도구에서 의도대로 걸리는지는 사람이 확인해야 할 항목으로 남아 있다.

CLI — knots-sync · kns

CLI 는 Node 파일 하나다(런타임 의존성 0). 패키지가 내는 실행 이름은 knots-sync · kns · harness-kit(옛 이름, 한동안) 셋이다.

지금은 npx 로 부르지 않는다

npm 배포 전이라 npx knots-sync 가 같은 이름의 남의 패키지를 받을 수 있다. 결정 D3 에 따라 먼저 npx github:<owner>/harness-starter-kit 로 배포하고, v2.2 까지 명령이 그대로면 npm 에 올린다. 그 전에는 아래 둘 중 하나를 쓴다.

방법명령비고
킷 저장소의 CLI 직접node <킷>/plugins/kns/skills/bootstrap/bin/knots-sync.js <명령>셸 별칭 alias knots-sync='node …/knots-sync.js' 를 권한다
플러그인 안의 입구bash <플러그인>/skills/bootstrap/kit.sh <명령>Node 18.3 이상이면 CLI 를 그대로 부르고, 없으면 v1 스크립트로 내려간다(v2.0 동안만)

kit.sh 가 Node 없이 내려가는 길: init · plan → setup.sh(plan 은 --dry-run), update → update.sh, add → add-agent.sh. remove · outdated · doctor · repair · uninstall · list 는 CLI 에만 있어 exit 5 로 멈춘다. kit.sh --which 는 cli 또는 legacy 한 줄을 낸다.

리포에 깔기 — init

순서는 늘 같다: plan 으로 보고 → init 으로 깔고 → doctor 로 확인하고 → 커밋한다. 실제 출력은 10분 시작에 있다.

하네스 고르기와 나중에 더하기

쓰는 하네스만 고른다. 고르지 않은 하네스의 폴더는 만들지 않는다.

이미 손으로 만든 하네스가 있는 리포

init --adopt 로 깐다. 있던 파일은 owner: user 로 남아 이후 update 가 건드리지 않는다. 그래도 두 파일은 한 번 바뀐다 — CLAUDE.md 에 킷 블록이 병합되고, 보드 블록(BOARD:BEGIN)이 있는 문서에 보드가 덧붙는다. 적용 뒤 git diff --stat 의 변경 파일이 이 둘뿐인지 눈으로 본다.

$ knots-sync init --adopt --dry-run     # 목록 검토
$ knots-sync init --adopt               # 사람이 승인한 뒤
$ knots-sync doctor --check             # exit 0 이면 끝

옛 이름(harness-kit)이나 v1 으로 깐 리포는 init 이 아니라 update 로 옮긴다 → 옛 이름에서 옮기기.

올리기 · 되살리기 · 지우기

하고 싶은 것명령동작
새 판이 있나knots-sync outdated [--check]설치 · CLI · 소스 최신 태그를 비교. 소스에 닿지 못하면 "확인 못 함"과 exit 0. 기본 원격은 킷 저장소
킷을 새 판으로knots-sync update --dry-run → update(또는 /kns:update)고치지 않은 킷 파일은 바꾸고, 고친 파일은 <경로>.new 로 옆에 둔다. 충돌이 있으면 exit 4
지워진 킷 파일 되살리기knots-sync repair [--only missing,drifted,stale,merge]같은 판으로 되살린다. 고친 파일은 그대로 둔다
킷 걷어내기knots-sync uninstall --dry-run → uninstall --yes킷 소유이면서 고치지 않은 파일만 지운다. --keep-state · --keep-packs
Kiro 킷 스킬 올리기bash install-kiro.sh --force설치 기록의 폴더를 새 판으로

.new 병합은 diff -u <파일> <파일>.new 로 보고 필요한 줄만 원본에 옮긴 뒤 .new 를 지운다. 리포 .gitignore 가 *.new 를 무시하면 git status 에 안 보이니 find . -name '*.new' -not -path './.git/*' 로 센다. verify.sh --fast 가 남은 .new 를 경고한다.

설치 확인 목록

  • Claude Code: /plugin 에 kns. Codex: codex plugin list. Kiro: ls ~/.kiro/skills/ | grep kns-. 하네스를 다시 켰는가.
  • 리포: knots-sync doctor --check 가 exit 0 이고 drifted 0 · missing 0.
  • knots-sync list 가 스택 · 변형 · 하네스 · 모듈 · 이슈 키 · base 를 보여 준다.
  • bash scripts/verify.sh --fast 가 통과한다.
  • 에이전트 세션에서 /kns-harness 를 부르면 규칙 컨텍스트가 실린다.

회사 팩과 개인 층(선택)

킷 위에 층을 더 얹을 수 있다. 우선순위는 킷 → 회사 팩 → 프로젝트 → 개인 순이다.

  • 회사 팩 — 여러 리포가 같이 쓰는 규칙 · 훅 · 검사 묶음. knots-sync pack new <이름> --dir <경로> --from <파일>… 로 프로젝트 파일에서 골격을 만들고, knots-sync.json 의 packs 에 적은 뒤 knots-sync update --packs 로 받는다. 팩끼리 같은 파일 · 훅 id 를 가지면 멈추고 사람이 정한다(exit 4).
  • 개인 층 — .agents/local/(커밋 안 함)의 개인 스킬 · Kiro 규칙 · 개인 훅. knots-sync local sync 로 하네스 폴더에 놓는다. 공유 원본과 이름이 같으면 놓지 않는다. 개인 층은 roles · git.ide 만 덮을 수 있고 게이트 · 승인자 · 검증 · 위험 설정은 무시된다.
