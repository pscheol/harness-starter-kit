09 · 운영과 팀

배포 · 운영 · 지표 · 규칙 후보

병합한 Unit 을 배포하고, 배포 결과와 운영에서 잰 값을 리포에 남기고, 그 기록에서 다음 요구사항 · bug 이슈 · 규칙 변경을 연다. 킷은 운영 배포 명령을 직접 하지 않는다 — 배포 앞의 승인 검사와 배포 뒤의 결과 기록을 맡는다.

한 바퀴

설계 단계에서 미리 — design §13

배포 준비는 design 에서 시작한다. design 템플릿 §13 "배포 · 롤백" 이 비어 있으면 design 승인이 거부된다.

  • 13.1 배포 계획(필수) — 순서 · 방식(한 번에 · 단계적 · 기능 플래그) · 하위 호환 · 마이그레이션(되돌릴 수 없으면 risk: high) · 확인 신호(스모크 · 헬스 · 지표 기준값).
  • 13.2 롤백(필수) — 방법 · 판단 기준(숫자로, 예: 5xx 비율 1% 초과가 5분) · 롤백 뒤 데이터 · 시험(deploy.py run --env verify --rollback-test).
  • 13.3 운영 점검 — 로그(개인정보 · 비밀값 없음) · 지표와 대시보드 링크 · 알람 · SLO. 항목마다 체크 또는 "해당 없음: <이유>".
  • 13.4 인프라 — 인프라를 바꿀 때만.

배포하지 않는 변경(라이브러리 내부 · 문서)은 §13 전체를 "배포 없음: <이유>" 한 줄로 둔다.

배포 기록 — deploy plan

$ knots-sync deploy plan SHOP-21 SHOP-22 --env production [--tag v2.3.0]
# → .agents/docs/ops/deploys/<날짜>-<키>.md (state: planned)

포함 이슈의 design §13 을 모아 배포 기록 하나(= 배포 묶음 하나)를 만든다. 구간은 둘이다.

  • 계획 구간(PLAN:BEGIN~PLAN:END): §1 포함 Unit(design §13 sha · 병합 커밋), §4 롤백(시험 결과), §5 배포 점검, §6 검증(full · 품질 게이트 결과와 CI 링크). deploy 승인은 이 구간의 sha 에 묶인다.
  • 결과 구간(RESULT:BEGIN~RESULT:END): §7 단계별 시작 · 끝 · 결과 · 근거. deploy.py result 가 쓴다. 손으로 고치지 않는다. 결과를 써도 승인은 유지된다.

머리 state: planned → approved → deploying → succeeded | rolled-back | failed. CI 결과는 knots-sync deploy record <기록> --from-ci <URL|파일|폴더> 로 §6 에 넣는다.

deploy 게이트 — D1~D7

ID조건
D1 포함 이슈포함 이슈마다 done 통과
D2 계획 승인포함 이슈마다 design 승인이 유효(승인 sha = 현재)하고 §13.1 · §13.2 가 차 있다
D3 롤백§4 가 시험: passed 이고 검증(verification) 환경에서 돌았다. 아니면 승인하는 사람이 넣은 면제 사유(10자 이상) — 단 risk: high 는 면제 불가
D4 CI§6 이 full: passed 이고 그 sha 가 배포 커밋이며, 같은 실행의 품질 게이트가 passed
D5 점검표§5 의 모든 줄이 체크 또는 "해당 없음: <이유>"
D6 승인자approvers.deploy(없으면 git 사용자 누구나). risk: high 면 서로 다른 2명이 같은 계획 sha 를 승인
D7 검증 환경자동 검증 배포를 켰으면 그 커밋의 결과가 passed

예시 리포에서 아직 준비가 안 된 기록을 검사하면 막힌 조건이 한 줄씩 나온다.

실제 출력knots-sync deploy check .agents/docs/ops/deploys/2026-11-24-INT-7.md 
D1 포함 이슈: SHOP-21: done 게이트를 통과하지 않았다
D2 계획 승인: SHOP-21: design 승인이 valid 가 아니다(none)
D3 롤백: 시험 결과가 없다(시험: none) — risk: high 는 롤백 시험 면제가 없다
D4 CI: 기록 §6 에 full: passed 가 없다
D4 CI: 기록 §6 에 quality-gate: passed 가 없다
D7 검증 환경: 자동 검증 배포가 stopped 다
[exit 1]

조건이 다 맞으면 운영 담당이 승인한다 — 관리 페이지(PIN), 또는 사람 터미널:

$ knots-sync approve deploy:2026-12-01-INT-7 --gate deploy --phrase "10%부터 연다"
$ knots-sync approve deploy:2026-12-01-INT-7 --gate deploy --phrase "…" --waive-rollback "검증 환경에 PG 샌드박스가 없다. 플래그 끄기로 되돌린다"

승인 기록은 포함 이슈의 approvals.md 마다 같은 내용으로 덧붙는다. 에이전트가 기록에 쓴 면제 문장은 세지 않는다. 채팅의 "배포해"는 승인이 아니다.

운영 배포를 막는 자리

운영 배포 작업은 배포 명령 앞에 이 검사를 부른다. 승인이 없거나 오래됐으면 exit 1 로 배포가 멈춘다.

$ python3 scripts/harness/deploy.py check <기록> --require-approved
  • 킷 CI 템플릿의 deploy-production 작업(사람이 수동 실행, KNS_DEPLOY_RECORD 에 기록 경로)은 deploy.py run --env production --record "$KNS_DEPLOY_RECORD" 이고, run 이 이 검사를 먼저 한다. 명령은 .agents/deploy.json 의 commands(자리표 {env} · {sha} · {toSha} · {url}).
  • 자기 배포 시스템을 쓰는 팀은 그 시스템의 첫 단계에 같은 명령을 넣고, 배포 뒤 deploy.py result <기록> --from <deploy-result.json> 로 결과를 넣는다. deploy.json 에 production 이 있는데 CI 설정에서 이 명령을 못 찾으면 doctor 가 경고한다.

병합 뒤 검증 환경 자동 배포(선택)

.agents/deploy.json 의 autoVerify.enabled 를 켜면 base 브랜치 push 마다 CI 의 deploy-verify 작업이 deploy.py auto-verify 를 돈다: 검증 환경 배포 → 스모크 · 헬스 → E2E 한 번 → 롤백 시험(마지막 통과 sha 로 되돌렸다가 다시 배포). 하나라도 실패하면 되돌리고 failed. 결과는 .agents/reports/deploy/auto-verify-<sha>.json.

연속 2회 실패하면 멈춘다(status: stopped). 관리 페이지 홈 · 운영 화면에 "자동 검증 배포가 멈췄다"가 뜬다. 다시 돌리려면 사람이 플랫폼에서 파이프라인을 수동 실행하며 KNS_DEPLOY_RESUME=true 를 넣는다(옛 이름 HX_DEPLOY_RESUME 을 쓰던 CI 변수는 사람이 이름을 바꾼다).

운영 기록 — ops new

$ knots-sync ops new --topic payment-v2-week1 --from 2026-12-01 --to 2026-12-07
$ knots-sync ops check            # 형식 검사. 읽기는 knots-sync status --ops [--json]

자리는 .agents/docs/ops/records/<기간 끝 날>-<주제>.md. 주기 기록(배포 뒤 1주 · 매월)과 장애 기록이 같은 형식이다.

절내용
1. 목표 대비 실측Intent 의 SC- · 이슈의 NFR- 마다 목표 · 실측 · 판정(충족 · 미달) · 출처(대시보드 링크 · CI 산출물)
2. 전달 지표knots-sync metrics --fill <기록> 이 쓰는 구간(손으로 고치지 않는다)
3. 장애INC-n · 등급 · 날짜 — 감지 · 영향 · 원인 배포 · 조치 · 런북 · 후속 이슈
5. 다음 Intent 후보NX-n — 후보 · 근거(지표 행 · 장애) · 종류 · 접수

전달 지표 — metrics

다섯 지표를 git 기록 · approvals.md · 배포 기록의 CI 값에서만 계산한다. 사람이 적은 값은 쓰지 않는다.

지표계산
리드 타임Intent 접수 커밋(없으면 requirements 커밋) → 운영 배포 성공 기록의 끝 시각. 중앙값 · p85
배포 실패율운영 배포 중 rolled-back · failed 이거나 7일 안 장애의 원인 배포인 것 ÷ 운영 배포 수
복구 시간장애 후속 bug 이슈 접수 → 복구 배포 끝. 중앙값
승인 대기 시간문서를 in-review 로 바꾼 커밋 → 그 sha 의 approved 기록. 중앙값 · p85
재작업 비율병합 뒤 30일 안에 같은 파일을 다시 고친 fix/ 이슈가 병합된 비율. 게이트 돌려보냄(changes-requested) 평균도 함께
실제 출력knots-sync metrics(관리 페이지 예시 리포) 
| 지표 | 기준선 | 이 기간 | 계산 방법 |
|---|---|---|---|
| 리드 타임(시간, 중앙값) | 96.5 | — | none |
| 배포 실패율 | 0.12 | 1.0 | kit (기준선 git — 계산 방법 다름) |
| 복구 시간(시간, 중앙값) | 5.2 | — | none |
| 승인 대기 시간(시간, 중앙값) | — | — | unavailable |
| 재작업 비율 | 0.18 | 0.0 | kit (기준선 git — 계산 방법 다름) |
  • 기본 기간은 최근 30일. 결과는 .agents/reports/metrics/delivery-<끝 날짜>.json(커밋 안 함).
  • --baseline: 킷을 들인 커밋(lock 을 처음 더한 커밋) 앞 90일의 기준선을 .agents/docs/ops/metrics-baseline.json 에 쓴다(커밋함). 도입 전에는 배포 · 승인 기록이 없어 git 만으로 계산하고 method: git 으로 표시한다 — 위 출력의 "계산 방법 다름"이 그 뜻이다. 이미 있으면 --force 없이는 거부한다.
  • --verify-baseline: 같은 입력으로 다시 계산해 다르면 exit 1. CI 야간 full 이 부른다. Node 없는 CI 는 python3 scripts/harness/delivery_metrics.py.

규칙 후보 — rules

리뷰 · 승인 · 운영에서 사람이 고친 것 중 반복될 것을 모아 사람이 골라 규칙으로 올린다.

출처후보가 되는 조건
승인 기록changes-requested 에 - 규칙 후보: 예(관리 페이지 "수정 요청을 규칙 후보로 남깁니다" 또는 approve … --changes-requested --rule-candidate)
리뷰 처리수용한 지적 중 같은 점검 · 같은 규칙이 30일 안 이슈 2개 이상
운영 기록§6 배운 것 행
$ knots-sync rules candidates --since 30d   # 출처를 훑어 새 후보 파일(.agents/docs/rule-candidates/RC-<n>-<이름>.md)
$ knots-sync rules list
RC-1 proposed .agents/rules/payment.md 출처 1건 · 23일
$ knots-sync rules promote RC-1              # 사람 터미널. chore/RC-1-… 브랜치에 규칙 수정 + 후보 accepted
$ knots-sync rules reject RC-1 --reason "…"  # 사람 터미널. 후보 rejected

규칙 파일은 MR 로 바뀐다. 오래 머문 후보(14일 넘게 proposed)는 관리 페이지 처리할 일에 "RC-1 규칙 후보가 23일째 proposed"처럼 뜬다.

관리 페이지 운영 화면

위 모든 것은 관리 페이지 운영(S10) 화면에 읽기 전용으로 모인다: 배포 기록 · 장애 · 운영 기록 · 다음 요구사항 후보 · 전달 지표 · 자동 검증 배포 · 규칙 후보. 같은 데이터는 knots-sync status --ops --json.
