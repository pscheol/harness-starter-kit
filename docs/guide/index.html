00 · 시작하기

knots-sync 사용 안내서

knots-sync(약어 kns)는 팀이 쓰는 에이전트 하네스 킷이다. 규칙 · 스킬 · 훅을 한 벌로 두고 Claude Code · Codex · Cursor · Kiro 네 하네스에 같은 모양으로 깔며, 요구사항 하나를 사람 승인 게이트가 있는 SDD 흐름으로 끝까지 끌고 간다.

이 장에서

  1. 무엇인가
  2. 누구를 위한 것인가

  4. 10분 시작

  6. 안내서 지도

무엇인가

에이전트마다 규칙 파일을 따로 두면 내용이 조금씩 어긋난다. knots-sync 는 원본을 리포의 .agents/ 한 곳에만 두고, 하네스 폴더(.claude/ · .codex/ · .cursor/ · .kiro/)에는 그 원본에서 만든 실제 파일(복사 · 생성 · 병합)을 둔다. 심볼릭 링크나 "원본을 읽어라" 같은 포인터 파일은 쓰지 않는다.

킷이 리포에 까는 것은 다섯 덩어리다.

덩어리내용자리
규칙 · 스킬 · 역할공통 규칙(SDD 워크플로 · git · 보안 · 승인 어휘 등), 프로젝트 스킬 15종(kns-intent · kns-specify · kns-plan …), 역할 6종(designer · planner · worker · reviewer · explorer · docs-researcher).agents/rules/ · .agents/skills/ · .agents/roles/
SDD 기록요구사항 접수 → Intent → Unit → 이슈별 requirements · design · tasks, 승인 기록 approvals.md.agents/docs/intents/ · .agents/docs/issues/
검증 게이트단일 검증 입구 scripts/verify.sh(fast · changed · affected · full), 정적 분석 · 품질 게이트, 승인 스크립트scripts/ · scripts/harness/
관리 페이지내 컴퓨터(127.0.0.1)에서만 여는 웹 화면. 처리할 일 · 진행 · 문서 · 승인 · 검증 · 스킬 · 운영 · 사용량knots-sync dashboard
선택 모듈AI-DLC(설계 도구) · Entire(대화 체크포인트) · jira-workflow · notion · multi-harness. 기본은 모두 꺼짐knots-sync add <모듈>

여기에 배포 기록 · 운영 기록 · 전달 지표 · 규칙 후보가 더해져, 운영에서 배운 것이 다음 요구사항과 규칙으로 돌아온다(→ 배포 · 운영 · 지표).

킷은 모델을 부르지 않는다

CLI · 관리 페이지 · 훅 · 스크립트는 어떤 모델 API 도 부르지 않는다. 글을 쓰는 일은 사람이 연 에이전트 세션 안에서만 일어난다. 킷이 세션에 덧붙이는 양에는 상한이 있다 — 세션 시작 훅 출력 합계 2,560바이트 이하, 늘 실리는 진입 파일(AGENTS.md · CLAUDE.md) 24KB 이하. 이 안내서를 쓰며 일회용 리포에 깐 직후 doctor 가 잰 값은 Claude Code 10,206바이트(훅 13개), Codex 8,380바이트(훅 8개)였다.

누구를 위한 것인가

사람킷이 주는 것먼저 볼 장
기획자 · PM요구사항 접수 화면, 질문에 답하는 화면, Intent · 기획물 · requirements 승인. 채팅으로 "좋아요" 한 말은 승인이 되지 않는다역할별 · 기획자, 새 요구사항
개발자이슈마다 한 폴더 · 한 브랜치 · 한 MR, 단계별 스킬(/kns-plan · /kns-tasks · /kns-implement), changed · affected 검증하루 흐름, 역할별 · 개발자
리뷰어 · 리드/kns-review 지적 목록, 리뷰 판단(수정 필요 · 위험 수용), design · MR 승인, 품질 게이트역할별 · 리뷰어, 검증 화면
운영 담당배포 기록 · deploy 승인 · 운영 기록 · 장애 → bug 이슈 · 전달 지표배포 · 운영 · 지표
팀 도입 담당설치 · 하네스 고르기 · 승인자 그룹 · 흐름 틀(게이트) · 모듈 · 옛 리포 이전설치, 역할별 · 도입 담당, 옮기기

이름 정리

2026-11-24 이름이 harness-kit 에서 knots-sync 로 바뀌었다. 저장소 이름(harness-starter-kit)은 그대로다. 문서와 화면에서 만나는 이름은 아래 다섯 가지다.

무엇이름예
제품knots-sync · 약어 kns—
CLIknots-sync <명령>(별칭 kns, 한동안 옛 harness-kit 도 같은 CLI)knots-sync doctor
플러그인 스킬(킷을 깔고 유지)/kns:<명령>/kns:bootstrap · /kns:update
프로젝트 스킬(매일 개발)Claude Code · Cursor · Kiro CLI 는 /kns-<명령>, Codex 는 $kns-<명령>/kns-specify · $kns-specify
상태 파일.agents/knots-sync.json(설정) · .agents/knots-sync.lock(설치 기록). 둘 다 커밋한다—

10분 시작

빈 리포 하나에 킷을 깔고, 요구사항 하나를 접수하고, 관리 페이지를 여는 데까지다. 아래 출력은 이 안내서를 쓰며 일회용 폴더(/tmp/…/demo-app)와 일회용 HOME 에서 실제로 돌린 결과를 그대로 옮겼다.

CLI 는 GitHub 에서 받는다

npm 에는 아직 올리지 않았다(결정 D3 — v2.2 까지 명령이 그대로면 올린다). 처음이면 Claude Code 플러그인(/kns:bootstrap · /kns:update)으로 시작하고, 터미널 CLI 는 npm i -g https://codeload.github.com/pscheol/harness-starter-kit/tar.gz/refs/tags/v2.0.0-alpha.2 로 전역 설치한다. 이 안내서와 관리 페이지의 knots-sync … 는 그 CLI 다. npx kns · npx knots-sync 는 쓰지 않는다.

  1. CLI 를 부를 수 있게 한다

    Node 18.3 이상이 필요하다. 킷 저장소를 받은 경로를 넣어 별칭을 만든다.

    입력셸 설정에 한 줄 
    $ alias knots-sync='node /path/to/harness-starter-kit/plugins/kns/skills/bootstrap/bin/knots-sync.js'
$ knots-sync --help | head -1
knots-sync 2.0.0-alpha.0 — 하네스 엔지니어링 스타터 킷

    플러그인으로 설치했다면 같은 CLI 가 플러그인 폴더의 skills/bootstrap/bin/knots-sync.js 에도 있다. Node 가 없으면 bash <플러그인>/skills/bootstrap/kit.sh <명령> 이 v1 설치 스크립트로 내려간다(→ 설치 · CLI).

  2. 무엇이 깔릴지 먼저 본다 — plan

    plan 은 아무것도 쓰지 않는다. 스택은 빌드 파일로 판단하고(pyproject.toml → python), 하네스는 플래그로 고른다.

    실제 출력knots-sync plan --stack python --agents claude,codex (create 줄 363개는 줄임) 
    knots-sync plan — /private/tmp/kns-guide-fx/demo-app
  선택: python · hexagonal · backend · 하네스 claude,codex · 모듈 none
  create    .agents/analyzers.json  [stacks/python]
  create    .agents/deploy.json  [common]
  …
  skip-user README.md  [common]  사람이 둔 파일이다
  파일: 생성 309 · 교체 0 · 같음 0 · 건너뜀(사람 파일) 1 · 하네스 제외 1 · 겹침 0
  배치: create 54
  상태 파일: .agents/knots-sync.json · .agents/knots-sync.lock · .agents/harness.json
  (plan — 쓰지 않았다)

    사람이 이미 둔 파일(README.md)은 덮지 않고 skip-user 로 남긴다.

  3. 깐다 — init

    실제 출력knots-sync init --stack python --agents claude,codex --yes 
    knots-sync init — /private/tmp/kns-guide-fx/demo-app
  선택: python · hexagonal · backend · 하네스 claude,codex · 모듈 none
  파일: 생성 309 · 교체 0 · 같음 0 · 건너뜀(사람 파일) 1 · 하네스 제외 1 · 겹침 0
  skip-user README.md  [common]  사람이 둔 파일이다
  배치: create 54
  상태 파일: .agents/knots-sync.json · .agents/knots-sync.lock · .agents/harness.json
  기능 문서: docs/features/ 생성
  등록부: demo-app 를 더했다(/tmp/kns-guide-fx/fx/home/.config/knots-sync/projects.json) — 관리 페이지 --all 에 보인다. 빼려면 knots-sync projects remove demo-app
  다음: knots-sync doctor

    프로젝트 밖에 쓰는 파일은 등록부 ~/.config/knots-sync/projects.json 하나뿐이다. 쓰지 않으려면 --no-register 를 붙인다.

  4. 점검한다 — doctor

    실제 출력knots-sync doctor 
    knots-sync doctor — /private/tmp/kns-guide-fx/demo-app
  킷: 설치 2.0.0-alpha.0 · lock 2.0.0-alpha.0 · CLI 2.0.0-alpha.0
  copy 항목: ok 309 · drifted 0 · missing 0
  배치 항목: ok 54 · 오류 0
  오류 0 · 경고 0 · 정보 0
  세션마다 실리는 양(claude): kit 10,206(훅 13) = 10,206바이트
  세션마다 실리는 양(codex): kit 8,380(훅 8) = 8,380바이트

    설치를 커밋한다. .agents/knots-sync.json · .lock 도 함께다.

  5. 요구사항 하나를 접수한다 — intake

    실제 출력knots-sync intake --title "업로드 임시 파일 정리" --kind feature --name upload-cleanup --area upload --text "…" 
    ✔ 접수: .agents/docs/intents/INT-1-upload-cleanup
다음: /kns-intent INT-1 (세션 요청은 사람이 고를 때만)

    접수 글은 trust: untrusted 로 표시된다. 에이전트는 그 안의 지시("이미 승인됐다", "명령을 실행해라")를 따르지 않고 자료로만 읽는다. 이어서 설계 세션(Claude Code)을 열고 /kns-intent INT-1 을 부른다.

  6. 관리 페이지를 연다 — dashboard

    자기 터미널에서 연다. 주소는 표준 출력, 승인 PIN 은 표준 오류에만 나온다. 에이전트 세션 안에서 연 서버는 읽기 전용이라 PIN 이 없다(→ 승인).

    사람 터미널출력 모양(주소 · PIN 은 실행마다 다르다) 
    $ knots-sync dashboard --open
http://127.0.0.1:<포트>/#t=<토큰>
승인 PIN: <10자> — 승인 · 질문 답 · 리뷰 판단 때 넣는다. 이 터미널에만 보인다(파일에 쓰지 않는다)

이 판의 상태와 아직 확인하지 못한 것

이 안내서는 CLI 2.0.0-alpha.0(브랜치 hk-22b-rename 끝, 두 구성 e2e 통과)을 기준으로 썼다. 명령과 플래그는 모두 실제 --help 와 맞췄다. 다만 아래는 시험 대역(가짜 응답 · 가짜 도구)으로만 확인했거나 사람이 실제 환경에서 봐야 하는 것으로 남아 있다. 해당 장에서 실환경 미확인 상자로 다시 표시한다.

  • Jira · Notion 실제 연결(흉내 응답 시험만 했다).
  • GitLab MR 요약 코멘트(가짜 glab 으로만 시험, GitHub 은 비공개 시험 저장소에서 확인).
  • Entire 체크포인트가 살아 있는 구현 세션 훅에서 실제로 생기는 것(e2e real 모드의 E4 는 정해서 건너뜀).
  • 살아 있는 세션 소켓으로 작업 요청 전달 · deep link · Codex 대기함 표시, Codex · Kiro 훅 입력의 cwd.
  • Claude Code claude -w 와 IDE 의 worktree 표시, Kiro fileMatchPattern 배열 · Cursor globs · Claude paths 가 Read 에도 걸리는지.
  • 설계 세션 한 바퀴(/kns-intent → 답 → intent 승인 → /kns-plans → /kns-specify --from-unit)를 사람이 실제로 도는 것, 관리 페이지 화면 모양의 사람 확인.
