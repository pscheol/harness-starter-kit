역할별 활용 가이드

같은 킷을 쓰지만 사람마다 하는 일이 다르다. 이 장은 다섯 역할 — 기획자 · PM, 개발자, 리뷰어 · 리드, 운영 담당, 팀 도입 담당 — 이 하루와 단계마다 무엇을 하고, 어느 화면 · 명령을 쓰고, 무엇을 사람이 승인해야 하며 왜 그런지를 적는다.

게이트 × 역할 한눈에

승인자 그룹은 knots-sync.json 의 approvers · groups 로 정한다. 아래는 설계서의 예시 배치다. 그룹을 정하지 않으면 리포의 git 사용자 누구나 승인한다.

승인이 사람 몫인 이유

게이트는 "다음 단계로 가도 된다"는 책임을 사람이 지는 자리다. 에이전트가 쓴 문서를 에이전트가 승인하면 게이트가 없는 것과 같다. 그래서 승인은 네 경로(관리 페이지 + PIN, 사람 터미널 approve, Jira 사람 전이, AI-DLC 확인 훅)로만 생기고, 승인은 문서의 sha256 에 묶여 문서가 바뀌면 다시 받아야 한다. 채팅에서 "좋아", "머지해", "배포해"라고 한 말은 어떤 말이든 승인이 아니다 — 대화의 지시로 커밋 · push 는 할 수 있어도 게이트 조건을 대신하지 못한다.

기획자 · PM

요구사항을 넣고, 질문에 답하고, Intent · 기획물 · requirements 를 승인하고, 완료를 확인한다. 에이전트 세션을 열지 않아도 대부분 관리 페이지에서 끝난다.

하루

  • 아침 — 관리 페이지 홈의 처리할 일에서 "내가 할 것"을 고른다. 내 차례 승인 · 내 직무의 열린 질문이 먼저 보인다.
  • 새 요구사항이 오면 — 새 요구사항에 제목 · 종류 · 본문 · 첨부(기획서 · 캡처)를 넣고 접수한다. Jira 에픽 · Notion 페이지라면 터미널에서 knots-sync intake --from jira:<키> · --from notion:<URL>. 접수 뒤 "설계 세션에 요청"을 고르거나 개발자에게 알린다.
  • 질문이 오면 — 질문 화면에서 권장안과 선택지별 영향을 읽고 고른다. 모르면 "other" 에 메모. 회의로 정할 일이면 몹 정리(knots-sync mob start)를 연다.
  • 승인 요청이 오면 — 문서를 끝까지 읽고 승인 문구를 남겨 승인하거나 "수정 요청"을 누른다. 같은 지적이 반복되면 "수정 요청을 규칙 후보로 남깁니다"를 켠다.
  • 끝 — 병합된 이슈를 검수하고 done 을 승인한다.

개발자

설계 · 구현 세션을 열어 스킬을 부르고, codebase · design · tasks 를 승인하고, 검증을 돌려 MR 을 연다.

하루

  1. 관리 페이지 홈 또는 knots-sync status 로 처리할 일을 본다. 세션 목록에서 내 세션이 무엇을 들고 있는지 본다.
  2. 작업 시작: 하네스를 열고 /kns-harness(규칙 컨텍스트). 같은 리포에서 다른 세션이 파일을 쓰고 있으면 python3 scripts/harness/worktree.py new <키> --open.
  3. 단계 스킬을 부른다(아래 표). 세션이 in-review 로 올린 문서는 내가 읽고 승인한다 — 세션에게 "승인해"라고 하지 않는다.
  4. Bolt 마다 bash scripts/verify.sh, MR 전 bash scripts/verify.sh --affected. full 은 CI 에 맡긴다.
  5. 끝: 커밋 · push. worktree 를 썼으면 worktree.py done <키> 로 바로 지운다.

막히는 것들

에이전트 세션의 verify.sh --full, base 브랜치 직접 push, 이슈 폴더 없이 <종류>/<키>-<이름> 브랜치 push, 승인 없이 status: approved · state: completed 로 바꾸는 쓰기, approvals.md 수정. 모두 의도한 막힘이다. 사람이 자기 터미널에서 할 일(승인 · full)은 자기 터미널에서 한다.

리뷰어 · 리드

리뷰 세션으로 MR 을 읽히고, 지적마다 수정 · 위험 수용을 정하고, mr 을 승인한다. 설계 승인에도 같이 들어간다.

MR 하나를 볼 때

  1. 리뷰 세션을 연다

    기본 배치는 Codex(roles.review.harness). $kns-review !123(GitHub 은 #45). 세션은 체크아웃하지 않고 원격 diff · SDD 세 문서 · 규칙 · 스캔을 읽어 지적을 쓴다. 점검표: 요구 커버리지(RV-COV) · 설계 준수(RV-ADR) · 규칙(RV-RULE) · 경계 · 실패 경로(RV-EDGE) · 시험(RV-TEST) · 스캔 해석(RV-SCAN) · 문서(RV-DOC).

  2. 지적을 판단한다

    관리 페이지 이슈 → review 또는 knots-sync review decide <키> F-n --fix|--accept-risk --reason "…". 수정 필요는 구현 세션이 고치고 리뷰를 다시 돈다. 위험 수용은 approvals.md 에 남는다.

  3. 품질 게이트를 본다

    검증 화면 · knots-sync quality --findings --new. 새 CRITICAL · HIGH, 새 코드 중복률, 복잡도. 기준은 .agents/quality-gate.json.

  4. mr 을 승인한다

    같은 head 의 affected 통과 · 품질 게이트 통과 · 열린 CRITICAL/HIGH 0 이 아니면 승인 자체가 거부된다(422). diff 가 risk.highPaths 에 걸리면 다른 승인자 1명이 더 필요하다.

리드로서 주기적으로

  • 규칙 후보 정리: knots-sync rules candidates → 고른 것은 rules promote RC-n(MR), 아닌 것은 rules reject RC-n --reason. 14일 넘게 머문 후보가 홈에 뜬다.
  • 스킬 지도(.agents/skill-map.json) 관리: 팀이 단계마다 어떤 스킬을 쓸지. 스킬 화면에서 이름 겹침 · 미분류를 본다.
  • 품질 기준선(.agents/quality-baseline.json) 갱신은 사람만 한다. 에이전트는 이 파일을 쓰지 못한다.
MR 은 base 의 검증으로 판정한다

MR 이 verify.sh · scripts/harness/ · 검증 설정을 고쳐도 판정은 base 쪽 것으로 한다. 검증을 느슨하게 바꾸는 변경이 자기 자신을 통과시키지 못하게 하려는 것이다. CI 진입 파일은 코드 소유자 승인을 건다.

운영 담당

배포 기록을 검토하고 deploy 를 승인하고, 배포 뒤 운영 기록을 쓴다.

언제하는 일어디서
design 승인 때§13 배포 계획 · 롤백 판단 기준(숫자) · 운영 점검을 본다. 비어 있으면 design 이 승인되지 않는다이슈 → design
배포 전knots-sync deploy plan <키…> → deploy check <기록> 로 D1~D7 확인 → 롤백 시험 · CI full · 점검표운영 화면 · 터미널
승인관리 페이지(PIN) 또는 knots-sync approve deploy:<기록> --gate deploy --phrase "…". 롤백 시험을 못 했으면 --waive-rollback "<사유>"(high 는 불가)사람 터미널
배포배포 시스템이 deploy.py check --require-approved 를 통과한 뒤 배포 → deploy.py resultCI · 배포 시스템
자동 검증 배포가 멈추면원인을 고친 뒤 파이프라인을 수동 실행하며 KNS_DEPLOY_RESUME=trueCI 플랫폼
배포 뒤 1주 · 매월 · 장애knots-sync ops new --topic … 로 운영 기록. 목표 대비 실측 · 장애 · 다음 후보 · 배운 것리포
장애가 나면운영 기록에 INC 를 쓰고 intake --kind bug --from ops:<기록>#INC-n터미널
달마다knots-sync metrics 로 리드 타임 · 배포 실패율 · 복구 시간 · 승인 대기 · 재작업을 기준선과 비교운영 화면 · 터미널
deploy 승인이 사람 몫인 이유

운영 배포는 되돌리기 가장 비싼 단계다. 승인은 배포 기록의 계획 구간 sha 에 묶이고, 운영 배포 작업이 배포 직전에 그 승인을 다시 검사한다. 계획이 바뀌면 승인은 오래된 것이 된다. 롤백 시험 면제는 승인하는 사람만 넣을 수 있다.

팀 도입 담당

킷을 리포에 들이고 팀 규칙을 설정한다. 한 번 하고 끝나는 일과, 판을 올릴 때마다 하는 일이 있다.

처음 들일 때

  1. 하네스와 역할을 정한다

    팀이 실제로 쓰는 하네스만 고른다(--agents). 역할 배치(roles)의 기본은 설계 · 구현 Claude Code, 리뷰 Codex, 문서 Kiro 다. 구현과 리뷰를 서로 다른 하네스로 나누는 것이 기본값이다.

  2. 설치하고 숫자를 잰다

    plan → init(손으로 만든 하네스가 있으면 --adopt) → doctor. "세션마다 실리는 양"을 기록해 둔다 — 도입 전후 값을 MR 설명에 나란히 적는다. 진입 파일(AGENTS.md + CLAUDE.md)은 24KB 이하가 목표다.

  3. 승인자 그룹을 정한다

    knots-sync.json 의 groups(git user.email 목록)와 approvers(게이트 → 그룹 · 이메일). 정하지 않으면 git 사용자 누구나 승인한다.

  4. 흐름 틀과 위험 경로

    하한 넷 밖의 게이트(codebase · intent · plans · tasks · deploy)를 knots-sync flow gates 로 켜고 끈다. risk.highPaths(인증 · 결제 · 마이그레이션 경로)와 risk.highApprovals(기본 2)를 정한다 — 프로젝트는 더 엄하게만 바꿀 수 있다.

  5. 검증 · CI · 브랜치 보호

    bash scripts/install-git-hooks.sh. 원격 CI 를 쓰기로 했으면 knots-sync add ci 로 진입 파일(.gitlab-ci.yml · .github/)을 깔고 fast · affected · full 을 켠다 — 깔면 다음 push 부터 파이프라인이 돈다(→ ci 모듈). 팀이 만든 .gitlab-ci.yml 이 있으면 거기에 ci/knots-sync.gitlab-ci.yml include 를 더한다. 서버 쪽 base 브랜치 보호는 사람이 켠다(doctor 가 안내). 정적 분석기는 .agents/analyzers.json, 품질 기준은 quality-gate.json.

  6. 모듈을 정한다

    AI-DLC · Entire 는 켜기 전에 세션 적재량과 push 정책을 보고 정한다(→ AI-DLC 언제 쓰나). Jira 를 쓰면 jira-workflow + /kns:jira-setup. 원격 CI 를 쓰면 ci. 결정은 ADR(.agents/docs/decisions/)로 남긴다.

  7. 기준선을 남긴다

    knots-sync metrics --baseline — 도입 커밋 앞 90일의 전달 지표. 나중에 "킷이 도움이 됐나"를 같은 계산으로 비교한다.

판을 올릴 때마다

  • knots-sync outdated --check → update --dry-run 목록을 MR 로 검토 → 사람 승인 → update → .new 병합 → doctor --check exit 0 → CI full → 커밋 하나.
  • 사람마다 플러그인을 다시 설치하게 안내한다(/plugin install kns@knots-sync, Kiro 는 install-kiro.sh --force).
  • 회사 팩을 쓰면 update --packs.

각자 컴퓨터에서 정하는 것(커밋하지 않음)

  • 대화 기록 읽기(사용량 · 프롬프트 기록): 기본 꺼짐. 켜려면 각자 ~/.config/knots-sync/config.json 에 "history": "on".
  • 개인 스킬 · 훅: .agents/local/ 에 두고 knots-sync local sync. 게이트 · 승인자 · 검증 설정은 개인 층이 바꾸지 못한다.
  • IDE: git.ide(code · idea)는 개인 층에서 덮을 수 있다.
도입 담당이 지켜볼 숫자

킷 자체는 모델을 부르지 않지만, 하네스 폴더에 깔리는 스킬 설명 · 역할 · 규칙은 세션마다 실린다. doctor 의 "세션마다 실리는 양"과 관리 페이지 하네스 화면의 "킷이 덧붙인 토큰"(세션 시작 평균 / 2,560바이트)을 도입 전후로 적는다. 늘어난 값은 사람이 받아들인 뒤 쓴다.
