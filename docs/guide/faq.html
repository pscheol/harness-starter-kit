12 · 옮기기와 도움

문제 해결 · FAQ

자주 막히는 자리와 이유다. 대부분은 의도한 막힘이고, 메시지가 다음 할 일을 알려 준다. 막히면 먼저 knots-sync doctor 와 종료 코드를 본다.

승인 · 관리 페이지

관리 페이지에 승인 단추가 꺼져 있다 / "읽기 전용"이 뜬다

서버를 에이전트 세션 안에서 열었다(판정: CLAUDECODE=1 같은 하네스 변수나 부모 프로세스). 그 서버는 PIN 을 만들지 않고 승인 · 답 · 리뷰 판단 · 작업 요청을 끈다. 자기 터미널에서 knots-sync dashboard 를 다시 연다. 같은 리포에 서버가 떠 있으면 새로 열지 않고 그 주소를 내니, 먼저 띄운 서버를 닫는다. 이 동작을 우회하는 방법(부모 프로세스 끊기 · 환경 변수 바꾸기)은 쓰지 않는다 — 에이전트가 스스로 승인하지 못하게 하는 장치다.

PIN 이 어디 있나

서버를 연 터미널의 표준 오류에 한 번 나온다(승인 PIN: … — 이 터미널에만 보인다). 파일 · 로그에 없다. 5번 틀리면 그 서버가 끝날 때까지 PIN API 가 막힌다 — 서버를 다시 연다.

승인하면 403 · 409 · 422 가 난다

응답뜻할 일
403 not_an_approver내 git user.email 이 그 게이트의 승인자 그룹에 없다하네스 화면의 승인 권한 확인. 그룹은 knots-sync.json 의 groups
403 pin_required · pin_locked · read_onlyPIN 없음 · 5회 실패 · 읽기 전용 서버위 두 질문
409 doc_changed화면을 연 뒤 문서가 바뀌었다다시 읽고 승인
409(이미 승인)같은 sha 로 이미 approved 기록이 있다할 일 없음
422[NEEDS CLARIFICATION 표지가 남았거나 앞 게이트 · MR 조건이 안 맞는다패널의 미충족 줄을 본다(예: "같은 HEAD · 깨끗한 트리의 affected 검증 통과 기록이 없다")

에이전트에게 "승인해"라고 했는데 승인되지 않았다

맞다. 채팅의 말은 어떤 말이든 승인이 아니다. 에이전트는 approvals.md 를 쓰지 못하고, knots-sync approve 는 에이전트 세션에서 exit 3 이다. 승인은 사람이 관리 페이지(PIN)나 자기 터미널에서 한다.

승인했는데 다시 "승인 대기"가 됐다

승인 뒤 문서가 바뀌어 승인이 오래된(stale) 것이 됐다. 승인은 문서 sha256 에 묶인다(status · state 줄만 바뀐 것은 셈하지 않는다). 다시 읽고 승인한다. Intent 는 intent.md · units.json 둘 다 본다.

종료 코드

코드흔한 원인과 할 일
1검사 문제. doctor --check 오류, deploy check 조건, 비밀값이 든 접수, 기준선 불일치. 출력 줄이 무엇이 틀렸는지 말한다
2사용법. 명령 · 플래그 철자(knots-sync <명령> --help). 참고로 worktree 는 CLI 명령이 아니라 python3 scripts/harness/worktree.py 다
3리포 상태. 에이전트 세션에서 사람 전용 명령, TTY 가 아님. 자기 터미널에서 다시
4사람 판단 필요. update 충돌(.new), remove · uninstall 이 고친 파일을 남김, 외부 도구 판이 범위 밖(--allow-unverified), 이미 가져온 출처의 diff(--yes)
5실행 환경. 외부 도구 없음(설치 안내를 따른다), 포트 사용 중, Node 없이 CLI 전용 명령

설치 · 업데이트

/kns:bootstrap 이 보이지 않는다

플러그인 · 스킬 목록은 세션 시작 때 읽힌다. 하네스를 다시 켠다. Kiro 는 ~/.kiro/skills/kns-bootstrap/SKILL.md 가 있는지(한 겹 더 감싼 skills/kns/skills/… 는 인식되지 않는다) 본다.

npx knots-sync · npx kns 가 이상한 패키지를 받는다

아직 npm 에 올리지 않았고, npm 의 kns 는 다른 사람의 패키지다. npm i -g https://codeload.github.com/pscheol/harness-starter-kit/tar.gz/refs/tags/v2.0.0-alpha.3 로 전역 설치해 knots-sync <명령> 으로 부르거나, 한 번만 쓸 때는 npx -y github:pscheol/harness-starter-kit#v2.0.0-alpha.3 <명령> 처럼 GitHub 에서 태그를 고정해 부른다(→ 설치 · CLI). npm i -g github:… 는 npm 11 에서 명령 링크가 깨지니 쓰지 않는다.

Node 를 지정했는데 "명령을 찾을 수 없다" · exit 126

asdf · nvm 같은 버전 관리자의 shim 은 HOME 을 바꾸면(일회용 HOME 시험) 실제 node 를 못 찾는다. 실제 실행 파일 경로(asdf which node 등)로 부른다.

update 뒤 .new 파일이 생겼다

사람이 고친 킷 파일의 새 판이다. diff -u <파일> <파일>.new 로 보고 필요한 줄만 옮긴 뒤 .new 를 지운다. 계속 내 판을 쓰고 킷 판을 받지 않으려면 update --forget <경로>. .gitignore 가 *.new 를 숨기면 find . -name '*.new' -not -path './.git/*'.

하네스 폴더 파일을 고쳤더니 되돌아간다 / drifted 가 뜬다

하네스 폴더(.claude/skills · .cursor/commands …)는 원본에서 만든 결과다. 원본(.agents/rules · .agents/skills · .agents/roles)을 고치고 knots-sync repair(Node 없으면 python3 scripts/harness/projection.py sync). 배치 검사(verify.sh --fast)가 어긋남을 알린다. 나만 쓰는 스킬은 .agents/local/ + local sync.

doctor 가 legacy-names 를 알린다

옛 이름(harness-kit) 상태 파일을 읽었다. knots-sync update 가 새 이름으로 옮긴다(→ 옮기기).

검증 · 커밋

에이전트가 verify.sh --full 을 못 돌린다

의도한 막힘이다. full 은 CI 몫이다. 에이전트는 MR 전에 --affected 를 쓴다. 사람은 자기 터미널에서 full 을 돌릴 수 있다.

push 가 막힌다

세 경우다. ① 브랜치 이름이 <종류>/<키>-<이름> 인데 커밋에 그 키의 이슈 폴더가 없다 → 이슈 폴더를 커밋한다. ② 에이전트 세션이 base 브랜치로 push → 이슈 브랜치로. ③ 서버 보호 브랜치.

MR 승인이 "affected 검증 통과 기록이 없다"로 막힌다

mr 게이트는 같은 head · 깨끗한 작업 트리의 affected 검증 통과 기록을 본다. 마지막 커밋 뒤 bash scripts/verify.sh --affected 를 다시 돌린다. 열린 CRITICAL · HIGH 리뷰 지적, 품질 게이트 실패도 같은 자리에서 막는다.

작은 수정인데 "이슈가 필요하다"로 실패한다

trivial 판정(바뀐 줄 20 이하, 새 · 지운 파일 0, lock 파일 변경 0, 위험 경로 0)을 넘었다. 메시지가 기준을 말한다("바뀐 줄 57 > 20"). 이슈를 연다.

세션 · 토큰

킷을 깔았더니 토큰이 늘었나

킷 자체(CLI · 관리 페이지 · 훅 · 스크립트)는 모델을 부르지 않는다. 늘 수 있는 것은 세션마다 실리는 글(스킬 설명 · 역할 · 진입 파일 · 규칙)과 세션 시작 훅 출력이다. doctor 의 "세션마다 실리는 양"과 관리 페이지 하네스 화면의 "킷이 덧붙인 토큰"(세션 시작 평균 / 2,560바이트 상한)으로 잰다. 깐 직후 일회용 리포의 값은 Claude Code 10,206바이트(파일 23 · 훅 13), Codex 8,380바이트였다. AI-DLC 를 켜면 약 73KB 가 더 실린다.

사용량 화면이 비어 있다

대화 기록 읽기는 기본 꺼짐이다. 각자 ~/.config/knots-sync/config.json 에 "history": "on". 켜도 복사본을 남기지 않고 내보내기 · 커밋 · 세션 요청에 넣지 않는다. Kiro 는 기록 위치를 아직 읽지 못한다("자료 없음").

세션 요청이 세션에 안 간다

세션 등록(knots-sync sessions)에서 그 세션이 살아 있고 수신함이 있는지 본다. 없으면 대기함에 쌓이고 다음 세션 시작 · 프롬프트 때 한 줄로 보인다. 에이전트 세션 안에서는 dispatch 가 막힌다.

세션 연결 쪽

살아 있는 세션 소켓 전달 · deep link · Codex 대기함 표시, Codex · Kiro 훅 입력의 cwd 는 사람이 실제 세션에서 확인해야 할 항목이다. 이상하면 대기함(dispatch list)을 쓴다.

worktree

worktree 를 언제 만드나

같은 리포에서 동시에 파일을 쓰는 세션이 둘 이상일 때만. 리포당 3개까지, 자리는 리포 옆 ../<리포>.worktrees/<키>-<이름>/, 끝나면 바로 worktree.py done <키>. 끝의 정의는 변경 없음 + push 안 된 커밋 0 + 브랜치 병합. worktree.py gc 가 정리 대상을 보이고 --apply 로 지운다(사람이 실행).

submodule 이 있는 리포

상위 리포는 worktree 로 만들지 않는다. 도메인 리포 단위로만(worktree.py new <키> --domain <경로>).
