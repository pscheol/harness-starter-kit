## 2. 요구사항

### R1 affected 레벨

- R1.1 `verify.sh --affected`를 부르면, 게이트는 `git merge-base HEAD origin/<git.base>`부터 HEAD까지 바뀐 파일과 작업 트리의 변경(색인·미색인·추적 안 된 파일, ignore 제외)을 합쳐 변경 집합으로 삼는다.
- R1.2 게이트는 변경 파일마다 스택별 규칙(3.1)으로 모듈을 정하고, 그 모듈을 쓰는 모듈을 전이적으로 더한다.
- R1.3 게이트는 고른 모듈의 검사만 돌린다. 프로젝트 전체 명령(`./gradlew check`, `pnpm -r test`, `go test ./...`)은 빌드 계약 파일이 바뀐 경우에만 쓴다.
- R1.4 모듈을 정하지 못한 파일이 있으면, 게이트는 그 파일이 속한 단위(`.agents/harness.json`이 있는 폴더)의 검사로 넓히고 넓힌 이유를 결과에 남긴다. full로 올리지 않는다.
- R1.5 `--affected --plan`이면 게이트는 명령 목록만 JSON으로 출력하고 아무것도 실행하지 않는다.
- R1.6 knots 사본에서 파일 하나를 바꾼 작업의 affected 검증은 15분 안에 끝난다.

### R2 에이전트 세션의 full 차단

- R2.1 에이전트 세션의 셸 도구 명령에 `verify.sh`와 `--full`이 함께 있거나 `HARNESS_VERIFY_LEVEL=full`이 있으면, PreToolUse 훅은 그 명령을 막고(exit 2) 3.2의 안내를 stderr로 낸다.
- R2.2 사람 터미널과 CI에서 부른 `verify.sh --full`은 지금처럼 돈다.
- R2.3 `.agents/harness-kit.json`의 `verify.fullOnlyInCI`가 `false`면 훅은 막지 않는다. 값이 없으면 `true`로 본다.
- R2.4 훅이 명령을 해석하지 못하면(JSON 파싱 실패, `tool_input.command` 없음) 통과시킨다. 셸 도구가 아닌 호출은 보지 않는다.

### R3 테스트를 못 찾을 때

- R3.1 changed 레벨이 코드 파일에 연결된 테스트를 찾지 못하면, 게이트는 그 파일이 속한 모듈 하나의 테스트 명령을 더한다(모듈을 쓰는 모듈은 더하지 않는다).
- R3.2 모듈 테스트도 없거나 실행된 테스트가 0개면, 게이트는 그 파일을 `unverified`로 보고하고 상태 `incomplete`, exit 2로 끝낸다.
- R3.3 게이트 출력·권고 문구에 full을 권하는 문장이 없다.

### R4 다층 리포 상위 게이트

- R4.1 루트 게이트를 changed·affected로 부르면, 게이트는 변경이 있는 도메인의 게이트만 부른다.
- R4.2 도메인 변경은 다음 중 하나로 판정한다: 루트 diff의 submodule 포인터 변경, submodule 작업 트리 변경, submodule HEAD에 원격 base에 없는 커밋, 도메인 경로 아래 루트 파일 변경.
- R4.3 부르지 않은 도메인은 `↷ <id> 건너뜀 — 변경 없음` 한 줄로 출력한다.
- R4.4 fast는 모든 도메인을, full은 지금처럼 모든 도메인을 부른다.

### R5 실행 기록

- R5.1 `verify.sh`는 레벨과 상관없이 끝날 때 `.agents/state/verify-last.json`을 원자적으로 쓴다(임시 파일 → rename).
- R5.2 기록에는 단계마다 명령·시작 시각·걸린 시간(ms)·exit code·상태가 있다.
- R5.3 `.agents/state/`는 `.gitignore`에 있다.

### R6 템플릿 문구

- R6.1 킷 템플릿에서 에이전트에게 full을 지시·권고하는 문장은 0개다(CI 템플릿과 `verification-ladder.md`의 레벨 정의 행 제외).
- R6.2 tasks·design 템플릿의 "full 선택/이유" 칸은 "affected 결과 · CI full 링크"가 된다.

### R7 이슈 단위 SDD

- R7.1 `scripts/new-feature.sh <이슈키> <이름>`은 `.agents/docs/issues/<이슈키>-<이름>/requirements.md`를 만든다.
- R7.2 `scripts/new-feature.sh --next <이름>`은 `issueKey.source`가 `kit`일 때 `<prefix>-<N>` 키를 만든다. N은 3.7.3의 최댓값 + 1이다.
- R7.3 `issueKey.source`가 `jira`인데 `--next`를 쓰면 키를 만들지 않고 exit 2로 끝낸다.
- R7.4 이슈 문서 세 종은 frontmatter에 `key`·`area`·`type`·`status`(tasks는 `state`)를 가진다.
- R7.5 보드는 `area` 값으로 묶어 보여 준다.
- R7.6 `sdd-layout.py migrate --dry-run`은 옮길 목록을 `migrate-map.json`으로 쓰고 파일을 바꾸지 않는다. `--apply`는 그 파일대로 `git mv`하고, 적용 전후 영역별 상태 개수가 다르면 되돌린다.
- R7.7 옛 구조(`<영역>-specs/`)는 읽기만 한다. 옛 구조에 새 이슈 폴더나 단계 문서가 생기면 fast 검증이 실패한다.
- R7.8 브랜치 이름은 `<종류>/<이슈키>-<이름>`이다. 이 형식의 브랜치를 push할 때 같은 키의 이슈 폴더가 없으면 pre-push가 막는다. `exp/`는 검사하지 않는다.
- R7.9 base에 같은 키가 다른 이름으로 있으면 fast 검증이 실패한다(키 충돌).

## 3. 설계

### 3.0 레벨 진입

`verify-entry.sh`가 레벨을 정한다. 우선순위: 명령 인자 > `HARNESS_VERIFY_LEVEL` > 기본 `changed`.

| 인자 | 레벨 | 실행 주체 |
|---|---|---|
| (없음) · `--changed` | changed | `verify-changed.py` |
| `--affected` | affected | `verify-changed.py --level affected` |
| `--fast` | fast | 스택 `verify.sh` 본문(지금 그대로) |
| `--full` | full | 스택 `verify.sh` 본문(지금 그대로) |

`--files`·`--tests`·`--plan`·`--base`는 changed·affected에 그대로 넘긴다. fast·full 본문은 바꾸지 않고, 기록만 3.5의 기록기가 감싼다.

```bash
# verify-entry.sh (발췌)
for a in "$@"; do case "$a" in
  --full) export HARNESS_VERIFY_LEVEL=full ;;  --fast) export HARNESS_VERIFY_LEVEL=fast ;;
  --affected) export HARNESS_VERIFY_LEVEL=affected ;;  --changed) export HARNESS_VERIFY_LEVEL=changed ;;
esac; done
case "${HARNESS_VERIFY_LEVEL:-changed}" in
  changed|affected) exec python3 "$dir/verify-changed.py" --level "${HARNESS_VERIFY_LEVEL:-changed}" "$@" ;;
  fast|full) . "$dir/harness/verify_record.sh" ;;   # 본문 stdout 을 기록기로 흘린다(3.5)
  *) echo "✖ 알 수 없는 검증 레벨: $HARNESS_VERIFY_LEVEL" >&2; exit 2 ;;
esac
```

### 3.1 affected 계획

`verify_affected.py`가 `affected_plan(root, files, units, base)`를 낸다. 형식은 지금의 `verification_plan` 결과와 같고 `level: "affected"`, `modules`, `widened` 필드가 붙는다.

순서:

1. base를 정한다. `origin/<git.base>`가 있으면 그것, 없으면 로컬 `<git.base>`, 둘 다 없으면 상태 `incomplete`, 오류 `base ref 없음: origin/develop — git fetch origin develop 뒤 다시 실행`.
2. 변경 집합 = `git diff --name-only -z <merge-base>` + `git status --porcelain -z --untracked-files=all`의 경로. submodule 포인터 변경은 지금의 `expand_gitlink_files`로 submodule 안 파일 목록으로 편다.
3. 파일마다 단위를 정한다(`units_for` · `owner_for`, 지금 코드).
4. 단위의 스택 판정기(아래 표)로 모듈을 정하고, 모듈 그래프에서 역방향 닫힘(reverse closure)을 구한다. 닫힘 계산은 지금의 `consumer_closure`와 같은 고정점 반복이다.
5. 모듈 집합으로 명령을 만든다. 같은 빌드 루트의 모듈은 명령 하나로 묶는다(Gradle 한 번 기동, pnpm 한 번 호출).
6. 문서·설정 파일은 지금처럼 `verify_static.py`와 `.agents/verify-checks.json`의 경로 검사로 보낸다.

빌드 계약 파일(아래 표의 "계약 파일")이 바뀌면 그 빌드 루트 전체를 고르고 `widened`에 `{"reason": "build-contract", "file": …}`를 남긴다.

| 스택 | 빌드 루트 | 파일 → 모듈 | 모듈 그래프 | 명령 | 계약 파일 |
|---|---|---|---|---|---|
| Gradle(jvm) | `settings.gradle(.kts)`가 있는 가장 가까운 상위 폴더 | 파일 위쪽으로 처음 만나는 `build.gradle(.kts)` 폴더가 등록된 모듈이면 그 모듈 | settings의 `include`와 각 모듈 빌드 파일의 `project(":x")`·`projects.x` 참조 | `./gradlew :a:check :b:check --continue --console=plain` | `settings.gradle*`, 루트 `build.gradle*`, `gradle/libs.versions.toml`, `gradle.properties`, `buildSrc/**`, `build-logic/**` |
| pnpm(web·electron) | `pnpm-workspace.yaml`이 있는 폴더 | 파일 위쪽으로 처음 만나는 `package.json`의 `name` | pnpm이 계산한다 | 스크립트(`lint` · `typecheck` · `test`)마다 `pnpm --filter "...<name>" run --if-present <스크립트>` | `pnpm-lock.yaml`, 루트 `package.json`, `pnpm-workspace.yaml`, `tsconfig.base.json` |
| uv workspace(python) | `[tool.uv.workspace]`가 있는 `pyproject.toml` 폴더 | 파일이 속한 멤버 폴더 | 멤버 `[project].dependencies`·`optional-dependencies`·`dependency-groups`에 다른 멤버의 이름이 있고 `[tool.uv.sources]`에 `workspace = true`이면 간선 | 멤버마다 `ruff check <멤버>` · `mypy`(설정이 있으면) · `pytest <멤버>/tests` | 루트 `pyproject.toml`, `uv.lock` |
| Go | `go.mod` 폴더(`go.work`가 있으면 그 안의 모듈 전부) | 파일 폴더의 import path(`go list -f '{{.ImportPath}}' ./<dir>`) | `go list -test -f '{{.ImportPath}} {{join .Deps " "}}' ./...`(`Deps`는 전이적이다) | `go vet <pkgs>` · `go test -race <pkgs>` | `go.mod`, `go.sum`, `go.work` |

#### Gradle 모듈 그래프

정적 파싱을 먼저 하고, 해석할 수 없는 구문이 나오면 Gradle 초기화 스크립트로 넘어간다.

1. settings에서 `include(":a", ":b:c")`, `include ':a'`, `include(":a")`를 읽는다. 경로 `:b:c`의 기본 폴더는 `b/c`다.
2. `project(":a").projectDir = file("x/y")` 리터럴은 폴더를 덮어쓴다.
3. 각 모듈 빌드 파일에서 정규식 `project\(\s*["'](:[^"']+)["']\s*\)`과 `projects\.([A-Za-z0-9.]+)`(타입 안전 접근자, camelCase → kebab-case)를 모은다. 설정 이름(`implementation`·`api`·`testImplementation`·`testFixtures(...)`)은 가리지 않는다. 시험 의존도 영향 범위다.
4. 정적 파싱 중단 조건: `include`에 문자열 리터럴이 아닌 인자, `includeBuild`, settings 안의 함수 호출로 만든 `projectDir`(예: `hexagonal-standalone`의 `context()` 도우미). 이때 `scripts/harness/gradle/affected-graph.init.gradle`로 `./gradlew -q --init-script … harnessProjectGraph`를 한 번 돌려 `{path, projectDir, projectDeps[]}` JSON을 받는다.
5. 그래프는 `.agents/state/gradle-graph-<빌드 파일 해시 16자>.json`에 캐시한다. 해시 대상은 settings와 모든 모듈 빌드 파일이다.

knots 예(`knots-app-server`, 모듈 17개): `knots-service-library/src/main/…/X.kt` 하나를 바꾸면 그래프상 `knots-service-library`를 `project(":knots-service-library")`로 참조하는 `knots-service-recording` · `knots-app-bootstrap` 등이 더해진다.

```text
./gradlew :knots-service-library:check :knots-service-recording:check :knots-app-bootstrap:check \
          --continue --console=plain
```

`:x:check`는 그 모듈의 컴파일·린트·테스트를 돌리고, 의존 모듈은 컴파일만 한다. changed 레벨의 `--no-daemon --dependency-verification=strict`는 affected에서도 유지한다.

#### pnpm

작업 트리의 변경까지 넣기 위해 킷이 패키지 이름을 직접 계산하고 `...<name>` 필터(그 패키지와 그것에 의존하는 패키지)를 패키지마다 붙인다.

```text
pnpm --filter "...@knots/app-web" --filter "...@knots/ui" --workspace-concurrency=4 -r run --if-present lint
pnpm --filter "...@knots/app-web" --filter "...@knots/ui" --workspace-concurrency=4 -r run --if-present typecheck
pnpm --filter "...@knots/app-web" --filter "...@knots/ui" --workspace-concurrency=4 -r run --if-present test
```

CI(작업 트리가 깨끗하다)에서는 같은 집합을 `--filter "...[origin/develop]"`로 고른다. `build`는 affected에서 돌리지 않는다(full·CI). 워크스페이스가 아닌 단일 패키지는 그 패키지의 `lint typecheck test`를 돈다. npm 워크스페이스는 의존 필터가 없어서 `package.json`의 `dependencies`에서 같은 워크스페이스 이름을 찾아 그래프를 만들고 `npm run <script> --workspace=<name>`을 패키지마다 부른다.

#### uv workspace

knots `knots-recording`(멤버 `knots-recording-server` · `knots-recording-model-server`)에서 `knots-recording-server/src/…`를 바꾸면 그 멤버와, 그 멤버를 의존으로 적은 멤버가 고른다. 실행 환경은 지금의 `.venv-verify` · `.venv` 탐색을 그대로 쓰고 `UV_NO_SYNC=1 UV_OFFLINE=1`로 설치를 막는다. 워크스페이스가 아닌 Python 프로젝트는 프로젝트 하나를 모듈 하나로 본다.

#### Go

`go list -test`의 출력에서 `pkg [pkg.test]` 같은 시험 변형 이름은 대괄호 앞만 쓴다. 바뀐 패키지 집합 P에 대해 `Deps ∩ P ≠ ∅`인 패키지를 더한다. 모듈 하나에서 `go list` 한 번(knots 규모에서 수 초)이다.

#### 그 밖의 스택

킷 스택 5종 밖(knots의 tauri · flutter · extension 단위)은 그래프를 만들지 않는다. 그 단위의 게이트를 `HARNESS_VERIFY_LEVEL=full HARNESS_VERIFY_PARENT=affected bash <단위>/scripts/verify.sh`로 부르고 `widened`에 `{"reason": "no-module-graph", "unit": "desktop"}`을 남긴다. 단위 하나의 full이므로 루트 full보다 범위가 좁다.

#### 시간 상한

| 레벨 | 명령별 상한 | 전체 상한 | 넘으면 |
|---|---|---|---|
| changed | 300초(`--timeout`, 지금 값) | 없음 | 그 명령 exit 124, 상태 `failed` |
| affected | 900초 | 1,200초(`--budget`) | 남은 명령을 돌리지 않고 상태 `incomplete`, `skipped`에 이름을 남긴다 |

### 3.2 full 차단 훅

새 파일 `scripts/hooks/block-full-verify.sh`. 판정은 Python으로 한다(JSON 이스케이프를 정규식으로 다루지 않는다).

```python
# block_full_verify.py 판정 (발췌)
FULL_ENV = re.compile(r'(^|[\s;&|(])(export\s+)?HARNESS_VERIFY_LEVEL=["\']?full\b')
FULL_FLAG = re.compile(r'verify(-entry)?\.sh\b[^;&|\n]*\s--full\b')
FULL_PY = re.compile(r'verify-changed\.py\b[^;&|\n]*--level[= ]full\b')
command = payload.get("tool_input", {}).get("command", "")
blocked = any(p.search(command) for p in (FULL_ENV, FULL_FLAG, FULL_PY))
```

stderr 안내(exit 2):

```text
차단: 에이전트 세션에서는 전체 검증(full)을 돌리지 않는다. 전체 검증은 CI가 돈다(D10).
→ 바꾼 범위:       bash scripts/verify.sh
→ MR 올리기 전:    bash scripts/verify.sh --affected
→ 범위만 보기:     bash scripts/verify.sh --affected --plan
사람이 터미널에서 직접 실행하는 full은 막지 않는다. 이 규칙은 .agents/harness-kit.json 의 verify.fullOnlyInCI 다.
```

하네스별 등록(v1.1은 설정 파일에 직접 넣는다. P18부터 `.agents/hooks.json`에서 생성한다. [03](03-projection-and-hooks.md#34-hooksjson)):

| 하네스 | 파일 | 이벤트 · matcher | 명령 |
|---|---|---|---|
| Claude Code | `.claude/settings.json` | `PreToolUse` · `Bash` | `bash "$CLAUDE_PROJECT_DIR"/scripts/hooks/block-full-verify.sh` |
| Codex | `.codex/hooks.json` | `PreToolUse` · `Bash` | 지금의 상위 탐색 `bash -c` 래퍼 + `block-full-verify.sh` |
| Kiro IDE | `.kiro/hooks/harness-block-full-verify.json` | `PreToolUse` · 셸 도구 이름(6장 확인) | 같은 래퍼, timeout 15 |
| Kiro CLI | `.kiro/agents/<slug>.json`의 `hooks.preToolUse` | matcher `shell` | 같은 래퍼, `timeout_ms` 15000 |

사람·CI가 영향받지 않는 이유: 이 훅은 하네스가 셸 도구를 부를 때만 돈다. 사람 터미널과 CI 러너에는 하네스 훅이 없다. 판정은 명령 문자열만 보므로, 에이전트가 문자열을 바꿔 우회하는 것까지 막지는 않는다. 목표는 완료 확인으로 full을 습관처럼 부르는 일을 없애는 것이다.

보조 점검: `verify-entry.sh`는 레벨이 full이고 `CI`가 비어 있고 `HARNESS_VERIFY_PARENT`가 비어 있고 에이전트 환경 표지(Claude Code `CLAUDECODE=1`, 나머지는 6장 확인 후 확정)가 있으면 같은 안내를 내고 exit 3으로 끝낸다. 상위 게이트가 하위 단위를 부를 때는 `HARNESS_VERIFY_PARENT`를 설정한다.

### 3.3 테스트를 못 찾을 때

지금은 `tests_for_project`가 `no related test found; … opt in to full verification`을 `incomplete`에 넣고 끝난다. 바꾼 뒤:

1. 관련 테스트가 없는 코드 파일 f의 모듈 m을 3.1의 판정기로 정한다(changed에서도 같은 판정기를 쓴다).
2. m의 모듈 테스트 명령을 더한다: Gradle `:m:test`, uv `pytest <멤버>/tests`, Go `go test <패키지>`, pnpm `--filter <name> run --if-present test`.
3. `widened`에 `{"file": f, "module": m, "reason": "no-related-test"}`를 남긴다.
4. m에 테스트 소스가 없거나(Gradle `src/test` 없음, `tests/` 없음, `*_test.go` 없음), 실행한 테스트 수가 0이면 `unverified`에 `{"file": f, "reason": "no-module-test"}`를 넣는다. 상태 `incomplete`, exit 2.

요약 출력(`verify_summary.py`)의 새 이유 이름:

```text
미완료 1개 — 전체 목록: python3 scripts/verify-changed.py --plan
- 미검증 1개: PaymentPolicy.kt — 관련 테스트와 모듈 테스트가 없다. 테스트를 추가하거나 --tests 로 지정한다
넓힘 2개: OrderMapper.kt → :knots-service-note:test, Retry.kt → :knots-common:test
```

`verify_runner.py`의 `zero tests executed; select --tests or opt in to full`, `changed code executed no tests; select --tests or full`과 `verify_planner.py`의 권고 4문장(`opt in to full and relevant integration verification` 등)은 `MR 전 bash scripts/verify.sh --affected` 안내로 바꾼다.

### 3.4 다층 리포 상위 게이트

`tools/harness/gates.py`에 `--changed --base <ref>`를 더한다. 출력 형식(`<id> <path> <rootVerify>`)은 같고, 변경 없는 도메인 줄을 뺀다.

도메인 d(경로 p)의 변경 판정, 하나라도 참이면 부른다:

1. `git diff --name-only <merge-base> -- p`에 p 자체(gitlink)가 있다.
2. `git -C p status --porcelain`이 비어 있지 않다.
3. `git -C p rev-list --count HEAD --not origin/<git.base>` > 0. 도메인 리포 브랜치에서 커밋했지만 루트 포인터를 아직 올리지 않은 경우다.
4. 루트 변경 집합에 `p/` 아래 경로(submodule이 아닌 폴더)가 있다.

루트 게이트의 루프는 레벨이 changed·affected면 `gates.py --changed`를, fast·full이면 지금의 `gates.py`를 쓴다. 루트 범위 검사(하네스 도구 테스트·드리프트·공급망 잠금)는 루트 파일이 바뀌었을 때만 changed·affected에서 돈다. 판정 경로는 `verify-checks.json` 항목으로 둔다.

```text
▶ 하네스 domain-service (affected)
↷ domain-platform 건너뜀 — 변경 없음
↷ domain-app 건너뜀 — 변경 없음
```

### 3.5 `.agents/state/verify-last.json`

changed·affected는 `verify-changed.py`가 직접 쓴다. fast·full은 본문 stdout을 기록기 `verify_record.py --tee`로 흘린다. 기록기는 `▶`(뒤에 공백)로 시작하는 줄을 단계 시작으로, 같은 단계 안의 `✖`(뒤에 공백) 줄을 단계 실패로 본다. `verify-entry.sh`는 EXIT trap에서 `::harness-exit <code>` 한 줄을 내보내고 기록기는 그 줄을 출력하지 않는다. 스택 본문은 고치지 않는다.

### 3.7 이슈 단위 SDD

#### 3.7.1 명령

```text
scripts/new-feature.sh <이슈키|--next> <이름> [--area <영역>] [--type feat|fix|refactor|perf|chore|docs]
                       [--intent <INT-키>] [--unit <U-번호>] [--dry-run]
scripts/new-feature.sh <이슈키> --stage=design|tasks
```

- 첫 단계(requirements)에는 `--area`가 필수다. 없으면 기존 이슈의 area 목록을 출력하고 exit 2.
- design·tasks 단계는 키만으로 폴더를 찾는다(`issues/<키>-*`가 하나여야 한다).
- 옛 형식 `new-feature.sh <slug> <이름>`(첫 인자가 키 형식이 아닌 소문자 토큰)은 v1.1 동안 `--next <이름> --area <slug>`로 바꿔 실행하고 stderr에 새 형식을 안내한다. v2.0에서 삭제한다. `--legacy`는 지원을 끝내고 exit 2로 안내한다.

종료 코드: 0 생성(또는 이미 있음), 1 선행 조건 실패(앞 단계가 approved가 아님), 2 인자 오류, 3 키 충돌.

#### 3.7.2 키와 이름 규칙

| 항목 | 규칙 | 예 |
|---|---|---|
| 이슈 키 | `^[A-Z][A-Z0-9]{1,9}-[1-9][0-9]{0,5}$` | `HDRV3D-12`, `KNOTS-17` |
| 이름(slug) | `^[a-z0-9]+(-[a-z0-9]+){1,4}$`, 2~5단어, 40자 이하, 영문 소문자·숫자 | `upload-cleanup` |
| 금지 | 한글·공백·대문자, `feat-` 같은 종류 접두, 숫자로 시작하는 첫 단어 | `feat-login` ✗ |
| 폴더 | `<키>-<이름>`, 60자 이하 | `KNOTS-17-desktop-parity` |

`issueKey.source = kit`이면 키의 접두는 `issueKey.prefix`와 같아야 한다. `jira`면 Jira 키 형식이면 받고, 접두가 `issueKey.prefix`와 다르면 경고만 낸다(Jira 프로젝트가 여럿인 팀).

v1.1의 설정 읽기: v1 메타(`.agents/harness-kit.json`)에 `issueKey`·`git.base`·`verify.fullOnlyInCI`가 없으면 기본값 `{"source": "kit", "prefix": <tokens.PROJECT_SLUG 대문자>}`, `develop`, `true`를 쓴다. `harness_write_meta`는 지금 파일을 통째로 다시 쓰므로, v1.1에서 모르는 키를 보존하도록 Python JSON 병합으로 바꾼다. 바꾸지 않으면 `hx-update` 한 번에 세 키가 사라진다.

#### 3.7.3 킷 키 만들기(`--next`)

1. `git fetch origin <git.base> --quiet`(10초 상한). 실패하면 경고하고 캐시된 ref를 쓴다.
2. 쓰인 번호를 모은다(접두 P):
   - `git ls-tree --name-only origin/<base> .agents/docs/issues/`에서 `^P-(\d+)-`
   - 작업 트리 `.agents/docs/issues/`의 폴더 이름
   - `git for-each-ref --format='%(refname:short)' refs/heads refs/remotes`에서 `/(P-\d+)-` — 브랜치 이름에 키가 있으므로 원격 브랜치의 파일을 읽지 않고 다른 사람이 연 키를 본다
   - `git worktree list --porcelain`의 브랜치(로컬 브랜치에 포함되지만 detached worktree를 위해 따로 본다)
3. N = 최댓값 + 1(없으면 1). `sdd_lock`(지금 코드) 안에서 폴더를 만든다.
4. 충돌 검사(fast 검증 단계 `check-issue-keys`): HEAD의 이슈 폴더마다 `origin/<base>` 트리에 같은 키·다른 이름의 폴더가 있으면 실패.

```text
✖ 키 충돌: KNOTS-18 이 origin/develop 에 KNOTS-18-token-expiry 로 이미 있다.
  → python3 scripts/sdd-layout.py rekey KNOTS-18 --next   (폴더·frontmatter 를 새 키로 옮기고 브랜치 이름 변경 명령을 출력한다)
```

`issueKey.source = jira`에서 `--next`:

```text
✖ issueKey.source 가 jira 라서 키를 만들지 않는다. Jira 이슈 키를 넣는다(예: scripts/new-feature.sh KNOTS-123 desktop-parity --area app).
  Jira 없이 쓰려면 .agents/harness-kit.json 의 issueKey.source 를 kit 로 바꾼다.
```

#### 3.7.4 frontmatter

```yaml
---
key: KNOTS-17
area: app                  # 영역. 옛 <영역>-specs 의 <영역>
type: feat                 # feat | fix | refactor | perf | chore | docs

status: draft              # requirements·design: draft | in-review | approved | superseded

jira: https://<site>.atlassian.net/browse/KNOTS-17   # 선택. source=jira 이면 new-feature 가 채운다
legacy: recording-specs/issues/163-feat-recording-quality-tiro-parity   # 옮긴 이슈만
created: 2026-11-23
---
```

- `tasks.md`는 `status` 대신 `state: active | check | completed | superseded`를 쓴다. 상태 전이는 파일 이동이 아니라 이 값을 바꾸는 것이다.
- 파서는 표준 라이브러리만 쓰는 부분 집합이다: 첫 줄 `---`부터 다음 `---`까지, 줄마다 `^([a-z][a-zA-Z0-9]*):\s*(.*?)(\s+#.*)?$`, 값은 문자열, 중첩 없음. 형식이 틀리면 그 문서를 `invalid`로 보고하고 보드 생성을 멈춘다.
- 상태의 원본은 frontmatter 하나다. 새 템플릿에서 `| 상태 |` 행을 지운다. 옛 문서는 지금처럼 표 행을 읽는다.
- 필수: `key`·`area`·`type`·`status`(또는 `state`). 폴더 이름의 키와 `key`가 다르면 fast 검증 실패.

#### 3.7.5 폴더와 보드

```text
.agents/docs/issues/KNOTS-17-desktop-parity/
├── requirements.md · design.md · tasks.md
├── checklists/            (/hx-checklist)
└── review.md · approvals.md · handoff-2026-11-23.md
```

보드는 `.agents/docs/specs-index.md`의 BOARD 마커 사이에 영역별 표를 쓴다. 영역 이름순, 영역 안에서는 키 번호순. 옛 구조 이슈는 같은 영역 표의 아래에 `(옛)` 표시로 붙인다.

```markdown
### app (새 2 · 옛 0)
| 키 | 이름 | 종류 | req | design | tasks | 상태 |

| KNOTS-17 | desktop-parity | feat | approved | in-review | — | 설계 |
```

상태 계산: `tasks.md`가 있으면 그 `state`, 없고 `design.md`가 있으면 "설계", 그 밖에는 "요구". 지금의 6칸(요구·설계·구현·검증·완료·폐기)과 같다. `scripts/board.sh --area <영역>`은 그 영역 표만 stdout에 낸다. 영역별 `index.md`는 v1.1 이후 만들지 않는다.

#### 3.7.6 옮기기(`sdd-layout.py migrate`)

```text
python3 scripts/sdd-layout.py migrate --dry-run [--include-legacy] [--prefix KNOTS] [--start 1] [--areas recording,auth]
python3 scripts/sdd-layout.py migrate --apply --map .agents/state/migrate-map.json [--rewrite-links]
```

기본 대상은 옛 이슈 폴더(`<영역>-specs/issues/<N>-<종류>-<이름>/`)다. `--include-legacy`를 주면 단계 폴더 구조의 문서(`requirements/<키>.md` 등)도 옮긴다. 주지 않으면 그 문서는 제자리에 두고 읽기만 한다.

dry-run 순서:

1. `.agents/docs/*-specs/`를 돈다. 영역 = 폴더 이름에서 `-specs`를 뗀 값.
2. 항목을 모은다: 옛 이슈 폴더는 폴더 하나 = 항목 하나. 단계 폴더 문서는 같은 키의 requirements·design·tasks/<상태>를 묶어 항목 하나.
3. 새 키를 정한다. 정렬 (영역, 옛 번호, 이름) 순으로 `<prefix>-<start + i>`. start 기본값은 3.7.3의 최댓값 + 1. 옛 번호를 그대로 쓰지 않는 이유: knots에서 영역 간 같은 번호가 18개다.
4. 경고를 모은다: 이름이 slug 규칙을 어기면 고친 이름 제안(`_`→`-`, 6단어 이상은 앞 5단어), 같은 키가 두 구조에 있으면 `duplicate`, 깨끗하지 않은 파일(`git status --porcelain <경로>`)은 `dirty`.
5. `.agents/state/migrate-map.json`을 쓴다. 파일을 옮기지 않는다.

```jsonc
{
  "schema": "harness-kit.migrate-map/v1",
  "createdAt": "2026-11-23T11:02:00Z",
  "base": { "ref": "origin/develop", "sha": "9c1e…" },
  "issueKey": { "source": "kit", "prefix": "KNOTS" },
  "counts": { "areas": 13, "items": 141, "legacyItems": 0 },
  "items": [
    {
      "action": "move",                        // move | skip  (사람이 고친다)
      "from": ".agents/docs/recording-specs/issues/163-feat-recording-quality-tiro-parity",
      "layout": "issue",                       // issue | stage
      "area": "recording", "type": "feat", "oldNumber": 163,
      "key": "KNOTS-128",                      // 사람이 Jira 키로 바꿔도 된다
      "slug": "recording-quality-tiro-parity",
      "to": ".agents/docs/issues/KNOTS-128-recording-quality-tiro-parity",
      "files": [
        { "from": "requirements.md", "to": "requirements.md", "status": "approved" },
        { "from": "design.md", "to": "design.md", "status": "approved" },
        { "from": "tasks/completed.md", "to": "tasks.md", "state": "completed" },
        { "from": "analysis-notes.md", "to": "analysis-notes.md" },
        { "from": "diagrams/", "to": "diagrams/" }
      ]
    }
  ],
  "boardBefore": { "recording": { "requirements": 0, "design": 0, "active": 0, "check": 0, "completed": 72, "superseded": 2 } },
  "warnings": [ { "item": "…/issues/12-feat-x_y", "code": "slug", "suggest": "x-y" } ]
}
```

apply 순서:

1. 지도를 검증한다: 키 형식·중복 없음, `to`가 없음, `from`이 있고 깨끗함, `.agents/docs/`에 커밋 안 된 변경 없음. 하나라도 어기면 아무것도 옮기지 않고 exit 3.
2. 항목마다 `git mv <from>/<파일> <to>/<파일>`. `tasks/<상태>.md` → `tasks.md`. 남은 파일·폴더도 `git mv`로 같이 옮긴다.
3. requirements·design·tasks에 frontmatter를 넣는다. 옛 `| 상태 |` 행 값은 `status`/`state`로 옮기고 표 행을 지운다. `legacy`에 옛 경로를 적는다.
4. 옮긴 문서 안의 상대 링크(`../../design/<키>.md`, `../requirements.md`)를 새 위치 기준으로 고친다. `--rewrite-links`면 `.agents/docs/**/*.md`에서 옛 경로를 가리키는 링크도 고친다. 그 밖의 파일은 목록만 출력한다.
5. 옛 `<영역>-specs/index.md`의 BOARD 마커 블록을 "이슈는 `.agents/docs/issues/`(area: <영역>)로 옮겼다" 한 줄로 바꾼다. research·interfaces 같은 비SDD 문서는 그대로 둔다.
6. 보드를 다시 만들고 영역별 상태 개수를 `boardBefore`와 비교한다. 다르면 `git restore --source=HEAD --staged --worktree -- .agents/docs`로 되돌리고, 지도의 `to` 폴더 중 남은 것을 지운 뒤 차이를 출력하고 exit 1. 1번에서 `.agents/docs`가 깨끗했으므로 옮기기 결과만 지워진다.
7. 커밋하지 않는다. 출력 끝에 `git status --short | wc -l`과 커밋 명령 예를 낸다.

#### 3.7.7 옛 구조 읽기 전용

- 보드·`check-sdd-prerequisites.sh`·`check-spec-freshness.sh`는 세 구조(새 `issues/`, 옛 이슈 폴더, 옛 단계 폴더)를 모두 읽는다.
- fast 단계 `check-legacy-frozen`: `git diff --diff-filter=A --name-only <merge-base> -- '.agents/docs/*-specs/issues/*' '.agents/docs/*-specs/requirements/*' '.agents/docs/*-specs/design/*' '.agents/docs/*-specs/tasks/*'`가 비어 있지 않으면 실패. 기존 문서의 수정은 허용한다(진행 중인 옛 이슈를 끝내기 위해).

#### 3.7.8 브랜치 이름

`<종류>/<이슈키>-<이름>`, 예 `feat/KNOTS-17-desktop-parity`. 정규식 `^(feat|fix|refactor|perf|chore|docs)/([A-Z][A-Z0-9]{1,9}-[0-9]+)-[a-z0-9-]+$`.

- pre-push: 올리는 브랜치가 이 형식이면 그 커밋 트리에 `.agents/docs/issues/<키>-*`가 있어야 한다. 없으면 exit 1. 형식이 아니면 경고만 낸다. `exp/`는 검사하지 않는다(병합하지 않는 실험 브랜치).
- 다층 리포: SDD 폴더는 메인 리포에 있고, 도메인 리포 브랜치도 같은 이름을 쓴다. 도메인 리포의 pre-push는 메인 리포 경로(`git rev-parse --show-superproject-working-tree`)에서 폴더를 찾는다.
- 지금의 "단위 id를 브랜치 앞에 붙인다" 규칙은 삭제한다. 키가 이미 리포 전체에서 하나다.

## 5. 완료 기준

[03장 v1.1 완료 기준](../harness-next/03-plan.html#now)을 그대로 쓰고 측정 방법과 추가 항목을 붙인다.

1. knots 사본에서 `knots-service-library`의 소스 파일 하나를 바꾼 작업: changed 3분 이내, affected 15분 이내. `verify-last.json`의 `durationMs`로 잰다.
2. 에이전트 세션에서 `bash scripts/verify.sh --full`, `HARNESS_VERIFY_LEVEL=full bash scripts/verify.sh`, `export HARNESS_VERIFY_LEVEL=full; bash scripts/verify.sh`를 부르면 훅이 exit 2와 안내를 낸다. Claude·Codex·Kiro 입력 fixture 3종 × 명령 3종 = 9건 테스트. `verify.sh --fast`, `verify.sh --affected`, `grep -- --full x.md`는 통과한다(오탐 3건 테스트).
3. 관련 테스트가 없는 소스 파일 fixture에서 changed가 모듈 테스트를 돌린다. 모듈 테스트도 없는 fixture는 `unverified` 1건, exit 2. 두 경우 모두 출력에 "full"이 없다.
4. 다층 fixture(도메인 3곳)에서 도메인 하나만 바꾸면 루트 affected 로그에 `▶ 하네스` 1줄, `↷ … 건너뜀` 2줄.
5. 네 레벨 모두 실행 뒤 `verify-last.json`이 스키마 검사를 통과한다. 쓰기 권한이 없어도 exit code가 같다.
6. `new-feature.sh HDRV3D-12 upload-cleanup --area upload`가 `issues/HDRV3D-12-upload-cleanup/requirements.md`를 만들고 `key: HDRV3D-12`가 들어 있다. `--next`는 `<prefix>-<최댓값+1>`.
7. 두 브랜치가 각자 `--next`로 `KNOTS-18`을 만들고 하나가 base에 병합되면, 다른 브랜치의 fast가 키 충돌로 실패한다. `rekey` 뒤 통과한다.
8. knots 사본에서 `migrate --dry-run`이 13개 영역, 141개 항목을 지도에 쓴다. `--apply` 뒤 영역별 상태 개수가 적용 전과 같다.
9. 3.6의 grep 검사가 테스트로 통과한다.
10. `feat/KNOTS-17-desktop-parity` 브랜치를 이슈 폴더 없이 push하면 pre-push가 막는다.
