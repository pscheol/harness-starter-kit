7신뢰 경계와 보안

에이전트 세션은 신뢰하지 않는 쪽이다. 세션은 문서와 코드를 쓰지만 게이트를 넘기는 기록은 쓰지 못하고, 그 기록은 사람만 쓰는 경로에서 생긴다.

7.1 승인 네 경로

승인은 아래 넷으로만 생긴다. 채팅에서 한 말("좋아" · "반영해" · "머지해" · "배포해")과 몹 회의에서 말로 한 결정은 승인이 아니다. 승인할 때 넣은 문구는 그 기록에 남지만 문구만으로 승인이 생기지는 않는다(README §3).

경로사람이 했는지 확인하는 방법기록의 출처 값설계
사람 터미널npx harness-kit approve(Node 없으면 approve.py). 에이전트 세션 판정이 거짓이고 TTY일 때만, 이슈 키를 다시 입력받는다terminal09 §3.8
관리 페이지서버를 띄운 터미널에만 출력한 PIN(10자, 50비트). 5회 틀리면 서버가 끝날 때까지 잠근다. 승인자 = 그 체크아웃의 git user.emaildashboard06 §3.7

7.2 에이전트 세션 판정

아래 중 하나라도 맞으면 에이전트 세션 안이다: CLAUDECODE=1, CLAUDE_CODE_MESSAGING_SOCKET이 있음, Codex · Kiro가 셸에 넣는 변수(확인 필요), 부모 프로세스에 하네스 실행 파일. 참이면 관리 페이지는 PIN 없이 읽기 전용으로 뜨고, approve · answer · review decide는 거부되고, pre-commit · pre-push는 에이전트 규칙을 적용한다(06 §3.11). 같은 OS 사용자 권한으로 도는 임의 프로세스는 막지 못한다. 더 강한 증거가 필요한 게이트는 Jira 사람 전이나 MR 플랫폼 승인을 쓴다.

7.5 비밀값과 외부 도구

  • 토큰은 환경 변수로만 받는다(JIRA_API_TOKEN · JIRA_USER_EMAIL · NOTION_TOKEN · CI 토큰). 리포 · harness-kit.json · 문서 · 예시에 쓰지 않는다.
  • 접수 첨부의 텍스트와 추출본은 gitleaks로 검사하고, 비밀값이 나오면 저장하지 않는다. 주민등록번호 · 전화번호 패턴은 커밋 전에 경고한다(08 §3.11).
  • Entire는 킷 비밀값 가드와 같은 마스킹 패턴을 쓰고, 원격 공개 여부를 확인하지 못하면 공개로 보고 체크포인트를 올리지 않는다(10 §3.3).
  • 외부 도구는 그 도구의 설치기와 명령으로 깔고 올린다. 킷은 외부 도구를 설치하지 않고, 필요한 도구가 없으면 설치 명령을 출력하고 exit 5로 끝낸다(10 MD-R3).

8.2 버전과 릴리스

  • 버전은 다섯 곳(package.json, 두 마켓플레이스 파일, Claude · Codex 플러그인 매니페스트)을 scripts/release.sh <버전>이 같이 올린다. --check는 매 MR에서 다섯 값이 같은지 본다.
  • major: 설치 결과의 경로 · 형식, 명령 삭제 · 이름 변경. minor: 명령 · 모듈 · 설정 키 · 분석기 추가(기본 꺼짐). patch: 템플릿 문구, 버그, 외부 도구 검증 범위.
  • P17은 2.0.0-alpha.N, P18 완료가 2.0.0이다. 태그는 지우거나 다시 쓰지 않고, 문제가 있는 버전은 patch로 고친다. lock의 kit.source가 설치한 태그를 남긴다.
  • 릴리스 조건: 단위 시험, CLI 시험, 두 구성 e2e-stub(합계 5분 이하), 사람이 하는 하네스별 스킬 목록 확인, 토큰 전후 비교(9.1). 스크립트는 커밋과 주석 태그까지만 하고 push하지 않는다(11 §3.5).

8.3 v1 리포 이전

이전은 doctor(읽기) → update --dry-run(계획) → 사람 승인 → update(.new 생성, lock v2) → .new 병합 → CI full · doctor --check → 커밋 하나 순서다. 되돌리기는 그 커밋의 git revert이고, 외부 도구 쪽은 그 도구 명령으로 되돌린다(11 §3.1 · §3.8).

속성장치
쓰기 안전임시 파일 + fsync + rename, 저장은 baseSha256 비교(다르면 409), 승인 두 파일 쓰기 중 하나가 실패하면 되돌림, update 전 백업 5개
부분 실패모듈 add는 스냅숏으로 킷 몫만 되돌린다. 분석기 하나가 시간을 넘으면 그 분석기만 incomplete. required 분석기가 없으면 로컬은 incomplete, CI는 실패
훅 오작동입력을 해석하지 못한 full 차단 훅은 통과시킨다(01 R2.4). 훅은 입력의 cwd로 하네스 루트를 찾아 worktree에서도 그 worktree를 본다
작업 공간 누적리포당 worktree 3개, wt done은 clean · push · 다른 세션 미사용을 확인한 뒤 지운다. wt gc --apply는 사람이 시킬 때만
확장새 하네스 = 어댑터 파일 하나 + 등록 한 줄. 회사 팩, 프로젝트 확장 지점(규칙 · 스킬 · 역할 · 훅 · 검증 단계 · 가드 · 템플릿 · 게이트 · 스킬 지도), module.json, analyzers.json
오프라인dist/cli.js는 런타임 의존 0, 리포 스크립트는 Python 표준 라이브러리, 관리 페이지 화면은 번들(CDN 없음). 네트워크가 필요한 것은 outdated(버튼을 눌렀을 때만), Jira · Notion 동기화, 실행 때 받는 Semgrep 공식 규칙뿐이다
저장소 · 검색DB를 두지 않는다. 원본은 git의 파일이고(브랜치 · worktree마다 다르고 MR로 리뷰된다), 관리 페이지는 stat 기반 메모리 캐시로 읽는다(06 §3.2). SQLite 같은 DB는 두 번째 원본이 되고 브랜치를 모른다. RAG · 벡터 DB도 두지 않는다. 문서 자리가 정해져 있어(issues/<키>/…) 경로로 바로 찾고, 코드는 에이전트가 grep · 읽기로 찾는다. 임베딩은 모델 호출이라 원칙 10과 맞지 않는다. 다시 볼 조건: 이슈 2,000건 이상에서 GET /overview p95가 500ms를 넘거나, 문서 전체 찾기가 필요해질 때. 그때도 먼저 지울 수 있는 숫자 캐시 · ripgrep 찾기를 쓰고, DB는 원본이 아닌 다시 만들 수 있는 캐시로만 둔다
