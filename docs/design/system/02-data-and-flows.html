무엇이 어디에 남고, 어떤 순서로 움직이나

리포 안 파일마다 누가 쓰고 누가 읽는지, 문서 상태와 게이트가 어떻게 바뀌는지, 요구사항 하나가 운영 기록이 되기까지의 순서를 적는다. 형식의 원본은 README §4~§9와 각 설계 문서이고, 여기서는 연결만 보인다.

5.2 문서 상태와 게이트

문서마다 머리의 status가 draft → in-review → approved | superseded로 바뀐다. 승인 기록에는 그 문서의 sha256이 남고, 승인 뒤 내용이 바뀌면 승인은 stale이 되어 다시 승인한다. 이슈의 단계(stage)는 flow.gates 순서에서 처음으로 통과하지 못한 게이트다(06 §3.3).

게이트승인 대상(sha 기록)기록 위치통과 조건 요약
codebasecurrent-state.md + 참조 코드 모델Intent접수 종류 feature · change · refactor일 때만. 막는 질문 0, 모델이 오래되지 않음(08 §3.13)
intentintent.md + units.jsonIntentcodebase 통과, 막는 질문 0, intent_check.py, CLARIFICATION 0
plansplans/*.md 각각Intentintent 통과, 기획물 필수 제목

design · 하한design.md이슈의존 계약 이슈의 design 통과, §13 배포 · 롤백 칸
taskstasks.md이슈design 통과
mr · 하한문서 없음이슈같은 head의 affected passed, 품질 게이트 passed, 열린 CRITICAL · HIGH 0
done · 하한문서 없음이슈이슈 브랜치가 base에 병합됨
deploy배포 기록 PLAN 구간포함 이슈마다D1~D7: 포함 이슈 done, 계획 승인 유효, 롤백 시험 또는 사람의 면제, 배포 커밋 full 통과, 점검표(14 §3.4)

승인 상태 값은 none · valid · stale · invalid(승인자가 approvers에 없음)다. 위험 high인 이슈는 design · mr · deploy에 서로 다른 승인자 2명이 필요하고, mr 판정 때 diff가 risk.highPaths에 걸리면 머리 값과 상관없이 high로 본다(08 §3.15). tasks.md 진행은 머리의 state가 active → check → completed | superseded로 바뀌고, completed는 유효한 done 기록이 있어야 쓸 수 있다.

Jira를 쓰면 같은 단계가 여덟 상태(백로그 · 요구사항 작성 · 요구사항 승인 대기 · 설계 · 구현 중 · 검증 · 완료 · 배포됨)로 보이고, Jira가 없으면 관리 페이지 보드가 같은 이름을 킷 단계에서 계산한다(10 §3.4).

6주요 흐름

그림의 사람 행위는 모두 관리 페이지 버튼이나 같은 일을 하는 콘솔 명령으로 할 수 있다(06 §3.15). 세션이 하는 일은 사람이 그 세션에 시킨 작업 안에서만 돈다.

6.1 요구사항 접수 → Unit 승인

  • 접수 종류는 product · feature · change · refactor · bug 다섯이다. bug는 Intent 없이 이슈 하나로 간다. feature · change · refactor는 스토리를 쓰기 전에 역공학으로 current-state.md를 만들고 codebase 게이트를 받는다(08 §3.11 · §3.13).
  • 분해 기준: 스토리 5개 이상, 도메인 2개 이상, 사용자 유형 3개 이상, 외부 통합 3개 이상 중 하나라도 맞으면 Unit을 나눈다. 계약 Unit을 먼저 두고, 처음부터 만드는 product는 맨 앞에 걷는 뼈대 Unit을 둔다(08 §3.4 · §3.12).
  • 첨부는 파일 하나 20MB, 접수 하나 100MB까지(제안값). 텍스트와 추출본은 gitleaks 검사를 통과해야 저장한다.
  • 5번 작업 요청은 사람이 접수 화면에서 고를 때만 보낸다. 사람이 세션에서 /kns-intent INT-8을 직접 불러도 된다.

6.2 Unit → 구현 · 검증 → 병합 → 배포 → 운영 기록

자리검증 레벨 · 장치막는 것설계
턴 끝(Stop 훅)fast: 구조 · SDD 상태 · 배치 검사 · 포맷승인 없는 approved · completed, 배치 어긋남01 §3.0, 03 §3.9
Bolt 끝 · 커밋 전 · pre-pushchanged: 바꾼 파일 + 연결 테스트 · 정적 분석테스트를 못 찾은 파일은 unverified, 상태 incomplete01 R3

리뷰 세션은 기능 브랜치를 체크아웃하지 않고 원격 diff · SDD 세 문서 · 규칙 · 스캔 결과만 읽는다. review.md는 구현 세션이 쓴다(09 VQ-R1 · R3). 운영 기록의 장애는 bug 이슈로, 다음 후보는 다음 Intent로, 배운 것은 규칙 후보로 간다. 규칙 후보는 사람이 골라 MR로 .agents/rules/에 넣는다(14 §3.8~3.11).

6.3 관리 페이지 문서 저장 → 세션 작업 요청

  • 이슈 문서는 그 이슈 브랜치가 체크아웃된 폴더에만 쓴다. 다른 브랜치의 작업 트리나 git 객체에는 쓰지 않는다(06 DB-R9).
  • 요청 글은 한 줄 1,000자 이하이고 경로 · 변경 요약 · 요청 문장만 담는다. 받는 세션이 파일을 다시 읽는다. 원칙 10에 따라 문서 내용을 세션에 밀어 넣지 않는다.
  • 소켓 연결에 실패하면 서버가 다른 방법으로 자동 전환하지 않는다. deep link는 사람이 Enter를 눌러야 보내지고, 대기함 항목은 다음 세션 시작이나 프롬프트 제출 때 붙는다.

6.4 킷 update · doctor · repair

  • 3방향 비교 표 전체와 orphan · --prune · --forget 규칙은 02 §3.10에 있다. update는 바꾸기 전 파일과 이전 lock을 .agents/state/backup/<시각>/에 최근 5개까지 둔다(11 §3.8).
  • repair의 missing 복원은 lock의 킷 버전과 CLI 버전이 같을 때만 한다. 다르면 update를 안내한다(다른 판의 내용을 넣지 않는다).
  • CLI가 설치된 킷보다 낮은 버전이면 exit 3이다. 내려가는 update는 --to로 적는다.

6.5 AI-DLC를 켰을 때 승인 가져오기

결정 2026-11-23: AI-DLC는 승인 입력을 사람이 했는지 자기 훅으로 확인하므로, 그 승인을 킷 게이트 승인으로 인정한다. 사람은 같은 게이트를 두 번 승인하지 않는다(README §3, 08 §3.10, 10 §3.2).

  1. add aidlc가 aidlc config --harness <설계 하네스>를 실행하고, 생긴 파일을 external:aidlc로 등록하고, flow.design = "aidlc"로 바꾼다.
  2. 설계 세션에서 사람이 /aidlc를 부르고, 질문 답과 Unit 분해 승인을 AI-DLC 안에서 한다. 킷 /kns-intent는 "설계 단계는 /aidlc가 맡는다"를 출력하고 끝낸다.
  3. npx knots-sync sync aidlc가 AI-DLC 폴더를 읽어 intent.json · units.json을 쓴다. 같은 입력 sha면 아무것도 바꾸지 않고, 다시 가져올 때 sourceId로 Unit의 issue 연결을 지킨다.
  4. AI-DLC 승인 기록에 승인자가 있으면 승인자 · 시각 · 문구를 intents/<INT>/approvals.md에 출처 aidlc로 옮긴다. 승인자가 없으면 옮기지 않고, 그 게이트는 관리 페이지 · approve · Jira 사람 전이로 승인한다.
  5. 그 뒤 기획물 · /kns-specify --from-unit · 게이트 검사 · 관리 페이지는 intent.json이 가리키는 AI-DLC 문서를 읽는다. 구현은 킷 SDD가 맡고, AI-DLC 구현 산출물이 생기면 doctor가 경고한다.

AI-DLC 세션의 그 밖의 대화는 승인이 아니다. AI-DLC가 승인자를 기록에 남기는지는 구현 전에 확인한다(10 §3.2).
