CJ올리브영: 30명, 3일, 과제 5개

AWS 기술 블로그, 2026-05-19. CJ올리브영 9명과 AWS 5명이 함께 썼다.

2026년 3월, CTO를 포함한 테크 조직 30여 명이 AWS 서울 오피스에서 3일짜리 Unicorn Gym 워크숍을 했다. 후보 과제 24개 중 비즈니스 임팩트, 기술 난도, 그린필드/브라운필드 균형을 보고 5개를 골랐다(그린필드 4, 브라운필드 1). 도구는 Kiro, 워크플로는 aidlc-workflows v1 규칙 파일이다.

왜 도입했나

개인 단위 바이브 코딩은 팀으로 가면 무너지는데 사람마다 접근과 품질이 다르고 명세 없이 만든 코드에는 의도와 설계 결정이 남지 않아 리뷰·온보딩·유지보수가 막히기 때문이다. 리더의 질문은 두 가지였다. 팀 전체가 같은 수준과 맥락으로 AI와 협업할 수 있는가, 그리고 그것이 반복 가능한 구조로 자리 잡을 수 있는가.

3일의 흐름

  1. 1일차 오전: 스티어링부터AI-DLC와 Kiro를 익히고 팀별 스티어링 문서를 만들었다. "이 설정이 이후 3일의 생산성을 좌우하는 만큼 오전을 충분히 할애했다."
  2. 1일차 오후: Inception요구사항 정의, 사용자 관점 구체화, 아키텍처 설계, Unit 구성을 진행했다. 개발자는 산출물을 검토하고 승인하는 오케스트레이터 역할을 맡았다. 하루가 끝날 때 기능 설계와 NFR 요구사항까지 마쳤다.
  3. 2일차: Construction전날 회고로 시작했다. Unit마다 코드 생성부터 테스트까지 한 사이클로 처리하고 끝나면 빌드를 통합해 요구사항대로 붙었는지 확인했다.
  4. 3일차: 통합과 배포코드 통합, 인프라 배포, 팀 간 공유와 회고를 했다. 이후 데모데이를 따로 열어 다른 조직에 공유했다.

과제별로 설계를 어떻게 했나

과제설계에서 결정적이었던 것
파트너 채널 자동 검증Inception에서 5개 Unit으로 쪼갰다(데이터 등록, 이미지 분석, AI 검증, 파이프라인 관리, 관리자 화면). 감사 추적과 정확히 한 번(exactly-once) 처리가 필요해 Step Functions Standard Workflow를 골랐다. 이 순차 서버리스 구조는 AI가 Inception에서 직접 제안했다.
장애 보상 자동화현행 프로세스(AS-IS)를 먼저 문서로 정리하고 자동화 범위(TO-BE)를 나눴다. "자동화 대상과 사람이 판단할 영역을 미리 분리하지 않았다면 3일 안에 완성하기 어려웠을 것."
물류센터 시뮬레이션도메인 전문가와 함께 입출력 모델, 최적화 제약, 리스크 지표를 구조화된 설계 문서로 만들었다. AI가 시뮬레이션 루프를 만들고 전문가가 실제 수치로 파라미터를 보정했다.
AI 대화형 검색Bedrock Claude로 구매 의도를 추출하고 OpenSearch 하이브리드 검색과 리뷰 RAG 요약을 붙였다. 사용자 의도를 상품 체계에 매핑하는 색인 설계가 핵심이었다.
백오피스 현대화 (브라운필드)AI가 레거시 UI 솔루션의 전용 문법을 거의 모르는 상태였다. 화면을 UI 컴포넌트 수, 테이블 수, API 호출 수로 4단계 난이도로 나누고 쉬운 것부터 검증했다. 에이전트 다섯(분석, 명세 작성, 코드 생성, 테스트 실행, 보고)을 파이프라인으로 묶었다. 테스트가 실패하면 코드 생성 단계로 되돌아가 최대 3번 재시도한다.

"이번 워크숍의 기술적 핵심은 Kiro의 Spec-Driven 기능이 아니라 AI-DLC 워크플로 저장소에 이미 준비된 스티어링 파일이었다."

통합 단계의 실무 요령도 남겼다. Inception에서 API 계약을 OpenAPI로 먼저 써 두면 Unit이 많아질수록 통합 품질이 올라간다. 통합 문제가 생기면 UI 화면을 캡처해 채팅에 넣거나, 테스트 진행 상황을 마크다운으로 정리해 컨텍스트로 넘겼다.

결과

  • "일반적인 개발 방식 대비 5배 이상 빠른 속도로 5개 비즈니스 과제를 3일 만에 프로토타입 수준으로 구현"
  • 검증 자동화로 건당 평균 5분 걸리던 처리를 10초 이내로 줄였다(최대 30배). 연간 수백 시간 절감을 기대한다.
  • 운영 지연 요인의 40%를 미리 막을 수 있는 가능성, 현대화 일정 50% 단축 기대. 이 둘은 기대치로 적혀 있다.

이들이 꼽은 교훈

  • 프로세스가 품질의 하한선을 만든다. 경험이 적은 사람도 단계를 따라가면 일정 수준 이상의 산출물이 나왔다.
  • Inception의 정제가 Construction의 효율을 정한다. 설계 문서 품질이 높을수록 생성 코드가 정확했다.
  • 품질은 AI를 다루는 솜씨보다 현업 맥락을 구조화하는 능력에 달려 있다.
  • 병렬 개발일수록 인터페이스를 먼저 합의해야 한다. 데이터 구조와 API 규격을 구현 전에 정해야 한다.
  • 현장 데이터 없이 만든 PoC는 실환경까지 이어지기 어렵다.
  • 아직 답이 없는 질문으로 AI 설계를 어디서 멈추고 사람이 개입할지 정하는 기준이 남았다.

샐러드랩: 4명, 매주 목요일 몹

샐러드랩 Tech story, 2026-10. 사이드 프로젝트 TF 사례.

네 명짜리 TF가 근태 관리와 가상 사무실을 합친 메타버스 서비스 Alpha-Town을 만들었다(Next.js, FastAPI, PostgreSQL, Redis, WebSocket). 목적은 개발팀의 AI 역량 강화였다. 역할을 나누지 않고 매주 목요일 한 화면을 같이 보며 "논의 → 구현 → 확인 → 피드백"을 돌렸다. "내 파트가 없으니 병목도 없었다."

지킨 규칙 두 개

AI가 작업을 분석해 [작업명]_plan.md를 쓰고 단계마다 [ ] 체크박스를 단 뒤 승인을 요청한다. 사람이 승인하면 한 단계씩 실행하고 [x]로 바꾼다. 철칙은 두 가지였다.

  • 승인 없이 다음 단계로 넘어가지 않는다.
  • 계획 없이 코드를 만들지 않는다.

그 결과 저장소에 계획 문서 15개, 요구사항 4개, 설계 문서 4개, 프롬프트 이력이 쌓였다. 문서를 쓰려고 쓴 것이 아니라 AI의 컨텍스트를 유지하려다 보니 자연스럽게 남았다.

결과와 교훈

  • 약 2시간 동안 11커밋, 4,686줄. 출퇴근 자동 체크, 일정 CRUD, 충돌을 막는 회의실 예약, 프론트엔드 통합까지 MVP를 마쳤다.
  • 계획이 오히려 속도를 높였다. 방향을 틀며 버리는 작업이 줄었다.
  • 역할이 "코드 치는 사람"에서 "방향 잡는 사람"으로 바뀌었고 처음엔 어색했다.
  • 병목이 기획·디자인으로 옮겨 갔다. 개발이 빨라지니 앞단이 따라오지 못했다.
  • 그린필드에서 더 잘 맞는다고 느꼈다. 브라운필드는 컨텍스트가 크고 계획-승인-실행 사이클을 기존 구조에 맞추기 어렵다.

농심 NDS: 왜 코딩만 빨라지면 안 되나

NDS Cloud Tech Blog, 2026-05. AWS Summit Seoul 2026 세션 후기라 자체 도입 수치는 없다.

도입 사례는 아니지만 AI-DLC가 왜 코딩 너머 생애주기 전체를 다루는지 보여 주는 숫자가 하나 있다. 이 세션은 개발 업무에서 코딩이 약 20%라고 소개했다. 나머지는 설계·분석 30%, 테스트·검증 30%, 소통·조율 20%다. 이 비율을 그대로 두고 코딩만 빨라질 때 전체 시간이 얼마나 줄어드는지 직접 계산하면 아래와 같다.

코딩이 두 배 빨라지면 전체는 10% 준다. 세션이 말한 "코딩을 50% 빠르게 해도 전체는 10%"가 이 줄이다. 다섯 배면 16%, 코딩 시간을 아예 0으로 만들어도 20%가 한계다. 나머지 80%는 설계와 검증, 그리고 개발·QA·보안·운영·DBA 사이의 대기에 있다. AI-DLC가 코드 생성보다 Inception의 질문과 결정, 연속 검증, 몹이라는 조율 방식을 먼저 바꾸려는 이유가 이 그래프다.

글이 정리한 도입 요령은 세 가지다.

  • 계층적으로 쪼갠다. 팀 → 파트 → "AI가 한 번에 처리할 수 있는 가장 안정적인 작은 단위"까지 내려간다.
  • 앞 단계 산출물을 강제로 주입한다. AI는 정보를 본능적으로 요약하려 해서 제약이 빠진다. 이전 단계의 산출물과 제약을 다음 단계 입력에 반드시 넣도록 구성한다.
  • 작은 파일럿부터 시작한다. 위키·Jira·파이프라인 같은 외부 컨텍스트도 참조하게 한다.

해설 글의 고유한 관점

글다른 글에 없는 관점
위키독스, 『함께해요 바이브 코딩』v1과 v2를 구분한다. 2026-11 기준 v2 문서에는 규칙 파일 복사 방식과 aidlc-docs/ 구조가 더 이상 나오지 않는다. 한 줄 수정이나 간단한 버그에는 부담이니 bugfix·express 프로필로 먼저 익히라고 권한다.
파이토치 한국 사용자 모임v2의 구조를 가장 자세히 소개한다. 결정적 엔진이 다음 스테이지를 정하고 사람의 실제 메시지가 있어야 승인 게이트가 열린다. Claude Code와 Codex CLI가 가장 적은 공백으로 동작한다. 토큰 비용이 크고 사람 없이 CI에서 끝까지 돌리는 용도에는 맞지 않는다.
개발자 조한빈"AI-DLC는 문서로 배우는 개념이 아니다." 직접 해 보는 것과 사내 개발 도구에 녹여 두는 것을 권한다. 결론은 "문제는 개발 문화 자체가 변하지 않으려는 점"이다.
sddevAI-DLC를 "컨텍스트 문서를 잘 정리해 시스템 프롬프트 삼아 개발하는 기법"으로 본다. Unit 사이는 Integration Contract 문서로 맞춘다. 반대 방향의 경고도 남긴다. 너무 잘게 나누면 Inception에 에너지를 다 쓰고 사람마다 모듈 하나씩만 맡는 사일로가 생긴다.
Feccle사람이 깊게 파야 할 곳을 구체적으로 짚는다. 동시성 락, 트랜잭션 경계, 레거시 호환성이다. "AI는 넓고 빠른 초안, 사람은 좁고 깊은 장애 예측." 테스트는 통과하지만 동시 요청에서 데드락이 나는 코드가 대표 사례다. 글에 나오는 명령어 예시는 공식 명령과 다르니 개념만 참고한다.

공통 성공 조건

여러 자료에 반복해서 나온 순서대로 적었다.

  1. 앞단을 먼저 정제한다. "Inception의 정제가 Construction의 효율을 극대화"(CJ), "계획이 오히려 속도를 높인다"(샐러드랩).
  2. 승인을 명시적으로 받는다. 모든 자료가 "AI 제안, 사람 승인"을 말한다. v2는 이것을 사람의 실제 메시지로 강제한다.
  3. 산출물로 컨텍스트를 잇는다. 각 단계 산출물이 다음 단계의 입력이 된다. 파일로 넘기니 에이전트를 바꾸거나 다시 돌리기 쉬웠다(CJ).
  4. 작게 쪼갠다. 느슨하게 결합되고 응집도가 높은 Unit, AI가 한 번에 안정적으로 처리할 수 있는 크기.
  5. 인터페이스와 계약을 먼저 정한다. OpenAPI 계약(CJ), Integration Contract(sddev), v2의 계약 설계 스테이지.
  6. 스티어링·규칙을 첫날 깐다. "3일의 생산성을 좌우"(CJ).
  7. 팀이 함께 본다. 몹, 팀 리뷰, 데모데이. 개인별 활용은 사일로를 만든다.
  8. 도메인 전문가와 실데이터를 들인다. 전문가가 파라미터를 보정하고 현장 데이터로 검증해야 PoC가 실환경으로 간다.

공통 실패 패턴

이런 신호가 보이면 멈추고 고친다

  • 작은 작업에 전체 절차를 돌린다. 한 줄 수정에 Inception 전체는 과하다. 프로필이나 단계 건너뛰기로 깊이를 줄인다.
  • 테스트는 통과하는데 동시 요청에서 깨진다. 락 범위와 트랜잭션 경계는 사람이 직접 설계한다.
  • AI가 앞 단계 제약을 요약하다 빠뜨린다. 산출물을 다음 단계 입력으로 명시해서 넣는다.
  • 레거시 규칙과 충돌한다. 지켜야 할 기존 규칙을 스티어링에 명시한다.
  • 병목이 기획·승인으로 옮겨 간다. 생성은 빨라졌는데 결정이 늦으면 대기열만 길어진다.
  • 현장 데이터 없이 PoC를 만든다. 데모는 되지만 운영으로 가지 못한다.
