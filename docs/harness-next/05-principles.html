AI-DLC를 지키고, 각자 고쳐 쓰는 하네스

킷은 AI-DLC 방법론을 구현하는 하네스다. AI-DLC 실행 도구(aidlc-workflows)를 켜든 끄든 원칙 다섯 가지는 킷이 지킨다. 이 장은 원칙마다 킷이 무엇으로 지키는지, 채널톡 사례에서 무엇을 가져오고 버리는지, 사람이 맡는 일과 폴더의 주인, 회사·팀·개인이 하네스를 고쳐 쓰는 방법을 적는다.

방법론과 도구를 나눈다

AI-DLC 방법론aidlc-workflows 도구
무엇세 단계, 대화 방향 역전, Unit·Bolt, 승인 게이트, 문서로 남는 맥락원칙을 돌리는 엔진(2.x: 다섯 페이즈, 33개 스테이지)
킷에서항상 지킨다. 킷의 흐름·명령·게이트가 곧 구현이다선택 모듈(flow.design = "aidlc"). 켜면 설계 단계를 대신 돌린다

그래서 "AI-DLC를 개발 방법론으로 한다"는 말은 도구 설치와 별개다. 킷만 쓰는 리포도 AI-DLC로 일한다.

원칙 다섯 가지

원칙킷이 지키는 방법기계로 막는 것빈 곳 → 보완
세 단계
(2.x 다섯 페이즈)		Initialization = harness-kit init · Ideation = 요구사항 접수 · Inception = /hx-intent와 기획물 · Construction = SDD와 검증 · Operations = 반영·배포·운영 기록앞 문서가 approved가 아니면 다음 문서를 만들지 못한다(check-sdd-prerequisites)배포 계획·롤백·배포 승인이 없다 → P24
대화 방향 역전단계 명령마다 AI가 먼저 계획·질문·대안을 내고 사람이 고른다. /hx-clarify는 질문 최대 5개에 선택지와 권장안, /hx-plan은 대안과 버린 이유(ADR), /hx-tasks는 작업 계획을 내고 승인을 받는다[NEEDS CLARIFICATION]이 남은 문서는 승인할 수 없다선택지를 눌러 답하는 화면이 없다 → P20 관리 페이지
Unit · BoltUnit = 이슈 하나 = SDD 폴더 하나 = 브랜치·MR 하나. Bolt = tasks의 Phase(수 시간~수 일). Bolt마다 바꾼 기능만 검증한다브랜치 이름과 이슈 키의 대응(git 훅), 이슈 폴더당 tasks 한 벌Unit을 나눌지 정하는 기준 → P21, Bolt 진행 보기 → P20
승인 게이트Intent·Unit → 기획물 → requirements → design → tasks 계획 → MR → 완료 → 배포. 단계마다 사람이 승인한다. 일의 크기와 위험에 따라 줄이는 것은 문서 분량이고, 승인은 건너뛰지 않는다지금은 상태값만 본다. AI-DLC를 켜면 AI-DLC가 사람 입력을 훅으로 확인한다. 킷은 그 기록에 승인자가 있으면 approvals.md로 옮겨 승인으로 인정하고, 없으면 킷 경로로 승인받는다누가 언제 승인했는지 강제하지 못한다 → P23 approvals.md와 훅
맥락이 문서로Intent·Unit, SDD 세 문서, 질문과 답, ADR, 승인 기록, 리뷰 결과, 인수인계, 운영 기록이 모두 리포에 남는다. Entire를 켜면 대화 원문까지오래된 초안·미해결 질문 보고(check-spec-freshness)관리 페이지에서 저장한 문서도 그 이슈 브랜치에 커밋돼야 한다 → P20

다섯 가지 모두 흐름은 이미 있다. 약한 곳은 셋이다. 배포 단계, 승인을 사람이 실제로 했는지 강제하는 장치, 사람이 선택지를 고르고 답하는 화면이다. 각각 P24·P23·P20에서 채운다.

채널톡 사례: 가져올 것과 버릴 것

02장의 하네스별 역할은 채널톡 사례에서 왔다. AI-DLC 기준으로 다시 거르면 반은 맞고 반은 어긋난다.

채널톡이 한 것AI-DLC와킷에서
이슈마다 워커 세션맞다. Unit마다 Bolt를 돌린다가져온다: 이슈 하나 = 세션 하나
Claude가 쓰고 Codex가 리뷰맞다. 사람 리뷰를 대신하지 않고 더한다가져온다: 실행 배치 기본값
처리할 일을 한 화면에맞다가져온다: 관리 페이지 "처리할 일"
회고 제안을 규칙 파일 커밋으로맞다. 배운 것을 규칙으로 되돌린다가져온다: 운영 기록 → 규칙 변경 MR
병합 뒤 자동 배포·E2E, 두 번 실패하면 멈춤맞다(Operations)가져온다: CI 템플릿 선택 단계
사람은 요구사항이 모호할 때와 머지 직전 두 곳에서만 멈춘다어긋난다. 단계마다 승인한다버린다. 04장의 같은 문장을 고쳤다
PM 세션이 병합·리뷰 요청·보류를 판정어긋난다. 판정은 사람이 한다버린다. 관리 페이지는 모아서 보여 주기만 한다
별도 스펙 문서 없이 계획만 확정어긋난다. 문서가 다음 단계의 맥락이다버린다. SDD 문서를 유지한다

사람 역할과 실행 배치

02장의 역할 표는 에이전트 작업을 어느 하네스가 돌리는지(실행 배치)다. AI-DLC가 말하는 역할은 사람의 역할이고, 승인 게이트마다 누가 승인하는지로 드러난다. 둘을 나눠 적는다.

사람 역할승인하는 것함께 일하는 실행 배치
PO요구사항, 범위 밖, 우선순위, Unit 분해, 기획물설계 세션(Claude Code, AI-DLC를 켰으면 AI-DLC)
개발자design의 트레이드오프, tasks 계획, 리뷰 지적 판단, MR구현 세션(Claude Code), 리뷰 세션(Codex)
QA수용 기준이 시험 가능한지, 검증 결과, 완료리뷰 세션, 스캐너, CI
운영배포, 운영 기록, 다음 요구사항 선택문서 세션(Kiro)

한 사람이 여러 역할을 맡아도 된다. 게이트마다 승인할 수 있는 사람은 harness-kit.json의 approvers에 적고, 관리 페이지와 승인 기록이 그 목록을 따른다.

사람이 하는 일

사람은 결정을 한다. 초안 쓰기, 폴더 사이 복사, 보드·HTML 갱신, tasks 파일 옮기기는 에이전트와 도구가 한다.

시점사람이 하는 일어디서
요구사항 접수한두 문단으로 요구사항을 적는다관리 페이지 "새 요구사항" 또는 Jira 이슈
설계 질문AI가 낸 질문에 답하고 선택지를 고른다관리 페이지 문서 화면(질문 파일)
Intent·Unit 승인범위와 분해를 승인한다관리 페이지 승인 버튼, 사람 터미널의 harness-kit approve, Jira 사람 전이. AI-DLC를 켜면 AI-DLC 안에서 한 승인도 인정한다. AI-DLC가 사람 입력을 직접 확인하므로, 킷이 그 기록을 approvals.md로 옮긴다(두 번 승인하지 않는다)
문서 승인기획물·requirements·design·tasks 계획을 승인하거나 고쳐서 돌려보낸다관리 페이지 승인 버튼, 사람 터미널의 harness-kit approve, Jira 사람 전이. 채팅에서 한 말은 승인이 아니다. 승인할 때 넣은 문구는 approvals.md에 누가·언제와 함께 남는다

규칙 변경규칙·게이트 변경 MR을 승인한다GitLab

이슈 키

  • Jira를 쓰면 Jira 키를 그대로 쓴다. 폴더 issues/HDRV3D-12-upload-cleanup/, 브랜치 feat/HDRV3D-12-upload-cleanup, worktree HDRV3D-12-upload-cleanup, MR·커밋 제목의 키가 모두 같다.
  • Jira가 없으면 킷이 같은 모양으로 만든다. <프로젝트키>-<번호>-<짧은 이름>, 예: KNOTS-17-desktop-parity. 프로젝트키는 harness-kit.json의 issueKey.prefix, 번호는 기본 브랜치에 있는 가장 큰 번호 + 1이다. 같은 번호가 두 브랜치에서 생기면 MR 때 검사가 잡는다.
  • 짧은 이름은 요구사항에서 영문 kebab-case로 만든다(3~5단어). 한글·공백·대문자는 쓰지 않는다.
  • jira-workflow 모듈을 켜면 /hx-intent가 Unit마다 Jira 이슈를 만들고 받은 키로 폴더를 만든다.
  • 지금의 영역 폴더(<영역>-specs)는 폴더가 아니라 requirements 머리의 area: 값이 되고, 보드와 관리 페이지가 이 값으로 묶어 보여 준다.

Jira를 AI-DLC에 맞추기

Jira를 쓰는 팀은 Jira 구조도 AI-DLC 단위와 승인 게이트에 맞춘다. 문서의 원본은 리포이고, Jira에는 상태·담당·링크를 둔다. Jira가 없어도 같은 상태표를 관리 페이지 보드가 쓴다.

  • 승인 상태로 옮기는 것은 사람만 한다. Jira 워크플로 조건으로 승인 전이를 사람 그룹으로 제한하고, 사람이 옮긴 기록(누가 · 언제)을 킷이 approvals.md로 가져온다.
  • 단계가 바뀌면 킷이 Jira 상태와 링크(SDD 경로 · MR · 체크포인트)를 갱신한다. 지금 있는 jira-workflow 모듈을 이 대응으로 고친다(P21). 연결은 Atlassian Rovo MCP 서버나 Jira API로 한다.
  • Agentic engineering 템플릿(Jira Cloud, 2026-07-15): 코딩 에이전트용 워크플로가 미리 깔린 공간 템플릿이다. 조직에 Rovo가 켜져 있어야 보인다. 만들 때 상태를 고르고 나중에 바꿀 수 있으므로, 템플릿으로 공간을 만든 뒤 위 상태표로 고친다. 템플릿의 기본 상태 목록은 Atlassian 문서에 없어서 만들어 보고 대응시킨다.
  • Jira에서는 작업 항목을 Claude Code·Cursor·Copilot에 바로 배정할 수 있다. 이렇게 배정된 에이전트도 리포의 AGENTS.md·규칙·검증 게이트를 따른다. 그 MR에도 같은 CI 검증과 승인 기록 검사를 걸어 로컬 하네스를 우회하지 못하게 한다.

하네스 고쳐 쓰기

회사마다, 팀마다, 사람마다 하네스에 더하고 싶은 것이 다르다. 킷은 고쳐 쓴 것을 네 층으로 나눠 업데이트가 지우지 않게 한다.

층누가어디에커밋킷 업데이트 때
1 킷 기본킷.agents/(주인 kit)예교체. 사람이 고친 파일은 .new로 옆에
2 회사 팩회사·사업부별도 git 리포나 npm 패키지. packs에 적으면 .agents/에 배치(주인 pack:<이름>)예팩 버전을 올릴 때만 같은 규칙으로 교체
3 프로젝트리포 팀.agents/ 안 팀 파일(주인 user)예건드리지 않는다
4 개인개인.agents/local/, 사용자 스킬 폴더아니오건드리지 않는다
  • 같은 이름이면 프로젝트 → 회사 팩 → 킷 순으로 앞의 것이 이긴다.
  • 개인 층은 더하기만 한다. 검증 게이트·승인 게이트·보호 경로를 끄거나 약하게 하는 개인 설정은 무시하고 doctor가 경고한다.
  • 관리 페이지의 하네스 탭과 doctor가 고쳐 쓴 것(어느 층이 무엇을 덮었나)을 보여 준다.
  • 여러 팀에 쓸모 있는 프로젝트 확장은 회사 팩으로, 회사 밖에도 쓸모 있으면 킷으로 올린다. knots의 역수출 도구(kit_export)가 하던 일을 이 경로로 정리한다.
