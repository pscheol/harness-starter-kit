# 하네스 아키텍처 — 설계 원리와 근거

이 문서는 **왜 이런 구조인지**를 설명한다. 무엇이 있는지는 [`README.md`](./README.md), 무엇을 채워야 하는지는 [`CUSTOMIZE.md`](./CUSTOMIZE.md).

---

## 전제: 에이전트는 세션마다 기억을 잃는다

사람 팀원에게는 "지난번에 말했잖아"가 통한다. 에이전트에게는 통하지 않는다.

여기서 하네스의 제1원칙이 나온다.

> **반복해야 할 것은 전부 저장소에 인코딩한다. 인코딩되지 않은 것은 존재하지 않는 것과 같다.**

두 번째 전제는 컨텍스트가 유한하다는 것이다. 모든 규칙을 항상 로드하면 정작 작업할 여유가 없다. 그래서 **항상 필요한 것**과 **가끔 필요한 것**을 물리적으로 분리해야 한다.

이 두 전제가 아래 5계층을 만든다.

---

## 계층 1: 진입점 — 하나의 원본, 여러 개의 거울

```text
AGENTS.md          ← 원본 (단일 진실)
CLAUDE.md          → AGENTS.md         (심볼릭)
.claude/skills     → .agents/skills    (심볼릭)
```

### 왜 심볼릭인가

도구마다 자동 로드하는 파일명이 다르다. Claude Code는 `CLAUDE.md`, Codex는 `AGENTS.md`, 다른 도구는 또 다르다.

사본을 두면 **반드시** 드리프트가 생긴다. 한쪽만 고치는 일이 100% 일어나고, 그때부터 도구에 따라 에이전트가 다르게 행동한다. 이건 디버깅이 거의 불가능한 종류의 버그다.

그래서 원본은 하나만 두고 나머지는 전부 심볼릭으로 비춘다.

### Windows 문제

Windows는 개발자 모드나 관리자 권한 없이는 심볼릭을 못 만든다. `bootstrap-harness.cjs`는 심볼릭 실패 시 **하드 카피로 폴백**하되, **매 실행마다 새로 복사**해 드리프트를 막는다. `verify-harness.cjs`는 하드 카피본과 원본의 내용이 어긋나면 실패로 잡는다.

### 진입점은 목차다

`AGENTS.md`가 비대해지면 아무도(에이전트도) 끝까지 읽지 않는다. 그래서 예산을 둔다.

```json
"budget": { "agentsMdMaxLines": 250, "claudeMdMaxLines": 120 }
```

초과하면 `verify-harness`가 경고한다. **경고를 없애는 방법은 내용을 지우는 게 아니라 `.agents/`로 옮기는 것이다.**

## 계층 2: 정책 — 항상 적용되는 규칙

```text
.agents/rules/*.md
```

### 규칙 파일의 형태가 정해져 있는 이유

모든 규칙은 같은 5단 구조를 갖는다.

| 섹션                 | 목적                                    |
| -------------------- | --------------------------------------- |
| frontmatter          | 적용 대상·경로·우선순위 (기계가 읽는다) |
| 무엇을               | 지시                                    |
| 왜                   | **근거**                                |
| 어떻게               | 적용 방법과 예시                        |
| 자동화로 잡히는 영역 | 여기 적힌 것은 리뷰에서 언급 금지       |
| 안티-규칙            | 이 규칙을 근거로 하면 안 되는 지적      |

"왜"와 "안티-규칙"이 핵심이다.

- **"왜"가 없으면** 규칙은 첫 반박에 무너진다. 에이전트는 근거 없는 지시를 만나면 상황에 따라 무시한다.
- **"안티-규칙"이 없으면** 규칙이 과잉 적용된다. 리뷰어 에이전트가 "코드 스타일 규칙이 있으니 스타일을 지적해야지"라고 판단하는 순간, 자동화가 이미 처리한 것을 다시 지적하기 시작한다.

### 자동화 위임 선언

각 규칙에는 "자동화로 잡히는 영역" 체크리스트가 있고, 거기 적힌 항목은 **리뷰 코멘트 금지**다.

이건 스타일 문제가 아니라 **어텐션 예산 문제**다. 포매터가 이미 처리하는 들여쓰기를 모델이 확인하면, 그 토큰만큼 로직 검토가 줄어든다.

### negative knowledge

`pr-review-policy.md`에는 "지적하지 말 것" 표가 있다. **알지만 지금은 안 고치기로 한 것**의 목록이다.

이 표가 비어 있으면 리뷰어는 매번 같은 것을 지적하고, 그 지적은 매번 무시된다. 몇 번 반복되면 리뷰 출력 전체가 무시된다.

## 계층 3: 절차 — 도메인 진입 시에만 로드

```text
.agents/skills/_project/<도메인>/SKILL.md
.agents/skills/<도메인>/  ← 평면 심볼릭 (자동 생성)
```

### rules vs skills

|           | rules                  | skills                    |
| --------- | ---------------------- | ------------------------- |
| 로드 시점 | 항상                   | 해당 도메인 작업 시       |
| 내용      | "무엇을 지켜야 하는가" | "이 작업은 어떻게 하는가" |
| 분량      | 짧게                   | 필요한 만큼               |

이 분리가 스킬의 존재 이유 전부다. 도메인 절차를 rules에 넣으면 관련 없는 작업에서도 매번 로드된다.

### description이 전부다

스킬은 **description 한 줄로 로드 여부가 결정**된다. 본문이 아무리 좋아도 description이 매칭되지 않으면 절대 로드되지 않는다.

```text
✅ "Use when adding a payment provider, changing refund logic, or touching billing/*.ts."
❌ "결제 관련 가이드"        — 추상적이라 매칭 안 됨
❌ "결제 API 사용법"         — 모델이 이미 아는 일반 지식과 중복
```

패턴: **"어떤 작업·파일에서 호출하는가" + "무엇을 다루는가"**.

### 평면 심볼릭

일부 도구의 스킬 탐색 글롭은 `*/SKILL.md` **한 단계**다. 원본이 `_project/<name>/SKILL.md`에 있으면 닿지 않는다.

원본 하나에서 자동으로 별칭을 만들어 해결한다. `bootstrap-harness.cjs`가 `_project/`를 스캔하므로 **스킬을 추가할 때 스크립트를 고칠 필요가 없다.** 별칭 목록을 스크립트에 하드코딩하면 스킬을 추가할 때마다 두 곳을 고쳐야 하고, 한쪽을 빠뜨리면 스킬이 조용히 로드되지 않는다.

## 계층 4: 기록 — SDD와 지식 베이스

```text
.agents/docs/
├── product-specs/<작업단위>/{requirements,design,tasks}.md   ← 작업 명세
├── product-specs/index.md                                    ← 단일 카탈로그
├── exec-plans/{active,completed}/                            ← 상위 계획
├── design-docs/                                              ← 방법론
├── knowledge/source-index.md                                 ← 외부 근거 ID
└── references/                                               ← 외부 문서 캐시
```

### 왜 세 파일로 나누는가

| 파일         | 질문        | 섞이면 생기는 일                            |
| ------------ | ----------- | ------------------------------------------- |
| requirements | 무엇을 / 왜 | 요구사항이 확정되기 전에 구현 방식이 굳는다 |
| design       | 어떻게      | 설계 근거가 사라지고 나중에 재논쟁된다      |
| tasks        | 지금 무엇을 | 진행 상태를 추적할 수 없다                  |

특히 requirements와 design을 섞으면, **"이 요구사항이 맞나"라는 질문과 "이 구현이 맞나"라는 질문을 동시에 못 한다.**

### tasks.md 체크박스가 상태의 단일 진실

여러 도구·여러 세션이 같은 작업을 이어받는다. 진행 상태를 도구 밖(사람의 기억, 채팅 이력)에 두면 다음 세션이 같은 작업을 중복 시도한다.

그래서:

- 체크박스는 `- [ ]`와 `- [x]` **두 상태만**. `- [~]` 같은 변형은 도구 간 호환성이 없다.
- 코드 변경과 체크박스 갱신은 **같은 커밋**에.
- `verify-harness`가 변형 체크박스를 실패로 잡는다.

### index.md 정합성 검사

spec 폴더를 만들고 색인에 등록하지 않으면 카탈로그에서 사라진다. 사라진 명세는 없는 명세다.

`verify-harness`가 폴더 ↔ 색인 정합성을 검사한다. **문서 규율을 사람의 성실함이 아니라 스크립트에 맡긴다.**

### Source ID

경로와 URL은 바뀐다. 외부 근거에 안정적 ID를 부여하고 문서에서는 ID로 인용하면, 자료가 이동해도 인용이 깨지지 않는다.

`source-index.md`에 `TBD`로 남은 근거가 필요한 작업은 **구현하지 않는다.** 명세 없이 추측으로 만든 API 클라이언트보다, 명세를 요구하며 멈추는 쪽이 싸다.

## 계층 5: 실행 — scripts/가 진실

```text
scripts/
├── harness-config.cjs           # 공용 설정 로더
├── assert-harness-context.cjs   # SessionStart: 하네스 없이 시작 차단
├── install-pkgs-if-remote.cjs   # SessionStart: 원격 환경만 설치
├── format-and-lint-hook.cjs     # PostToolUse: 편집 파일만 포맷·린트
├── bootstrap-harness.cjs        # 심볼릭 생성 (idempotent)
├── precommit.cjs                # 커밋 전 통합 게이트
└── verify-harness.cjs           # 하네스 계약 회귀 검사
```

### 어댑터는 얇다

```text
.claude/settings.json  ─┐
                        ├─→  scripts/*.cjs   ← 실제 구현
.codex/hooks.json      ─┘
```

도구 설정에는 **어느 스크립트를 언제 부르는지**만 있다. 로직은 없다.

이 구조 덕분에:

- 새 도구를 붙일 때 어댑터만 추가하면 정책이 자동으로 따라온다
- 로직을 고칠 때 한 곳만 고치면 모든 도구에 반영된다
- 두 어댑터가 다른 스크립트를 부르기 시작하면 `verify-harness`가 **드리프트로 경고**한다

마지막 항목이 중요하다. 하네스가 조용히 깨지는 가장 흔한 경로가 "한쪽 도구 설정만 고침"이다.

### harness.json — 프로젝트 종속성의 단일 격리 지점

하네스 스크립트에 프로젝트 값을 직접 적으면(런타임 버전 요구, `npm run lint`, 특정 가드 호출) 스택이 바뀔 때마다 스크립트를 고쳐야 한다. 그러면 하네스를 다른 저장소로 옮길 수 없고, 옮기더라도 곧 두 벌로 갈라진다.

그래서 달라지는 값은 전부 `.agents/harness.json` 하나로 뺀다.

```json
{
  "runtime": { "packageManager": "npm", "minNodeMajor": 20 },
  "commands": { "lint": "...", "typecheck": "...", "test": "..." },
  "format": { "formatCommand": "...", "lintFixCommand": "..." },
  "guards": [{ "name": "...", "command": "...", "enforceEnv": "..." }],
  "budget": { "largeFileThreshold": 800 }
}
```

효과: **스택이 바뀌어도 스크립트를 고치지 않는다.** Python 프로젝트든 Go 프로젝트든 설정 파일 하나만 다르다.

### precommit 단계 순서에는 이유가 있다

```text
1. 런타임 확인   버전이 틀리면 아래 결과가 전부 신뢰할 수 없다
2. 포맷          이후 단계의 diff 잡음을 없앤다
3. 하네스 계약   규칙 문서 자체가 깨졌는지 먼저 본다
4. lint          가장 싸고 가장 많이 잡는다
5. typecheck     lint보다 느리고 더 정확하다
6. 도메인 가드   프로젝트 고유 불변 조건
7. test          가장 느리므로 마지막
```

원칙은 **싼 것부터, 넓은 것부터**다.

### SKIP\_\*를 허용하는 이유

모든 단계는 환경변수로 우회 가능하다. 우회를 막으면 사람이 **게이트 자체를 건너뛴다**. `--no-verify`로 커밋하거나 훅을 지운다.

그래서 우회는 허용하되 **눈에 보이게** 한다. 로그에 남고, 생략 사유를 기록하도록 규칙이 요구한다.

### 가드는 경고로 시작한다

새 가드를 처음부터 강제하면 기존 위반이 전원의 커밋을 막고, 가드는 제거된다.

```text
1. 문서       golden-rules 불변 조건 표      알고는 있으나 안 지켜진다
2. 경고 가드  harness.json#guards            위반이 보인다
3. 강제 가드  enforceEnv=1                   위반이 막힌다
```

**2단계를 건너뛰지 않는다.**

## 전체 흐름

```text
세션 시작
  └→ assert-harness-context   하네스 없으면 exit 1
  └→ install-pkgs-if-remote   원격 환경만

작업 착수
  └→ AGENTS.md (목차) + 관련 rules 로드
  └→ 도메인 진입 시 SKILL.md 로드
  └→ reuse-before-new: 기존 owner 검색
  └→ product-specs/<작업단위>/ SDD 작성

구현
  └→ tasks.md 최소 단위 하나
  └→ 편집마다 format-and-lint-hook

검증
  └→ verification-ladder로 수준 결정
  └→ 대상 테스트 → precommit
       └→ verify-harness (하네스 계약)
       └→ guards (프로젝트 불변 조건)

마무리
  └→ tasks.md 체크박스 + 코드 = 같은 커밋
  └→ QUALITY_SCORE 자체 검토
  └→ 검증 결과·생략 사유·잔여 위험 보고
```

## 이 구조가 막는 실패 모드

| 실패 모드                      | 방어 장치                             |
| ------------------------------ | ------------------------------------- |
| 규칙 없이 세션이 시작됨        | `assert-harness-context` (exit 1)     |
| 도구마다 다르게 행동함         | 심볼릭 + 어댑터 드리프트 검출         |
| 진입점이 비대해져 안 읽힘      | 토큰 예산 경고                        |
| 같은 작업 중복 구현            | `tasks.md` 체크박스 + 한 슬롯 규칙    |
| 명세가 카탈로그에서 사라짐     | `index.md` 정합성 검사                |
| 기존 owner 두고 새로 만듦      | `reuse-before-new` Inventory 의무     |
| 자동화 항목을 리뷰가 반복 지적 | 자동화 위임 선언 + negative knowledge |
| 검증 생략이 통과로 읽힘        | 생략 사유 기록 의무                   |
| 회귀가 반복됨                  | 불변 조건 → 가드 승격 경로            |
| 부채가 매번 새로 논쟁됨        | tech-debt-tracker                     |
| 추측으로 만든 API 클라이언트   | Source ID `TBD`면 구현 중단           |

## 확장 방법

| 추가하려는 것  | 위치                                         | 잊지 말 것                      |
| -------------- | -------------------------------------------- | ------------------------------- |
| 새 정책        | `.agents/rules/<name>.md`                    | `AGENTS.md` 규칙 색인에 한 줄   |
| 새 도메인 절차 | `.agents/skills/_project/<name>/SKILL.md`    | 부트스트랩 실행 + 스킬 카탈로그 |
| 새 검증        | `scripts/<name>.cjs` + `harness.json#guards` | 경고로 시작                     |
| 새 도구 지원   | `adapters/.<tool>/`                          | 기존과 **같은 스크립트**를 호출 |
| 새 작업 명세   | `product-specs/<작업단위>/`                  | 같은 커밋에 `index.md` 등록     |
