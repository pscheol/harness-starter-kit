# Spec-Driven Workflow — {{PROJECT_NAME}}

> 여러 도구·여러 세션이 **같은 작업 명세를 공유**하게 만드는 규약이다.

## 핵심 원칙

1. **`.agents/docs/product-specs/`가 작업 명세의 단일 위치**다. 모든 도구가 여기를 활성 명세의 단일 진실로 본다.
2. **`tasks.md` 체크박스가 진행 상태의 단일 진실**이다. 누가 어느 도구로 끝냈든 `[ ]` → `[x]`로 바꾸고 커밋한다.
3. **명세는 기획·기록 허브, 에이전트는 실행 허브**다. 산출물은 모든 도구가 읽고 쓸 수 있다.
4. **도구별 명세 사본을 만들지 않는다.** `.claude/specs/`, `.codex/specs/` 같은 구조는 동기화 지옥이다.

## 디렉터리 구조

```text
.agents/docs/product-specs/
├── index.md                  # 전체 작업 단위 색인 (단일 카탈로그)
├── _templates/               # 신규 작업 단위 시작점
│   ├── requirements.md
│   ├── design.md
│   └── tasks.md
└── <작업단위>/
    ├── requirements.md       # 무엇을/왜 — 수용 기준, 테스트 가능한 요구사항
    ├── design.md             # 어떻게 — 기존 owner, 영향 범위, 위험, 비범위
    └── tasks.md              # 실행 — 체크박스 + 검증 방법
```

작업 단위 이름은 `<식별자>-<짧은-슬러그>` 형식을 권장한다 (예: `PRJ-123-login-retry`).

**새 폴더를 추가하면 같은 커밋에서 `index.md`에도 한 줄 추가한다.** `scripts/verify-harness.cjs`가 이 정합성을 검사한다.

## 문서 경계

| 위치                        | 용도                                           | 만들지 말아야 할 것 |
| --------------------------- | ---------------------------------------------- | ------------------- |
| `product-specs/<작업단위>/` | 개별 기능/티켓의 requirements·design·tasks     | —                   |
| `design-docs/`              | 반복 적용되는 방법론, 운영 의사결정            | 개별 티켓 폴더      |
| `exec-plans/active/`        | 여러 티켓·여러 저장소·장기 rollout의 상위 계획 | 개별 티켓 폴더      |
| `references/`               | 외부 문서 요약·캐시                            | 원본 대용량 자산    |

## Spec 필요 여부

| 작업                                          | Spec                |
| --------------------------------------------- | ------------------- |
| 단일 파일 1~2줄 수정, 단일 컴포넌트 내부 변경 | ❌ 즉흥             |
| 여러 파일에 걸친 변경                         | ⚠️ 가벼운 spec 권장 |
| 이슈 트래커 기반 코드 영향 구현               | ✅ 필수             |
| 공개 계약(API/스키마/채널/설정) 변경          | ✅ 필수             |
| 거대 파일 리팩터링, 의존성 메이저 전환        | ✅ 필수             |

## 작업 흐름

### 채팅에서 시작할 때

1. 먼저 `.agents/docs/product-specs/`를 확인한다. 관련 spec이 있으면 그것을 입력으로 쓴다.
2. 관련 spec이 없고 작업이 단순하면 즉흥으로 진행한다.
3. 관련 spec이 없고 작업이 복잡하면 **spec 작성을 먼저 제안**한다.
4. 작업 완료 후 해당 `tasks.md` 체크박스를 갱신한다.

### 기존 spec을 이어받을 때

1. `requirements.md`와 `design.md`를 읽어 맥락을 잡는다.
2. `tasks.md`에서 **첫 번째 미완료 체크박스 하나**를 고른다.
3. 구현 → 검증 → 체크박스 갱신 순으로 진행한다.
4. 설계와 구현이 어긋나면 **먼저 `design.md`를 갱신한 뒤** 구현한다.

## tasks.md 작성 규약

```markdown
## 1단계: 준비

- [x] 1.1 기존 owner 조사
  - 내용: 무엇을 만드는가
  - 파일/모듈: `{{SOURCE_DIR}}/...`
  - 검증: 어떤 명령으로 확인하는가
  - 요구사항: R1.1
  - 설계: design §4

## 2단계: 구현

- [ ] 2.1 ...
```

체크박스는 `- [ ]`와 `- [x]` **두 상태만** 사용한다. `- [~]` 같은 변형은 도구 간 호환성이 없고, `scripts/verify-harness.cjs`가 실패로 잡는다.

## 갱신 의무

작업 완료 시:

1. 해당 태스크 체크박스를 `[x]`로 바꾼다.
2. **코드 변경과 같은 커밋**에 포함한다.
3. 커밋 메시지에 작업 단위를 남긴다: `<요약> [tasks: <작업단위>#2.1]`

갱신을 빠뜨리면 다음 세션의 다른 도구가 같은 작업을 중복 시도하고, 진행률 추적이 불가능해진다.

## Anti-Patterns

- ❌ 공개 계약을 spec 없이 변경 — 영향 범위 누락
- ❌ 체크박스 갱신 없이 코드만 커밋 — 상태 불일치
- ❌ 도구마다 spec 사본 생성 — 동기화 지옥
- ❌ `index.md` 등록 없이 spec 폴더 추가 — 카탈로그에서 사라짐
- ❌ 거대 파일 리팩터링을 spec 없이 즉흥 진행
