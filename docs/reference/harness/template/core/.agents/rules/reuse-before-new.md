# Reuse Before New — {{PROJECT_NAME}}

## 원칙

새 기능·컴포넌트·헬퍼·스타일·테스트를 만들기 전에 **반드시 기존 구현을 먼저 찾고 판단**한다.

에이전트는 검색보다 생성이 싸기 때문에, 명시적으로 막지 않으면 항상 새로 만든다. 그 결과가 병렬 owner와 중복 구현이다.

1. 기존 코드에 같은 기능이 있는지 확인한다.
2. 같은 역할의 owner(컴포넌트·서비스·스타일)가 있는지 확인한다.
3. 확장할지, 공통으로 추출할지, 새로 만들지 결정한다.
4. **결정 근거를 작업 요약에 남긴다.**

## 적용 대상

- UI 컴포넌트, 모달/팝업/다이얼로그/알림, 폼 요소, 내비게이션
- 서비스·헬퍼·훅·스토어·API 래퍼
- 스타일 클래스, 디자인 토큰, 유틸리티 함수
- 테스트 헬퍼, fixture, mock
- 설정 로더, 경계 어댑터

## 1. Inventory 먼저

```bash
rg --files {{SOURCE_DIR}} | rg -i "(modal|dialog|toast|loading)"
rg -n "TargetSymbolOrClassName" {{SOURCE_DIR}}
```

확인 범위:

- **파일명**: 관련 키워드로 `rg --files`
- **코드**: 컴포넌트·함수·클래스의 정의와 사용처
- **스타일**: 클래스 계열과 owner 파일
- **테스트**: 기존 계약 테스트와 fixture
- **문서**: `.agents/rules`, `.agents/docs/product-specs`, 진행 중 계획

## 2. 판정

| 분류      | 조치                                                  |
| --------- | ----------------------------------------------------- |
| 이미 있음 | 새 파일 금지. 그대로 쓰거나 필요한 props/state만 확장 |
| 부분 구현 | 기존 owner를 유지하고 누락된 계약만 보강              |
| 중복 구현 | 새로 추가하지 말고 통합·삭제 계획을 세운다            |
| 없음      | 새로 만들 수 있다. 단 사용처와 owner를 명시한다       |

## 3. 공통 추출 기준

- 같은 역할이 **2곳 이상** 있거나 곧 2곳 이상 적용될 계획이면 공통 후보로 둔다.
- 같은 역할이 다른 이름으로 이미 있으면, 새로 만들지 말고 **기존 것을 개선**한다.
- 공통 컴포넌트는 **실제 호출처 적용과 함께** 만든다. 사용처 없는 primitive만 추가하지 않는다.
- 추출할 때 기존 동작·레이아웃 소유권·테스트 커버리지를 유지한다.

## 4. 스타일 owner

- 새 스타일 파일을 만들기 전에 기존 클래스 계열의 owner를 확인한다.
- 같은 variant의 스타일은 한 owner에 모은다.
- 화면 하나의 특수 값을 공통 토큰인 것처럼 추가하지 않는다.

## 5. 기록 의무

사소하지 않은 작업은 요약에 남긴다.

- 검색한 기존 owner
- 새로 만들지 않고 재사용·확장한 이유
- 새로 만들었다면 기존 구현으로 부족했던 이유
- 공통 추출 범위와 적용된 호출처

## 금지

- 기존 구현 검색 없이 새 컴포넌트·헬퍼·스타일 생성
- 기존 owner가 있는데 병렬 owner를 새로 만드는 것
- 실제 사용처 없는 공통 primitive 추가
- 기존 fixture를 확인하지 않고 중복 fixture 생성

## 리뷰 체크리스트

- [ ] 구현 전에 관련 기존 코드와 테스트를 검색했다
- [ ] 같은 역할의 owner가 확인됐다
- [ ] 새로 만든 경우 기존 구현으로 부족한 이유가 명확하다
- [ ] 반복 UI가 공통 owner로 수렴한다
- [ ] 미사용 헬퍼/primitive가 추가되지 않았다
