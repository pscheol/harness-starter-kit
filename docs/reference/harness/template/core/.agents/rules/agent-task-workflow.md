# Agent Task Workflow — {{PROJECT_NAME}}

기준 순서:

```text
요구사항 -> SDD(requirements/design/tasks) -> 구현 -> 검증 -> 검토
```

이슈 트래커는 **입력과 추적 표면**이지 엔지니어링 규칙의 출처가 아니다. 규칙의 출처는 `AGENTS.md`, `.agents/rules`, `.agents/skills`, 기존 코드 owner, 그리고 `scripts/`의 검증 스크립트다.

## 1. 착수 전 (Debug Before New)

수정 요청, 검토 실패, 미완료 브랜치 복구는 **기존 근거 위의 디버깅**이다. 기존 브랜치를 되살릴 수 없다는 사실이 기록되기 전에는 병렬 구현을 새로 만들지 않는다.

코딩 전 순서:

1. 요청 본문, 코멘트, 연결된 이슈, 리뷰 노트, 브랜치/PR 근거를 모두 읽는다.
2. `rg`로 기존 코드와 문서 owner를 찾는다 (`.agents/rules/reuse-before-new.md`).
3. 새 파일을 만들기 전에 기존 owner를 재사용·확장할 수 있는지 판단한다.
4. 영향 범위와 부작용 범위를 정의한다.
5. 코드 편집 전에 `.agents/docs/product-specs/<작업단위>/`의 SDD 산출물을 만들거나 갱신한다.
6. `.agents/rules/verification-ladder.md`에서 이 변경에 맞는 검증 수준을 고른다.

## 2. SDD 산출물

코드 영향 작업에 필요한 세 문서:

```text
requirements.md  요구사항, 완료 조건, 테스트 방법, 근거 매핑
design.md        기존 owner, 영향 범위, 설계 결정, 위험, 비범위
tasks.md         구현 태스크와 검증 태스크 체크박스
```

세 파일은 `.agents/docs/product-specs/<작업단위>/` **한 폴더**에 모은다. 개별 티켓을 위해 `design-docs/<ticket>`이나 `exec-plans/<ticket>`을 만들지 않는다.

SDD 생략이 허용되는 경우:

- 단일 파일 1~2줄 수정
- 문서만 바꾸는 변경
- 하네스 메타데이터만 바꾸는 변경
- 이미 기존 spec 폴더의 태스크로 연결된 작업

생략했으면 결과 보고에 `SDD exception: <이유>`를 남긴다. 사용했으면 `SDD spec: <경로>`를 남긴다.

## 3. 구현 절차

1. 기준 브랜치(`{{DEFAULT_BRANCH}}`)의 최신 상태를 가져온다.
2. 새 로컬 세션이면 하네스 상태를 확인한다 (`{{CMD_VERIFY_HARNESS}}`).
3. 작업 하나당 브랜치 하나를 만든다 (`.agents/rules/git-branch-policy.md`).
4. 코드 편집 전에 SDD spec을 만들거나 갱신한다.
5. `tasks.md`에서 **가장 작은 검증 가능한 태스크 하나**를 구현한다.
6. 대상 테스트를 먼저 돌리고, 그다음 필수 게이트를 돌린다.
7. 코드 변경과 `tasks.md` 체크박스 갱신을 **같은 커밋**에 넣는다.
8. 검토로 넘기기 전에 브랜치를 원격에 push한다.
9. 검증 근거를 결과 보고에 기록한다.

## 4. 기본 게이트

코드 영향 작업의 기본:

```bash
{{CMD_TYPECHECK}}
{{CMD_LINT}}
{{CMD_TEST}}
```

다음 변경은 여기에 `{{CMD_BUILD}}` 또는 `{{CMD_PRECOMMIT}}`까지 추가한다.

```text
보안 경계 / 프로세스 경계 / 프로세스 간 통신
패키징 · 릴리즈 · 업데이터
인증 · 최초 실행 흐름
호출처가 넓은 공용 서비스나 헬퍼
대규모 리팩터링 또는 마이그레이션
```

환경 문제로 전체 게이트를 못 돌리면, 같은 항목을 가능한 범위로 쪼개 실행하고 **생략 사유와 잔여 위험을 반드시 기록**한다. 조용한 생략은 통과로 읽힌다.

## 5. 동시 작업 슬롯

한 세션/워크트리는 **한 번에 하나의 작업**만 진행 중 상태로 둔다.

여러 작업을 요청받으면 순차 큐로 처리한다.

1. 후보 목록을 만든다.
2. 정확히 하나를 claim 한다.
3. 완료·차단·해제 중 하나로 종료한다.
4. 상태를 다시 조회한다.
5. 다음 하나를 claim 한다.

## 6. 완료 보고

작업을 넘길 때 반드시 포함한다.

```text
변경 파일 목록
실행한 검증과 결과 (생략한 것과 그 이유 포함)
SDD spec 경로 또는 exception 사유
잔여 위험과 사람이 확인해야 할 항목
```

## 7. 금지

- 요구사항 확인 없이 구현을 시작하는 것
- 검증 실패를 보고하지 않고 완료로 처리하는 것
- 요청 범위를 임의로 넓히거나 좁히는 것
- 기존 owner를 확인하지 않고 병렬 구현을 만드는 것
- `tasks.md` 갱신 없이 코드만 커밋하는 것
