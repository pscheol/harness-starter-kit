1한눈에 보기

세 가지 질문에 먼저 짧게 답하고, 나머지 절에서 근거와 방법을 풀어 갑니다.

둘은 서로 다른 구현 방법론인가?

아니요, 층이 다릅니다

AI-DLC는 무엇을 왜 만들고 언제 누가 승인할지를 정하는 개발 방법론입니다. Entire는 에이전트가 쓴 코드와 그 과정을 저장하고 검토하는 Git 플랫폼입니다. 둘이 겹치는 곳은 코드 리뷰와 병합 구간 정도입니다.

같이 쓰는 건 불가능한가?

가능합니다

둘 다 Claude Code, Codex, Cursor, Copilot CLI, OpenCode를 지원하고, 저장소 안에서 쓰는 폴더도 대부분 다릅니다. 다만 공식 연동은 없고, 둘 다 .claude/settings.json에 훅을 넣기 때문에 설치 순서와 점검이 필요합니다.

같이 쓰면 무엇이 좋아지나?

결론과 과정이 함께 남습니다

사람이 승인한 요구사항과 설계(AI-DLC)에, 에이전트가 거기까지 간 대화와 도구 호출(Entire)이 커밋 단위로 붙습니다. 코드 리뷰 1차는 에이전트에 맡기고, 결정은 계속 사람이 합니다.

2Entire는 무엇인가

Entire는 GitHub CEO였던 Thomas Dohmke가 세운 회사이자 제품 이름입니다. 2026년 2월에 첫 제품인 Checkpoints CLI를 오픈소스로 내놓으며 시작했고, 10월 26일에는 Trails를 앞세운 Git 포지를 모든 개발자에게 열었습니다. 스스로를 “에이전트와 사람이 함께 일하는 Git 포지”라고 소개합니다.

출발점은 리뷰 병목입니다. 에이전트가 코드를 빨리 쓸수록 사람이 diff를 읽는 속도가 따라가지 못하고, 에이전트 세션이 끝나면 “왜 이렇게 짰는지”가 사라집니다. Entire는 이 두 문제를 각각 체크포인트(과정 기록)와 Trails(에이전트 평가 기반 리뷰)로 풉니다.

네 덩어리로 나눠 보기

Checkpoints: 과정을 커밋에 붙인다

내 컴퓨터에서 도는 CLI입니다(MIT 라이선스). 에이전트 훅과 Git 훅으로 프롬프트, 대화, 도구 호출, 바뀐 파일, 토큰 사용량을 모았다가, 커밋하는 순간 그 내용을 체크포인트로 저장합니다.

커밋 메시지에는 Entire-Checkpoint 트레일러가 붙고, 기록은 내 저장소 안의 별도 ref에 들어가므로 작업 브랜치는 깨끗하게 남습니다.

Git 포지: 미러와 호스팅

GitHub 저장소를 미러로 등록하면 에이전트가 가까운 리전에서 clone과 push를 합니다. push는 미러를 거쳐 GitHub로 가므로 기존 권한, 브랜치 보호, 리뷰 규칙이 그대로 적용됩니다.

Entire에 저장소를 직접 만들 수도 있고, 데이터 보관 리전을 고를 수 있습니다.

Trails: 풀 리퀘스트를 대신하는 리뷰 단위

작업의 의도, 코드, 에이전트 세션, 리뷰 근거를 시작부터 병합까지 한곳에 모읍니다. push마다 리뷰 에이전트가 클라우드 샌드박스에서 돌며 점수와 근거, 고칠 항목(Findings)을 남깁니다.

최근 다섯 번의 결과가 나란히 보여서, 에이전트가 쓴 코드가 안정됐는지 흐름으로 판단합니다. 병합 조건은 Gates로 정합니다.

기억과 검색 (선택)

Brain은 저장된 세션, 체크포인트, 문서, 코드 맥락을 묶은 프로젝트 기억이라 Claude Code에서 Codex로 바꿔도 이전 맥락을 넘겨줄 수 있습니다. entire-graph는 함수와 타입이 어떻게 이어지는지 보여 주는 코드 지도입니다.

그 밖에 과거 작업 검색(search), 활동 요약(recap, dispatch)이 있습니다.

용어 정리

용어뜻
Session에이전트와 한 번 작업한 기록. 프롬프트, 대화, 도구 호출, 바뀐 파일, 토큰 사용량이 들어갑니다.
Checkpoint세션 기록을 Git 커밋 하나에 연결한 것. 에이전트 턴마다가 아니라 커밋할 때 생깁니다. 세션 하나가 여러 커밋에 걸치거나, 커밋 하나에 세션 여러 개가 묶일 수 있습니다.
Trail풀 리퀘스트를 대신하는 상위 단위. 제목, 설명, 유형, 우선순위, 담당자, 의도한 결과를 담습니다. 버그 리포트, 기능 요청, 에이전트의 계획에서 시작할 수 있고 여러 저장소에 걸칠 수 있습니다.
ChangeTrail에 연결된 브랜치. 저장소마다 하나씩이고, 따로 리뷰하고 따로 병합합니다.
Agent (리뷰 에이전트)Trail의 변경을 평가하는 AI 작업. 기본 제공은 Code review, Security review, Slop 세 가지이고 직접 만들 수도 있습니다.
Finding리뷰 에이전트가 찾아낸 고칠 항목. 고치거나, 해결 처리하거나, 기각해야 병합 조건을 통과합니다.
Gate병합 조건. Up to Date(기준 브랜치와 최신 상태), Human Review(사람 승인), Agent Review(남은 Finding), Checks(CI) 네 가지입니다.
MirrorGitHub 저장소를 Entire 리전에 비춰 둔 사본. 에이전트는 미러로 clone과 pull을 하고, push는 미러를 거쳐 GitHub로 갑니다.
비용

공식 문서 기준으로 돈이 드는 것은 리뷰 에이전트 같은 Agent 사용뿐이고, 나머지 기능은 무료로 쓸 수 있습니다. Agent 사용료는 선불 크레딧에서 모델 토큰 단가대로 빠집니다. 직접 만든 리뷰 에이전트를 쓰려면 결제 수단을 등록해야 합니다. 가격은 바뀔 수 있으니 쓰기 전에 Billing 문서를 확인하세요.

3Entire 사용법

설치부터 첫 Trail까지 순서대로 따라 할 수 있게 적었습니다. 명령은 공식 문서에 나온 그대로입니다. 4~7단계는 계정이 필요하고, 1~3단계는 혼자서도 됩니다.

  1. CLI 설치

    macOS, Linux, Windows를 지원하고 Git 2.25 이상이 필요합니다.

    # macOS
brew install --cask entireio/tap/entire
# Linux
curl -fsSL https://entire.com/install.sh | bash
# Windows PowerShell
irm https://entire.com/install.ps1 | iex
# 설치 확인
entire version

  2. 저장소에서 켜기

    저장소 루트에서 에이전트를 지정해 켭니다. 에이전트 훅과 Git 훅이 설치되고 .entire/settings.json, .entire/.gitignore가 생깁니다. Claude Code는 2.1.78 이상이어야 기록되고, 훅을 설치한 뒤에는 Claude Code 세션을 새로 열어야 합니다.

    cd my-project
entire enable -y --agent claude-code
# 이미 켠 저장소에 에이전트를 하나 더 붙일 때
entire agent add codex
entire agent list

  3. 첫 체크포인트 만들기

    에이전트에게 작은 일을 시키고 평소처럼 커밋합니다. “이 커밋을 세션과 연결할까요?”라고 물으면 Enter를 누릅니다. always를 고르면 다음부터 묻지 않습니다.

    git add hello-entire.md
git commit -m "Add first Entire checkpoint"
entire checkpoint list
entire status --detailed   # 세션이 안 보이면 entire doctor

  4. 기록 들여다보기

    낯선 코드를 고치기 전에 그 코드가 왜 생겼는지 거슬러 올라갈 때 씁니다. blame과 why는 아직 실험 기능이라 출력 형식이 바뀔 수 있고, 줄 단위가 아니라 커밋 단위로 귀속을 알려 줍니다.

    entire blame src/main.js --line 279          # 그 줄의 커밋과 체크포인트
entire why src/main.js:279                   # 원래 프롬프트와 세션
entire checkpoint explain <체크포인트ID> --generate   # 의도와 결과 요약
entire session resume <브랜치>               # 그 브랜치 세션 이어서 열기

  5. GitHub 저장소를 미러로 등록

    로그인하고 Entire GitHub App이 저장소에 접근할 수 있게 한 뒤 미러를 만듭니다. origin은 그대로 GitHub를 가리키고 entire 원격이 하나 더 생깁니다.

    entire login
entire repo mirror add          # 저장소와 리전 선택
entire repo remote add entire
git fetch entire
git push entire

  6. 첫 Trail 만들기

    기준 브랜치에서 실행하면 제목으로 브랜치를 만들어 올리고 Trail에 연결합니다. 그 브랜치의 변경, 세션, 체크포인트는 자동으로 Trail에 붙습니다.

    entire trail create --title "My first Entire trail" --checkout
entire trail show
# 작업, 커밋 후
git push origin my-first-entire-trail

  7. 리뷰 에이전트와 Gates 켜기 (웹)

    entire.com의 프로젝트에서 Agents로 들어가 기본 에이전트(Code review, Security review, Slop)를 켜거나 New agent로 직접 만듭니다. 이어서 저장소 Settings → Gates에서 병합 조건을 정합니다. Trails를 켠다고 리뷰 에이전트가 따라 켜지지는 않으니 둘 다 따로 설정해야 합니다.

더 써 볼 기능

내 컴퓨터에서 교차 리뷰

에이전트 두 개에게 같은 변경을 리뷰시키고 한 에이전트가 결과를 합칩니다. Trail을 쓰기 전에 혼자 연습하기 좋습니다.

entire review --configure --set-agents codex,claude-code --set-judge codex --set-output local
entire review general --prompt "Focus on risky state transitions and missing tests."
entire recap --week --static     # 한 주 동안의 세션, 체크포인트, 토큰 사용 요약

프로젝트 기억(Brain)과 코드 지도(entire-graph)

설정하면 AGENTS.md와 CLAUDE.md에 관리 블록이 추가되고, 에이전트는 작업 전에 entire brain brief로 관련 맥락을 모읍니다. 기억은 기본적으로 내 컴퓨터에만 있고, entire brain connect를 해야 Entire 저장소와 동기화됩니다.

entire plugin install brain
entire plugin install graph
entire brain setup
entire graph setup
entire brain status

민감 정보 가리기

체크포인트에는 프롬프트와 대화 원문이 들어가므로 무엇이 남는지 알고 써야 합니다. API 키, 액세스 토큰, 자격 증명이 든 URL, DB 접속 문자열, 개인 키는 기본으로 가려집니다. 개인정보(PII) 가리기는 기본으로 꺼져 있고, 사내 패턴은 직접 추가합니다(Go RE2 정규식). 아래 내용은 팀 공용이면 .entire/settings.json에, 나만 쓸 거면 .entire/settings.local.json에 넣습니다. commit_linking을 always로 두면 커밋할 때마다 연결 여부를 묻지 않습니다.

{
  "commit_linking": "always",
  "redaction": {
    "custom_redactions": {
      "acme_token": "ACME_TOKEN_[A-Za-z0-9]{20,}"
    }
  }
}

저장소에 생기는 것

경로커밋 여부용도
.entire/settings.json커밋 (팀이 함께 쓸 때)체크포인트 저장 방식, 팀 가리기 규칙 같은 공용 설정
.entire/settings.local.json커밋 안 함개인 설정, 개인 가리기 규칙
.entire/redactors/커밋팀 공용 가리기 규칙 묶음
.claude/, .codex/, .cursor/ 등에이전트별각 에이전트의 훅 설정. Claude Code는 .claude/settings.json에 훅을 추가하고 관계없는 설정은 그대로 둡니다.
refs/entire/checkpoints/…작업 파일 아님체크포인트 저장소(0.10.0 이후 기본). 코드와 함께 push됩니다. 그 전에 켠 저장소는 entire/checkpoints/v1 브랜치를 씁니다.
.git/entire-sessions/Git 디렉터리 안진행 중인 세션 상태

4AI-DLC와 무엇이 다른가

질문을 바꿔 보면 차이가 선명해집니다. AI-DLC가 답하는 질문은 “이번 Intent에서 무엇을 어떤 순서로 정하고, 사람은 어디서 승인하는가”입니다. Entire가 답하는 질문은 “에이전트가 만든 변경을 어디에 남기고, 병합해도 되는지 어떻게 판단하는가”입니다.

예전 도구로 치면 AI-DLC는 스크럼이나 애자일 같은 일하는 방식에, Entire는 GitHub 같은 저장소와 리뷰 플랫폼에 가깝습니다. 스크럼과 GitHub 중 하나를 고르는 팀이 없듯이, 둘은 고르는 대상이 아니라 쌓는 대상입니다.

비용무료. 쓰는 에이전트의 모델 비용만 듭니다리뷰 에이전트 같은 Agent 사용만 선불 크레딧으로 과금. 나머지는 무료

Entire에도 작업 방식이 들어 있다

Entire를 그냥 저장소로만 보면 놓치는 부분이 있습니다. Trails에는 “에이전트가 push하면 리뷰 에이전트가 채점하고, Finding을 고쳐 다시 push하고, 점수가 안정되면 병합한다”는 리뷰 순환이 들어 있습니다. 공식 문서도 Trail의 목적을 코딩 에이전트와 리뷰 에이전트 사이의 순환이 충분히 돌아 안정 상태에 이르렀는지 보여 주는 것이라고 설명합니다.

다만 이것은 코드 변경 하나를 다루는 리뷰 방식이지, 요구사항을 정하고 설계를 쪼개는 개발 수명주기 전체를 다루는 방법론은 아닙니다. 그래서 두 도구가 실제로 부딪치는 자리는 “리뷰와 승인” 한 곳뿐입니다.

겹치는 곳 1. 맥락 보존

AI-DLC는 결론을 남깁니다. “이 요구사항으로 정했고 누가 승인했다”가 문서로 남습니다. AI-DLC 2.x 세션 관리 문서에는 대화 원문이나 도구 호출 로그를 저장한다는 내용이 없습니다.

Entire는 과정을 남깁니다. 그 결론까지 어떤 프롬프트와 도구 호출을 거쳤는지가 커밋에 붙습니다. 그래서 둘은 서로의 빈자리를 채웁니다.

겹치는 곳 2. 리뷰 철학

AI-DLC는 “사람이 결정한다”를 원칙으로 게이트를 강제합니다. Trails는 사람이 diff를 다 읽는 부담을 에이전트 평가로 줄이려 합니다. 방향이 반대처럼 보입니다.

하지만 검토 대상이 다릅니다. AI-DLC 게이트는 요구사항, 설계, 유닛 완료 같은 결정을 승인하고, Trails는 push된 코드를 평가합니다. Trails의 Human Review 게이트로 사람 승인을 병합 조건에 넣을 수도 있습니다.

5같이 쓸 수 있나

쓸 수 있습니다. 두 도구 모두 같은 코딩 에이전트 위에서 동작하고, 한쪽은 일하는 순서를, 다른 쪽은 기록과 리뷰를 맡아 역할이 거의 겹치지 않습니다. 다만 두 가지는 알고 시작해야 합니다.

  • 두 회사가 만든 공식 연동은 없습니다. 2026년 11월 22일 기준으로 둘을 함께 쓴 공개 사례도 찾지 못했습니다. 아래 내용은 각 도구의 공식 문서를 맞춰 본 결과입니다.
  • 둘 다 Claude Code의 .claude/settings.json에 훅을 넣습니다. 설치 순서를 지키고, 설치한 뒤 양쪽이 모두 살아 있는지 확인해야 합니다(6절).

왜 서로 부딪치지 않나

  • 훅이 하는 일이 다릅니다. AI-DLC 훅은 워크플로가 돌 때만 움직이며 순서와 규칙을 지킵니다. Entire 훅은 막지 않고 기록만 합니다. Claude Code는 같은 이벤트에 등록된 훅을 모두 실행합니다.
  • 기록이 겹치지 않고 이어집니다. AI-DLC는 상태, 결과물, 감사 기록을 파일로 남기고, Entire는 그 파일을 만든 대화와 도구 호출을 커밋에 붙입니다. AI-DLC가 코드 생성(3.5 스테이지)을 서브에이전트로 돌려도, Entire는 서브에이전트 작업을 부모 세션에 귀속해 다음 체크포인트에 넣습니다.
  • 커밋은 사람이 정합니다. AI-DLC 세션 관리 문서에는 Git 커밋 이야기가 없고, Entire 체크포인트는 커밋할 때 생깁니다. 그래서 “언제 커밋하느냐”를 팀 규칙으로 정해 두면 두 도구의 단위가 맞물립니다(9절).

6함께 쓰는 설정 순서

Claude Code를 기준으로 했습니다. 핵심은 AI-DLC를 먼저 깔고 Entire를 나중에 켜는 것, 그리고 설치 뒤 두 쪽 훅이 모두 살아 있는지 확인하는 것입니다.

  1. 준비

    Git 저장소와 Claude Code 2.1.78 이상이 필요합니다. 처음에는 실제 서비스 저장소 말고 작은 연습 저장소에서 해 보세요.

    claude --version
git status

  2. 두 도구 설치

    # AI-DLC (macOS, Linux, WSL)
curl -fsSL https://github.com/awslabs/aidlc-workflows/releases/latest/download/install.sh | sh
# Entire (macOS는 brew install --cask entireio/tap/entire)
curl -fsSL https://entire.com/install.sh | bash

  3. AI-DLC를 먼저 프로젝트에 깔기

    cd my-project
aidlc config --harness claude
aidlc doctor

  4. 그다음 Entire 켜기

    Entire는 .claude/settings.json에 자기 훅을 추가하고 다른 설정은 보존합니다.

    entire enable -y --agent claude-code

  5. 커밋 연결을 자동으로

    에이전트가 커밋하면 “세션과 연결할까요?” 질문에 답할 사람이 없을 수 있습니다. 팀 공용 설정에 넣어 두세요.

    // .entire/settings.json 에 추가
"commit_linking": "always"

  6. 두 쪽이 모두 살아 있는지 확인

    .claude/settings.json을 열어 aidlc engine hook … 명령과 Entire 명령이 함께 들어 있는지 눈으로 봅니다. 그리고 Claude Code를 새로 열어야 새 훅이 적용됩니다.

    aidlc doctor
entire agent list
entire status --detailed
claude          # 새 세션으로 시작

  7. (선택) 미러, Trails, Gates

    팀 리뷰까지 Entire로 하려면 미러를 만들고 리뷰 에이전트와 Gates를 켭니다(3절 5~7단계). 처음 몇 주는 기존 GitHub PR과 나란히 돌려 보세요.

나중에 AI-DLC를 업데이트할 때

aidlc config를 다시 실행했다면 Entire 훅이 남아 있는지 확인하세요. 빠졌으면 entire agent add claude-code --force로 다시 넣습니다. 반대로 AI-DLC 쪽이 이상하면 aidlc doctor부터 봅니다.

7함께 쓰는 작업 흐름

Intent 하나를 처음부터 병합까지 따라가 봅니다. 사람, AI-DLC, 내 컴퓨터의 Entire CLI, entire.com이 각각 언제 움직이는지 보세요.

  1. Intent를 Trail로 연다

    Intent 한 문장을 Trail 제목과 “의도한 결과” 칸에 그대로 씁니다. 기준 브랜치에서 실행하면 작업 브랜치가 생기고, 이후 세션과 체크포인트가 이 Trail에 붙습니다.

    entire trail create --title "회의실 예약 API" --type feature --checkout
claude
> /aidlc 회의실 예약 REST API를 Spring Boot로 만들어줘

  2. Inception은 AI-DLC 방식 그대로

    AI-DLC가 질문하고, 요구사항, 스토리, 유닛을 만들고, 사람이 승인합니다. 이 구간에서 Entire는 끼어들지 않고 대화만 기록합니다.

  3. 승인한 문서를 커밋한다

    Inception 승인 직후 aidlc/ 아래 결과물을 커밋합니다. 이 커밋의 체크포인트에는 요구사항을 만든 질문과 답변 대화가 붙어, 나중에 “이 요구사항은 어떤 대화에서 나왔나”를 바로 찾을 수 있습니다.

  4. 유닛마다 구현하고 승인한다

    AI-DLC가 유닛 설계, 코드, 검증을 하고, 검증 명령이 exit 0으로 끝나면 사람이 유닛을 승인합니다. 여기까지는 AI-DLC 규칙 그대로입니다.

  5. 유닛 하나를 커밋 하나로 push한다

    유닛이 승인되면 커밋하고 push합니다. 유닛 하나가 체크포인트 하나가 되므로, 리뷰도 추적도 유닛 단위로 할 수 있습니다.

  6. 리뷰 에이전트가 채점한다

    push마다 리뷰 에이전트가 점수와 Finding을 남깁니다. Finding을 고칠 때는 다시 AI-DLC로 돌아가 해당 유닛 안에서 고치고, 고친 내용을 커밋해 push합니다. 최근 다섯 번의 점수가 안정되는지 봅니다.

  7. Gates를 통과하면 병합한다

    사람 리뷰, 남은 Finding, CI, 최신 상태 조건이 모두 통과하면 병합합니다. 미러 저장소라면 병합은 연결된 GitHub PR로 이뤄지고, GitHub 쪽 승인 규칙도 따로 지켜야 합니다.

8같이 쓰면 좋아지는 것

하나만 쓸 때 비어 있던 자리를 다른 쪽이 채우는 경우만 골랐습니다.

결론과 과정이 한 커밋에 묶인다

AI-DLC만 쓰면 무엇을 정했는지는 남지만 에이전트가 어떻게 만들었는지는 사라집니다. Entire만 쓰면 과정은 남지만 그 작업이 어떤 승인된 요구사항에서 왔는지가 흐립니다.

장애 난 줄에서 entire why → 원래 프롬프트와 체크포인트 → 커밋 메시지의 REQ ID → AI-DLC 요구사항과 audit/에서 누가 왜 승인했는지까지 한 번에 따라갑니다.

리뷰 부담은 줄고 결정은 사람에게 남는다

요구사항, 설계, 유닛 완료 같은 결정은 계속 AI-DLC 게이트에서 사람이 승인하고, Trails 리뷰 에이전트가 코드의 1차 검토를 맡습니다. 사람은 Finding이 가리킨 곳과 점수가 흔들리는 곳만 깊게 봅니다.

diff 수천 줄을 다 읽는 대신 “Security 점수가 지난 push보다 떨어진 이유”부터 봅니다.

의도 이탈을 기준을 갖고 잰다

리뷰 에이전트가 Drift를 평가하려면 원래 의도가 글로 있어야 합니다. AI-DLC Inception이 만든 요구사항, 수용 기준, 비기능 목표가 바로 그 기준이 됩니다.

US-03의 수용 기준을 리뷰 에이전트 지시문에 넣으면 “기준마다 테스트가 있는가”를 push마다 확인합니다(9절).

에이전트나 모델을 바꿔도 맥락이 이어진다

AI-DLC는 park와 resume으로 진행 위치를 이어 주지만, 문서에 적히지 않은 대화 맥락은 넘어가지 않는다고 밝힙니다. Entire의 세션 재개와 Brain이 그 대화 맥락을 넘겨줍니다.

Claude Code로 Inception을 마치고 Codex로 유닛 하나를 맡길 때, 앞선 질문과 답변을 다시 설명하지 않아도 됩니다.

운영에서 원인을 찾는 길이 짧아진다

AI-DLC는 운영에서 얻은 신호를 다음 Intent의 입력으로 삼습니다. Entire 기록이 있으면 그 신호가 어떤 결정과 어떤 대화에서 나온 코드인지 바로 찾을 수 있습니다.

entire blame → entire checkpoint explain --generate로 의도와 결과를 확인하고, 고칠 범위를 새 Intent로 엽니다.

회고 재료가 저절로 쌓인다

AI-DLC는 스테이지 결과와 배운 규칙을 남기고(/aidlc-session-cost, /aidlc-outcomes-pack), Entire는 세션, 체크포인트, 토큰 사용을 요약합니다(entire recap).

“어느 스테이지에서 질문이 가장 많이 오갔고, 어느 유닛에서 Finding이 몰렸나”를 숫자로 보고 다음 Intent의 깊이를 조정합니다.

9활용 방법

바로 가져다 쓸 수 있는 규칙과 설정 예시입니다. 공식 템플릿이 아니라 두 도구의 문서를 맞춰 이 문서에서 만든 예시이니, 팀에 맞게 고쳐 쓰세요.

1. 커밋 규칙: 유닛 하나에 커밋 하나

두 도구를 잇는 고리는 커밋입니다. AI-DLC는 커밋 시점을 정하지 않고, Entire는 커밋할 때 체크포인트를 만듭니다. 그래서 커밋 시점을 팀 규칙으로 못박으면 둘의 단위가 맞물립니다.

  • Inception 승인 직후 결과물을 한 번 커밋합니다.
  • Construction에서는 유닛이 검증(exit 0)과 사람 승인을 통과했을 때만 커밋합니다.
  • 커밋 메시지에 유닛 이름과 요구사항, 스토리 ID를 넣습니다. Entire의 why와 blame이 이 메시지까지 함께 보여 줍니다.
docs(inception): 회의실 예약 요구사항과 유닛 분해 승인 [intent 261122-room-booking]
feat(U1): 예약 생성 API [REQ-RES-001, US-01]
fix(U1): 같은 시간대 중복 예약 막기 [REQ-RES-003] (Trail Finding 반영)

2. “AI-DLC 추적 검사” 리뷰 에이전트 만들기

4. 도입 단계

  • 연습 저장소에 AI-DLC와 Entire Checkpoints만 켭니다. 계정도 비용도 필요 없습니다.
  • “유닛 하나에 커밋 하나” 규칙을 손에 익힙니다.
  • 주말에 커밋 하나를 골라 entire why와 entire checkpoint explain으로 거꾸로 따라가 봅니다. AI-DLC 문서의 어느 요구사항과 이어지는지 확인합니다.
  • 미러를 만들고 기본 리뷰 에이전트 세 개를 켭니다.
  • 기존 GitHub PR 리뷰는 그대로 유지하고, Trails 결과와 나란히 비교합니다.
  • Finding마다 “사람 리뷰에서도 잡았을까, 쓸모 있었나”를 짧게 적어 둡니다. 이 기록이 Gates 기준을 정하는 근거가 됩니다.
  • 2~3주차 기록을 보고 Gates를 켭니다(3번 표).
  • AI-DLC 추적 검사 에이전트를 추가합니다(2번).
  • 여러 에이전트를 오가거나 저장소가 크면 Brain과 entire-graph를 붙입니다. 이때 AI-DLC의 학습 규칙(memory/)과 Brain 기억이 서로 다른 말을 하지 않는지 가끔 확인합니다.
혼자 개발하거나 공부 중이라면

1주차 단계만으로도 얻는 것이 큽니다. AI-DLC로 요구사항과 설계를 정하고 Entire Checkpoints로 과정을 남기면, 몇 주 뒤의 내가 “그때 왜 이렇게 했지”를 바로 찾을 수 있습니다. Trails와 리뷰 에이전트는 팀 리뷰가 병목이 될 때 붙여도 늦지 않습니다.

10주의할 점

  • 공식 연동이 없습니다. 둘을 함께 쓴 공개 사례를 찾지 못했으니, 실제 서비스 저장소에 넣기 전에 연습 저장소에서 6절 순서를 먼저 돌려 보세요.
  • 설정 파일을 나눠 씁니다. 두 도구 모두 .claude/settings.json에 훅을 넣습니다. AI-DLC를 업데이트하거나 aidlc config를 다시 돌린 뒤에는 Entire 훅이 남아 있는지 확인합니다.
  • 대화 원문이 저장소에 올라갑니다. 체크포인트에는 프롬프트와 대화가 들어가고 코드와 함께 push됩니다. 비밀 값은 기본으로 가려지지만 개인정보 가리기는 꺼져 있고, 이미지 내용은 검사하지 않습니다. 고객 데이터를 프롬프트에 붙여 넣는 습관이 있다면 가리기 규칙부터 정하세요.
  • 비용이 양쪽에서 듭니다. AI-DLC는 스테이지가 많아 토큰을 꽤 쓰고, 리뷰 에이전트는 push마다 돕니다. 경로 필터와 트리거로 리뷰 에이전트가 도는 범위를 좁히세요.
  • 승인이 플랫폼마다 따로입니다. 미러 저장소에서 Entire의 승인은 GitHub 승인을 대신하지 않고, GitHub 브랜치 규칙이 따로 병합을 막을 수 있습니다.
  • 실험 기능이 섞여 있습니다. entire blame, entire why는 실험 기능이라 출력이 바뀔 수 있고, 줄 단위가 아니라 커밋 단위로 귀속합니다. entire investigate도 실험 단계입니다.
  • Kiro는 아직 짝이 안 맞습니다. AI-DLC는 Kiro를 지원하지만 Entire 공식 문서의 지원 에이전트 목록에는 Kiro가 없습니다. 함께 쓰려면 Claude Code를 권합니다.
  • 둘 다 빨리 바뀝니다. Entire는 2026년 2월에 첫 제품을 냈고 10월에 포지를 열었습니다. AI-DLC 2.x도 몇 주 간격으로 새 버전이 나옵니다. 이 문서의 명령은 2026년 11월 22일 기준이니, 쓰기 전에 공식 문서를 한 번 더 보세요.

11스스로 점검하기

답을 펼치기 전에 먼저 소리 내어 답해 보세요.

AI-DLC와 Entire가 각각 답하는 질문은 무엇인가?

AI-DLC는 “무엇을 왜 만들고, 어떤 순서로 정하고, 누가 승인하나”에, Entire는 “에이전트가 만든 변경을 어디에 남기고, 병합해도 되는지 어떻게 판단하나”에 답합니다. 방법론과 플랫폼이라 층이 다릅니다.

Entire 체크포인트는 언제 생기고, 무엇이 들어 있나?

에이전트 턴마다가 아니라 커밋할 때 생깁니다. 프롬프트, 대화, 도구 호출, 바뀐 파일, 토큰 사용량이 들어가고, 커밋 메시지의 Entire-Checkpoint 트레일러로 커밋과 이어집니다.

한 저장소에 둘을 설치할 때 순서와 그 이유는?

AI-DLC(aidlc config)를 먼저, Entire(entire enable)를 나중에 합니다. 둘 다 .claude/settings.json에 훅을 넣는데, Entire는 다른 설정을 보존한다고 밝히고 AI-DLC 문서는 합치는지 덮어쓰는지 밝히지 않기 때문입니다. 설치 뒤 aidlc doctor, entire agent list, entire status --detailed로 확인합니다.

AI-DLC의 승인 게이트와 Entire의 Human Review 게이트는 무엇이 다른가?

AI-DLC 게이트는 요구사항, 설계, 유닛 완료 같은 결정을 승인합니다. Entire의 Human Review는 코드 변경을 병합해도 되는지 승인합니다. 대상이 다르니 둘 다 둡니다.

리뷰 에이전트의 의도 이탈 평가를 쓸모 있게 만드는 AI-DLC 결과물은?

Inception의 요구사항, 스토리의 수용 기준, 비기능 목표입니다. 이것을 리뷰 에이전트 지시문에 넣으면 “의도”가 막연한 설명이 아니라 ID가 붙은 기준이 됩니다.
